SQL Execution Order

October 15, 2026

When writing SQL queries, we usually start with SELECT because we first think about which columns we want to retrieve. However, SQL does not logically process clauses in the order they appear.

Understanding SQL execution order helps explain common surprises, such as why an alias defined in SELECT cannot normally be used in WHERE, and how joins combine data from multiple tables.

1. The Logical Execution Order

For a typical query, the logical processing order is: 

FROM / JOIN
WHERE
GROUP BY
HAVING
SELECT
DISTINCT
ORDER BY
LIMIT / OFFSET

This is the logical order, not necessarily the physical order in which the database executes operations. The query optimizer may choose a different execution plan to improve performance.

2. What Happens at Each Step?

  • FROM / JOIN: Identifies the tables and combines their rows.
  • WHERE: Filters individual rows before grouping.
  • GROUP BY: Groups rows for aggregate calculations.
  • HAVING: Filters groups after aggregation.
  • SELECT: Determines which columns and expressions to return.
  • DISTINCT: Removes duplicate result rows.
  • ORDER BY: Sorts the resulting rows.
  • LIMIT / OFFSET: Restricts the number of rows returned and can skip rows.

3. Understanding SQL JOINs

A JOIN combines rows from two tables based on a related column or another join condition. Different join types determine which matching and non-matching rows are included in the result.

Imagine we have the following tables.

Employees

id | name  | department_id
---|-------|--------------
1  | Alice | 10
2  | Bob   | 20
3  | Carol | NULL

Departments

id | department
---|------------
10 | Engineering
20 | Finance
30 | Marketing

INNER JOIN

Returns only rows that have a match in both tables. 

SELECT e.name, d.department
FROM employees e
INNER JOIN departments d
    ON e.department_id = d.id;

Result:

Alice | Engineering
Bob   | Finance

Carol is excluded because she has no matching department. Marketing is excluded because it has no matching employee.

LEFT JOIN (LEFT OUTER JOIN)

Returns every row from the left table and matching rows from the right table. If there is no match, the right-side columns contain NULL. 

SELECT e.name, d.department
FROM employees e
LEFT JOIN departments d
    ON e.department_id = d.id;

Result:

Alice | Engineering
Bob   | Finance
Carol | NULL

Use this when you want to keep every employee, even if they do not belong to a department.

RIGHT JOIN (RIGHT OUTER JOIN)

Returns every row from the right table and matching rows from the left table. Unmatched left-side columns contain NULL. 

SELECT e.name, d.department
FROM employees e
RIGHT JOIN departments d
    ON e.department_id = d.id;

Result:

Alice | Engineering
Bob   | Finance
NULL  | Marketing

Use this when you want every department, even those without employees. You can usually rewrite a RIGHT JOIN as a LEFT JOIN by swapping the table positions.

FULL OUTER JOIN

Returns all rows from both tables. Matching rows are combined, while unmatched rows from either table are also included with NULL values for the missing side. 

SELECT e.name, d.department
FROM employees e
FULL OUTER JOIN departments d
    ON e.department_id = d.id;

Result:

Alice | Engineering
Bob   | Finance
Carol | NULL
NULL  | Marketing

MySQL does not directly support FULL OUTER JOIN. It can be emulated with a combination of LEFT JOIN, RIGHT JOIN or UNION-based queries.

CROSS JOIN

Returns every possible combination of rows from both tables. This is called a Cartesian product. 

SELECT e.name, d.department
FROM employees e
CROSS JOIN departments d;

With three employees and three departments, the result contains nine rows.

Use it when you intentionally need every combination, such as generating all product-and-size combinations. Be careful: the result can grow very quickly.

SELF JOIN

A self join joins a table to itself. It is useful when rows in the same table are related.

For example, imagine an employees table with a manager_id column referencing another employee's id. 

SELECT
    e.name AS employee,
    m.name AS manager
FROM employees e
LEFT JOIN employees m
    ON e.manager_id = m.id;

This retrieves employees together with their managers. A LEFT JOIN also keeps employees who do not have a manager, such as the most senior person in the hierarchy.

A SELF JOIN is not a separate join operator like INNER or LEFT JOIN. It describes joining a table to itself, and it can use different join types.

JOIN Types at a Glance

  • INNER JOIN: Only matching rows from both tables.
  • LEFT JOIN: All left rows and matching right rows.
  • RIGHT JOIN: All right rows and matching left rows.
  • FULL OUTER JOIN: All rows from both tables, matched where possible.
  • CROSS JOIN: Every possible combination of rows.
  • SELF JOIN: A table joined to itself using a chosen join type.

4. JOIN vs. Subquery

A subquery is a query nested inside another query. Both JOINs and subqueries can retrieve related data, but they express the problem differently.

Suppose we want to retrieve each order with its customer's name.

Using a JOIN

SELECT
    o.id,
    c.name
FROM orders o
JOIN customers c
    ON c.id = o.customer_id;

Using a scalar subquery

SELECT
    o.id,
    (
        SELECT c.name
        FROM customers c
        WHERE c.id = o.customer_id
    ) AS customer_name
FROM orders o;

Both can return the same results when the customer relationship and data satisfy the necessary conditions. The JOIN is often easier to read when combining columns from related tables.

A scalar subquery must return at most one row for each outer row. If multiple matching customers exist, the query may fail, while a JOIN can return multiple rows.

Can a subquery be slower?

Sometimes. A correlated subquery may require repeated lookups for many outer rows. However, modern database optimizers can transform some subqueries into efficient execution strategies, including semi-joins.

Do not assume that JOINs are always faster. Compare execution plans and measure performance with realistic data before choosing an alternative.

5. Why Can't WHERE Use a SELECT Alias?

Imagine an orders table with an amount column. We want to retrieve orders whose amount including VAT exceeds 100. 

SELECT
    amount * 1.21 AS amount_with_vat
FROM orders
WHERE amount_with_vat > 100;

In many SQL databases, this fails because WHERE is logically processed before SELECT. The alias amount_with_vat has not been defined yet.

Instead, repeat the expression in WHERE:

SELECT
    amount * 1.21 AS amount_with_vat
FROM orders
WHERE amount * 1.21 > 100;

Alternatively, use a subquery to make the calculated column available to the outer query. 

SELECT *
FROM (
    SELECT amount * 1.21 AS amount_with_vat
    FROM orders
) AS calculated_orders
WHERE amount_with_vat > 100;

Some databases allow SELECT aliases in additional clauses, such as ORDER BY. Exact rules vary by database.

6. WHERE vs. HAVING

Both clauses filter data, but they operate at different stages.

  • WHERE: Filters individual rows before grouping.
  • HAVING: Filters groups after aggregation.

For example, find customers whose total spending on paid orders exceeds 500. 

SELECT
    customer_id,
    SUM(amount) AS total_spent
FROM orders
WHERE status = 'paid'
GROUP BY customer_id
HAVING SUM(amount) > 500
ORDER BY total_spent DESC;

Logically, the database:

  1. Reads the orders table.
  2. Keeps only paid orders.
  3. Groups the remaining orders by customer.
  4. Calculates each customer's total spending.
  5. Keeps groups with spending above 500.
  6. Returns the selected columns and sorts by total spending.

7. Why Does Execution Order Matter?

Understanding logical execution order helps you:

  • Understand why aliases are unavailable in WHERE.
  • Choose between WHERE and HAVING.
  • Understand when grouping and aggregation happen.
  • Choose the correct JOIN type for your requirements.
  • Understand how DISTINCT, sorting, and pagination affect results.
  • Debug queries that return unexpected results.

Remember that logical execution order explains query semantics, not necessarily performance. To understand how a database physically executes a query, inspect its execution plan with EXPLAIN.

8. Summary

The logical SQL execution order is:

FROM → WHERE → GROUP BY → HAVING
     → SELECT → DISTINCT
     → ORDER BY → LIMIT / OFFSET

The key concepts to remember are:

  • JOINs combine rows from related tables.
  • INNER JOIN returns matching rows, while LEFT, RIGHT, and FULL OUTER JOIN preserve unmatched rows from one or both sides.
  • CROSS JOIN generates every possible combination of rows.
  • SELF JOIN joins a table to itself.
  • Subqueries can retrieve related values or create intermediate results. They are not automatically slower than JOINs.
  • WHERE filters rows before grouping, while HAVING filters groups after aggregation.
  • EXPLAIN helps you inspect how the database plans to execute a query.

The goal is to understand what result you need first, write a query that produces the correct result, and then optimize it based on the actual execution plan.
