Database Replication & Read Replicas

October 15, 2026

As applications grow, a single database server can become a bottleneck. It may struggle to handle thousands of queries, become a single point of failure, or introduce high latency for users in different regions.

Database replication helps address these challenges by copying data between database servers. Read replicas use this capability to handle read queries without sending every query to the primary database.

Let's understand how they work, why they are useful, and what you need to consider before introducing them.

1. What Is Database Replication?

Database replication is the process of copying data from one database server to one or more other database servers. These copies are called replicas.

In a common setup, one database acts as the primary (also called the leader), while other databases act as replicas (also called followers or standbys). 

                 Writes
Application ───────────────► Primary Database
                                  │
                                  │ Replication
                         ┌────────┴────────┐
                         ▼                 ▼
                    Replica 1         Replica 2

The primary is responsible for accepting writes. Changes are then propagated to the replicas, which maintain copies of the primary's data.

Depending on the database and its configuration, replicas may be used for read queries, high availability, disaster recovery, or other workloads.

2. How Does Replication Work?

Imagine an e-commerce application where a customer updates their delivery address. 

1. The application sends an UPDATE to the primary.
2. The primary commits the change.
3. The change is recorded in the database's replication log.
4. A replica receives and applies the change.
5. The updated address becomes available on that replica.

Databases commonly use logs to communicate changes. For example, MySQL uses binary logs, while PostgreSQL uses write-ahead logs (WAL) for replication.

Replication is not necessarily instantaneous. Depending on the replication mode, a replica might receive a change before the original write is acknowledged, or it might apply the change a little later.

3. Types of Replication

Synchronous replication

With synchronous replication, the primary waits for confirmation from the required replica or replicas before acknowledging a transaction, according to the configured durability guarantees. 

Application ──► Primary
                   │
                   ▼
                 Replica
                   │
                   ▼
             Confirmation
                   │
                   ▼
Application receives success

Advantages:

  • Can provide stronger guarantees that changes have reached a replica before success is acknowledged.
  • Can reduce the risk of losing acknowledged changes during certain failures.

Disadvantages:

  • Writes can become slower because they depend on replica acknowledgements.
  • Network failures or unavailable replicas can affect write availability.

The exact guarantee depends on the database configuration. For example, waiting for a replica to receive a log record is not always the same as waiting for it to apply the change or persist it to durable storage.

Asynchronous replication

With asynchronous replication, the primary does not wait for replicas to confirm each change before acknowledging the write to the application. 

Application ──► Primary
                   │
                   ├──► Write succeeds
                   │
                   └──► Replica catches up afterward

Advantages:

  • Lower write latency because the primary doesn't wait for replica acknowledgements.
  • Replicas can catch up in the background.

Disadvantages:

  • Replicas may temporarily contain stale data.
  • If the primary fails before changes are replicated, some acknowledged writes may be lost during failover.

Asynchronous replication is common when read scalability is a priority and a small delay between the primary and replicas is acceptable.

Primary-replica vs. multi-primary replication

Replication also differs in which database servers can accept writes.

  • Primary-replica: One primary accepts writes, and replicas receive changes from it. This is a common and relatively straightforward architecture.
  • Multi-primary: Multiple database servers can accept writes. This can support some distributed-write use cases, but conflicting changes, consistency, and failover become more complicated.

Multi-primary replication is not simply a faster version of primary-replica replication. It requires a deliberate strategy for handling conflicting writes and maintaining correctness.

4. What Are Read Replicas?

A read replica is a database server that receives replicated data from the primary and is used primarily to serve read queries.

Instead of sending every query to one database, an application can send writes to the primary and direct suitable reads to replicas. 

                         ┌──────────────────┐
                         │    Application   │
                         └────────┬─────────┘
                                  │
                     ┌────────────┴────────────┐
                     │                         │
                  Writes                     Reads
                     │                         │
                     ▼                         ▼
              ┌─────────────┐         ┌────────────────┐
              │   Primary   │────────►│  Read Replica  │
              │ Read/Write  │ Replicate│  Read only     │
              └─────────────┘         └────────────────┘
                                              │
                                              ▼
                                       ┌────────────────┐
                                       │  Read Replica  │
                                       │  Read only     │
                                       └────────────────┘

A read replica is not just a backup. It is an additional database instance that can actively serve application queries.

Read replicas are often configured to reject direct writes, although the exact restrictions depend on the database and setup.

5. Why Use Read Replicas?

Better read performance

The primary no longer needs to execute every read query. Replicas can handle queries such as loading product listings, retrieving user profiles, or displaying reporting dashboards.

Horizontal read scalability

You can add more replicas to distribute read traffic. This can help when an application has many more reads than writes.

However, adding replicas does not automatically make every query faster. Queries still depend on indexes, query plans, available CPU, memory, storage, and the replication workload.

Isolation of workloads

You can send analytical or reporting queries to a dedicated replica instead of letting expensive reads compete with latency-sensitive transactions on the primary.

Geographic distribution

Replicas in different regions can serve nearby users, potentially reducing read latency. Cross-region replication introduces additional network latency and may increase replication lag.

6. How Does an Application Use Read Replicas?

The application needs a way to choose which database connection should execute each query.

For example, imagine an application with two connections:

PRIMARY_DATABASE_URL=postgres://primary.example/app
READ_DATABASE_URL=postgres://replica.example/app

The application can use the primary for writes and consistency-sensitive reads, and the replica for reads where slightly stale data is acceptable.

Conceptually:

// Write to the primary
order = primaryDatabase.insertOrder(orderData);

// Read from a replica
products = readDatabase.getProducts();

// Read the newly created order from the primary
// when an up-to-date result is required
order = primaryDatabase.getOrder(order.id);

This is illustrative pseudocode, not a specific ORM API. In a real application, the database driver, framework, or repository layer determines how connections are configured and selected.

Many frameworks support read/write connection splitting. Still, routing every SELECT to a replica is not always correct. The application must account for queries that need to observe recent writes.

7. What Is Replication Lag?

Replication lag is the delay between a change being committed on the primary and that change becoming available on a replica.

Consider this sequence:

1. A user updates their profile.
2. The primary saves the new name: "Alex".
3. The application returns success.
4. The user refreshes the profile.
5. The read replica still contains the old name: "Alice".

The user may see the old name even though the update succeeded. This is a common example of eventual consistency.

How can you handle replication lag?

  • Read your writes from the primary: After a user changes data, send related reads to the primary for a short period or until the change is known to be replicated.
  • Monitor replication lag: Track replication delay and alert when it exceeds acceptable limits.
  • Use a consistency-aware routing policy: Route reads according to their freshness requirements, rather than sending every read to a replica.
  • Define a fallback: If a replica is too far behind or unavailable, consider routing eligible reads to the primary.

Sending a query to the primary avoids replica lag for that read, but it does not solve every consistency issue in a distributed application.

8. When Should You Use Read Replicas?

Read replicas can be useful when:

  • Your application handles significantly more reads than writes.
  • The primary is approaching its read-processing capacity.
  • Reporting queries are competing with important transactional workloads.
  • You need to serve read traffic from multiple regions.
  • Your application can tolerate some reads being slightly stale.

When might they not be worth it?

  • Your database is small and performs well on a single instance.
  • Most of your workload consists of writes, so read replicas will not address the main bottleneck.
  • Nearly every read must immediately observe the latest write, and you cannot implement suitable routing.
  • Your team cannot yet support the extra monitoring, connection management, and operational complexity.

Before adding replicas, measure the workload and identify the bottleneck. Slow queries, missing indexes, inefficient joins, and excessive database round trips may be better first targets.

9. Replication Is Not the Same as Sharding

Replication and sharding solve different scaling problems.

  • Replication: Copies the same data to multiple database servers.
  • Sharding: Splits data across multiple database servers, with each shard holding only part of the dataset.

For example:

Replication:

Primary:   Users A, B, C, D
Replica:   Users A, B, C, D


Sharding:

Shard 1:   Users A, B
Shard 2:   Users C, D

Replication is often used to scale reads and improve availability. Sharding can distribute both storage and workload when a single database cannot handle the full dataset or throughput.

They can also be combined: each shard can have its own replicas.

10. Replication and High Availability

Replicas can help a system recover from a primary failure, but replication alone does not guarantee high availability.

A production setup may need to detect failures, select a suitable replica, promote it to primary, redirect application connections, and prevent the old primary from accepting conflicting writes.

This process is called failover. It may be managed by a database service, orchestration system, or dedicated database tooling.

With asynchronous replication, a replica may not have received every acknowledged write before the primary fails. Promoting it can therefore result in data loss. Synchronous replication can reduce some risks, but its guarantees depend on configuration and failure scenarios.

Replication is also not a replacement for backups. Accidental deletions or corrupted data may be replicated to every copy. Backups and recovery testing are still essential.

11. Real-World Example: An E-commerce Application

Imagine an online store with the following workloads:

  • Customers browse product listings thousands of times per minute.
  • Customers place orders and update their accounts.
  • Employees generate reports about sales and inventory.

A possible architecture is:

Product listing reads ──────► Read Replica 1

Reporting queries ──────────► Read Replica 2

Order creation ─────────────► Primary Database

Payment state changes ──────► Primary Database

Consistency-sensitive reads ► Primary Database

The replicas absorb eligible read traffic, while the primary handles writes and reads that need the latest committed data.

This architecture still needs careful transaction design. For example, inventory checks and order creation must protect against overselling; reading a stale inventory value from a replica is not sufficient to guarantee correct stock management.

12. Things to Keep in Mind

  • Replication lag: A replica may not immediately reflect a committed change.
  • Connection routing: Applications need to send queries to the appropriate database.
  • Failover: Promoting a replica requires a defined recovery procedure.
  • Monitoring: Monitor lag, replica availability, query latency, and resource usage.
  • Cost: Additional replicas require compute, storage, and operational resources.
  • Backups: Maintain independent backups and test restoration.

13. Summary

Database replication copies data between database servers. Read replicas use those copies to serve eligible read queries, helping applications scale read workloads and isolate expensive queries from the primary.

The key concepts to remember are:

  • Replication keeps multiple database instances synchronized to some degree.
  • Synchronous replication can provide stronger replication guarantees at the cost of latency or availability trade-offs.
  • Asynchronous replication usually improves write responsiveness but can introduce lag and potential data loss during some failures.
  • Read replicas distribute read traffic but do not automatically improve write capacity.
  • Replication lag means an application must think carefully about which reads need the latest data.
  • Replication is not a backup and does not eliminate the need for recovery planning.

The goal is not to add more database servers just because an application is growing. It is to identify the actual bottleneck and choose the simplest architecture that meets the application's performance, consistency, and availability requirements.
