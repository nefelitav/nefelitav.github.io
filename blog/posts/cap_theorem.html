CAP Theorem

7 October 2026

The CAP theorem describes a fundamental trade-off in distributed systems: when a network partition occurs, a system cannot guarantee both strong consistency and availability at the same time.

CAP stands for Consistency, Availability and Partition Tolerance.

1. What is CAP?

A distributed system often has multiple servers or nodes that communicate with each other and may contain copies of the same data. 

        Network
┌───────────────┐
│               │
Server A  <------>  Server B
X = 10              X = 10

CAP describes what happens when these servers can no longer communicate.

The important point is that the theorem is specifically about what happens during a network partition.

2. The Three Properties

Consistency

Consistency means that every read receives the most recent successful write, or an error.

After writing X = 20, a read should not return the old value X = 10. 

WRITE X = 20
Server A
X = 20

READ X → 20

Availability

Availability means that every request to a non-failing node receives a response, even if that response may not contain the latest data.

The system continues serving requests instead of refusing them because another node is unreachable.

Partition Tolerance

Partition tolerance means that the system can continue operating despite a network failure that prevents some nodes from communicating with each other.

A network partition does not necessarily mean that a server has crashed. The servers may still be running, but they cannot communicate. 

Server A       ❌       Server B

🟢          Network      🟢
            partition

Both servers are running,
but they cannot communicate.

3. A Practical Example

Imagine an application with two database replicas: 

Server A                 Server B

X = 10                   X = 10

        <---------->
      network

A user updates the value: 

WRITE X = 20

Server A now has: 

Server A                 Server B

X = 20                   X = 10

Normally, Server A would communicate the change to Server B. But now the network connection between them fails. 

Server A       ❌       Server B

X = 20                  X = 10

This is a network partition.

Now a user sends: 

GET X

to Server B.

Server B has an important decision to make.

4. Consistency vs Availability

Choose Consistency

Server B could refuse to return the value because it cannot guarantee that its data is up to date. 

GET X

→ Error / wait

"I cannot guarantee that my data is current."

This preserves consistency, but the system is sacrificing availability.

Choose Availability

Alternatively, Server B could return the value it currently has: 

GET X

→ 10

The request was successfully served, so the system remains available.

However, the value is stale because another server already has X = 20. Strong consistency has been sacrificed.

5. The CAP Trade-off

When a network partition occurs, the system has to choose between maintaining strong consistency and maintaining availability. 

             Network Partition
                │
         ┌──────┴──────┐
         │             │
   Consistency    Availability
         │             │
    reject/wait      respond
    requests         with data

This is the core idea behind the CAP theorem:

During a network partition, you cannot guarantee both strong consistency and availability.

6. Why Partition Tolerance Matters

In a distributed system, network failures are unavoidable. Servers can lose connectivity because of hardware failures, network problems, configuration errors, overloaded components or failures between data centers.

Therefore, partition tolerance is generally something distributed systems need to handle rather than something they can simply choose to ignore.

This means the practical trade-off is often described as: 

        P
        │
   ┌────┴────┐
   │         │
   C         A
   │         │
Consistency  Availability

A system can be designed to prioritize either consistency or availability when communication between nodes is lost.

7. Strong vs Eventual Consistency

Systems that prioritize availability may allow replicas to temporarily contain different values. 

Immediately after a write:

Server A → X = 20
Server B → X = 10

Later, after synchronization:

Server A → X = 20
Server B → X = 20

This is an example of eventual consistency. The system may temporarily return stale data, but replicas eventually converge on the same value.

Eventual consistency is common in systems where remaining available is more important than immediately having identical data everywhere.

Final Thought

The easiest way to remember CAP is: when distributed nodes cannot communicate, you have to decide whether to keep serving requests or guarantee that the data is consistent.

In other words: Partition → Consistency or Availability.
