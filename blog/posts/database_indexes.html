Database Indexes

8 October 2026

Database indexes are one of the most important tools for improving query performance.

They allow a database to find rows efficiently without scanning the entire table. But indexes are not free: they consume storage and make writes more expensive.

A useful principle is: index the access patterns your application actually needs, not every column that appears in a table.

1. What Is an Index?

Imagine a table containing millions of users: 

users


| id               | name  | email                                         |
| ---------------- | ----- | --------------------------------------------- |
| 1                | Alice | [alice@example.com](mailto:alice@example.com) |
| 2                | Bob   | [bob@example.com](mailto:bob@example.com)     |
| 3                | Carol | [carol@example.com](mailto:carol@example.com) |
...

Without an index, a query such as: 

SELECT *
FROM users
WHERE email = '[alice@example.com](mailto:alice@example.com)';

may require the database to inspect many or even all rows. This is called a table scan.

An index on email gives the database a separate data structure that can be searched efficiently. 

CREATE INDEX idx_users_email ON users(email);

Instead of searching every row, the database can use the index to locate the relevant row much faster.

2. Without an Index vs With an Index

Conceptually, searching a table without an index looks like: 

Row 1 → Does email match?
Row 2 → Does email match?
Row 3 → Does email match?
Row 4 → Does email match?
...
Row 1,000,000 → Does email match?

An index provides a structure that allows the database to navigate towards the matching value instead. 

             email
           │
    ┌──────┴──────┐
    │             │


a... - m...     n... - z...
│
[alice@example.com](mailto:alice@example.com)
│
row

The exact implementation depends on the database and index type, but the key idea is the same: avoid examining unnecessary rows.

3. B-Tree Indexes

One of the most common index structures is the B-tree.

B-trees keep values ordered and balanced, allowing the database to efficiently perform operations such as:

  • Equality lookups
  • Range queries
  • Sorting
  • Prefix searches
WHERE id = 123

WHERE created_at >= '2026-01-01'

WHERE price BETWEEN 10 AND 100

ORDER BY created_at

The database can navigate through the tree rather than scanning every row.

4. Primary Keys and Indexes

A primary key is normally indexed automatically. 

CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  email VARCHAR(255)
);

This allows queries such as: 

SELECT *
FROM users
WHERE id = 123;

to efficiently locate a specific row.

Primary keys are also important because many databases use the primary key as part of the physical organization of the table or as information stored in secondary indexes.

5. Indexing Foreign Keys

Foreign keys are often good candidates for indexes. 

orders


| id | customer_id      |
| -- | ---------------- |
| 1  | 100              |
| 2  | 200              |
| 3  | 100              |
| 4  | 300              |

If the application frequently executes: 

SELECT *
FROM orders
WHERE customer_id = 100;

an index can make the lookup much more efficient. 

CREATE INDEX idx_orders_customer_id ON orders(customer_id);

6. Selectivity

An important concept when designing indexes is selectivity.

A highly selective column has many distinct values and therefore allows the database to narrow down the result significantly.

For example, suppose a table has one million users.

An id column might have one million distinct values, while a country column might only have 100. 

id       → very selective

email    → very selective

country  → less selective

gender   → usually much less selective

This does not mean low-cardinality columns should never be indexed. It means that the usefulness of an index depends on the query, data distribution and database optimizer.

7. Composite Indexes

Sometimes a query filters by multiple columns: 

SELECT *
FROM orders
WHERE customer_id = 123
AND status = 'pending';

Instead of creating two separate indexes, we can create a composite index: 

CREATE INDEX idx_orders_customer_status ON orders(customer_id, status);

The order of columns matters.

Conceptually, this index is ordered like: 

customer_id
↓
status
↓
indexed rows

The database can efficiently search for a specific customer_id and then narrow the results by status.

8. The Leftmost Prefix Rule

Consider: 

CREATE INDEX idx_orders_customer_status_date ON orders(customer_id, status, created_at);

The index is ordered first by customer_id, then by status, then by created_at.

Queries using the leftmost columns can generally benefit from the index: 

WHERE customer_id = 123
WHERE customer_id = 123
AND status = 'pending'

WHERE customer_id = 123
AND status = 'pending'
AND created_at >= '2026-01-01'

But a query filtering only by the later columns may not be able to use the index as effectively: 

WHERE status = 'pending'
WHERE created_at >= '2026-01-01'

This is commonly described as the leftmost prefix rule.

9. Column Order Matters

Compare these two indexes: 

INDEX(customer_id, status)
INDEX(status, customer_id)

They are not equivalent.

If the application's most common access pattern is: 

WHERE customer_id = ?
AND status = ?

both indexes may be useful for that query. But their behavior for queries using only one of the columns can be very different.

Composite indexes should therefore be designed around the application's actual query patterns.

10. Indexes and ORDER BY

Indexes can also help with sorting. 

SELECT *
FROM orders
WHERE customer_id = 123
ORDER BY created_at DESC;

An index such as: 

CREATE INDEX idx_orders_customer_created ON orders(customer_id, created_at);

may allow the database to retrieve the relevant rows in the required order without performing an additional expensive sort.

11. Indexes and Range Queries

B-tree indexes are particularly useful for range queries. 

SELECT *
FROM orders
WHERE created_at >= '2026-10-01'
AND created_at < '2026-11-01';

Instead of scanning the entire table, the database can locate the relevant portion of the index and scan that range.

This is one reason columns such as timestamps are common candidates for indexing.

12. Covering Indexes

Sometimes an index contains everything the database needs to answer a query. 

CREATE INDEX idx_users_email_name ON users(email, name);

Consider: 

SELECT name
FROM users
WHERE email = '[alice@example.com](mailto:alice@example.com)';

The database may be able to find both email and name directly in the index without reading the corresponding table row.

This is commonly called a covering index.

Covering indexes can improve performance, but adding many columns to an index also increases its size and write cost.

13. Indexes Are Not Free

An index makes reads faster, but it introduces costs.

  • Indexes consume disk space.
  • INSERT operations must update indexes.
  • UPDATE operations may need to update indexes.
  • DELETE operations must remove index entries.
  • Indexes increase memory and cache pressure.
  • Too many indexes can make write-heavy systems slower.

For example: 

INSERT row
     ↓
┌────┴────┐
↓    ↓    ↓
index1 index2 index3
↓    ↓    ↓
update update update

Every additional index potentially adds work to writes.

14. Don't Index Everything

It can be tempting to add an index to every column used in a WHERE clause.

This is usually a mistake.

A better approach is to start from actual queries: 

1. Identify slow queries.

2. Inspect their execution plans.

3. Understand the access pattern.

4. Design an appropriate index.

5. Measure the improvement.

6. Remove indexes that provide little value.

Indexes should support real workloads rather than theoretical possibilities.

15. EXPLAIN

Databases provide tools for understanding how a query will be executed.

In MySQL, one of the most important tools is EXPLAIN. 

EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 123;

The query plan can show information such as:

  • Which table is being accessed
  • Which indexes are available
  • Which index is being considered or used
  • How many rows may be examined
  • How the tables are joined
  • Whether an additional sort is required

An index existing on a table does not guarantee that the optimizer will use it.

16. The Optimizer Can Ignore an Index

The database optimizer chooses what it believes is the cheapest execution plan.

Sometimes that means not using an available index.

For example, if a query returns a very large percentage of a table, scanning the table may be cheaper than using an index and then fetching a large number of rows. 

SELECT *
FROM users
WHERE country = 'US';

If most users are from the US, an index on country might not provide much benefit.

An index is a tool, not a guarantee.

17. Functions Can Prevent Efficient Index Usage

Be careful when applying functions to indexed columns.

For example: 

SELECT *
FROM users
WHERE LOWER(email) = '[alice@example.com](mailto:alice@example.com)';

Depending on the database and index configuration, this may prevent the normal index on email from being used efficiently.

Often it is better to store or index data in the form needed for the lookup, or use a database-supported functional index where appropriate.

18. Avoid Wrapping Indexed Columns When Possible

Another common example is applying a function to a timestamp: 

WHERE DATE(created_at) = '2026-10-08'

A range condition can often be more index-friendly: 

WHERE created_at >= '2026-10-08 00:00:00'
AND created_at <  '2026-10-09 00:00:00'

This allows the database to search a range of the indexed timestamp values directly.

19. Indexes and NULL

Index behavior around NULL values depends on the database system and index type.

Queries such as: 

WHERE deleted_at IS NULL

may be able to benefit from an index on deleted_at, but the usefulness depends on the database, data distribution and query plan.

Always verify with the database's execution plan rather than assuming an index will be used.

20. Unique Indexes

A unique index both supports efficient lookup and enforces uniqueness. 

CREATE UNIQUE INDEX idx_users_email ON users(email);

This prevents two rows from having the same email address while also providing an index for lookups.

A UNIQUE constraint is often preferable when the business rule is that a value must be unique, because it expresses the constraint explicitly.

21. Indexes and Constraints

Indexes and constraints solve different problems.

  • Index — helps the database find data efficiently.
  • UNIQUE constraint — enforces uniqueness.
  • PRIMARY KEY — uniquely identifies a row.
  • FOREIGN KEY — enforces relationships between tables.

Some constraints are implemented using indexes internally, but their purpose is still different.

22. Index Size Matters

The size of an index depends on factors such as:

  • Number of rows
  • Indexed column size
  • Number of columns in a composite index
  • Data distribution
  • Database implementation

Indexing a large text column can therefore be considerably more expensive than indexing a small integer.

In general: smaller indexes are cheaper to maintain and easier to keep in memory.

23. Duplicate and Redundant Indexes

Over time, a table can accumulate indexes that overlap. 

INDEX(customer_id)
INDEX(customer_id, status)

The second index already starts with customer_id, so the first index may be redundant for many workloads.

However, whether an index is truly redundant depends on the database and the exact workload.

Before removing an index, verify which queries depend on it.

24. Indexing a Query Pattern

Instead of thinking: 

"Which columns should I index?"

think: 

"How does my application access this data?"

For example, suppose the application frequently runs: 

SELECT *
FROM payments
WHERE merchant_id = ?
AND status = ?
ORDER BY created_at DESC
LIMIT 50;

A possible index could be: 

CREATE INDEX idx_payments_merchant_status_created ON payments(merchant_id, status, created_at);

The index is designed around the complete access pattern: filtering by merchant, filtering by status, and then ordering by creation time.

The best index is often the one designed around the query, rather than around an individual column.

25. Indexes and Joins

Indexes are also important when joining tables. 

SELECT orders.*
FROM orders
JOIN customers
ON orders.customer_id = customers.id
WHERE customers.id = 123;

An index on the columns used to locate and join rows can significantly reduce the amount of data the database needs to examine.

Primary keys are commonly indexed automatically, while foreign key columns are often good candidates for explicit indexes.

26. Indexes and Write-Heavy Systems

Index design is especially important for write-heavy workloads.

Imagine a table receiving thousands of inserts per second. Every additional index may need to be updated for every insert. 

INSERT
│
├── update primary key index
├── update customer index
├── update status index
├── update timestamp index
└── update another composite index

An index that saves a few milliseconds on an occasional query may not be worth the cost if it significantly increases the cost of millions of writes.

27. The Trade-off

Database indexing is fundamentally a trade-off: 

More indexes
 ↓
Faster reads
+
More storage
+
More expensive writes
+
More maintenance

Conversely: 

Fewer indexes
 ↓
Cheaper writes
+
Less storage
-
Potentially slower reads

Good database design finds the appropriate balance for the application's workload.

28. A Practical Indexing Process

A useful process for adding an index is:

  1. Identify a slow or frequently executed query.
  2. Inspect the current execution plan.
  3. Understand which rows the query filters, sorts or joins.
  4. Design an index around that access pattern.
  5. Check the new execution plan.
  6. Benchmark the query.
  7. Measure the impact on writes and storage.
  8. Monitor the index in production.

Do not stop at: 

"The index exists."

The important question is: 

"Did the index actually improve the workload?"

29. Common Indexing Mistakes

  • Adding indexes to every column
  • Ignoring composite index column order
  • Creating duplicate or redundant indexes
  • Ignoring write performance
  • Ignoring index storage requirements
  • Assuming an index will always be used
  • Not checking the execution plan
  • Indexing without understanding the query workload
  • Adding very large indexes unnecessarily
  • Keeping unused indexes forever

Indexing Checklist

  • Is this query actually slow or frequently executed?
  • What does the current execution plan look like?
  • Which columns are used for filtering?
  • Which columns are used for joins?
  • Which columns are used for sorting?
  • Should this be a composite index?
  • Is the column order appropriate?
  • Is the index selective enough for the workload?
  • Could the index cover the query?
  • What will the index cost in storage?
  • How will it affect INSERT, UPDATE and DELETE performance?
  • Is there already a redundant index?
  • Did the execution plan actually improve?

Final Thought

An index is essentially a trade: pay extra storage and write overhead to make certain reads significantly cheaper.

Good indexing is therefore not about having as many indexes as possible. It is about understanding how the application accesses its data and building indexes around those access patterns.

The most useful mindset is: measure the query, understand the execution plan, design the index, and measure again.
