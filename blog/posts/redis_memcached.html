Redis vs Memcached

15 October 2026

Redis and Memcached are both in-memory key-value stores commonly used to cache data. Instead of repeatedly querying a database or calling an external API, an application can store frequently needed results in memory and retrieve them much faster.

The main difference is that Memcached focuses on simple, ephemeral caching, while Redis provides a richer set of data structures and additional capabilities such as persistence, atomic operations, and messaging.

1. What Is Caching?

Imagine that your API repeatedly executes an expensive database query to retrieve a merchant's configuration.

Without caching, every request might follow this path:

Client Request
      |
      v
Application Server
      |
      v
Database Query
      |
      v
Return Result

With caching, the application first checks whether the result is already stored in memory.

Client Request
      |
      v
Application Server
      |
      v
   Cache Lookup
      |
      +---- Cache HIT ----> Return Cached Result
      |
      +---- Cache MISS ---> Query Database
                                  |
                                  v
                            Store in Cache
                                  |
                                  v
                            Return Result

A cache hit occurs when the requested data is available in the cache. A cache miss occurs when the application must retrieve the data from its original source.

Caching can reduce database load and latency, but it introduces new challenges: expiration, stale data, invalidation, memory limits, and consistency.

2. Redis

Redis is an in-memory data structure store that can be used as a cache, database, message broker, or streaming data store. It supports several data types and operations beyond simple key-value retrieval.

Supported data structures

  • Strings: simple values, counters, and serialized objects.
  • Hashes: field-value collections, useful for representing objects.
  • Lists: ordered collections that can support queue-like patterns.
  • Sets: collections of unique values.
  • Sorted Sets: unique members ordered by score, useful for leaderboards.
  • Streams: append-oriented records useful for event and message-processing patterns.

Example: storing a cached value

SET merchant:123:config '{"currency":"EUR"}' EX 300

GET merchant:123:config

The EX 300 option gives the key a time-to-live (TTL) of 300 seconds. After expiration, the application must retrieve the value again if it is needed.

Example: atomic counter

INCR api:merchant:123:requests

Redis increments the integer atomically. This is useful for counters and can form part of a rate-limiting implementation.

When would you use Redis?

  • Application and database query caching.
  • Session storage across multiple application instances.
  • Rate limiting and counters.
  • Leaderboards using sorted sets.
  • Distributed coordination using carefully designed atomic operations and locking patterns.
  • Lightweight queues, streams, and messaging patterns.
  • Use cases that need configurable persistence or replication.

3. Memcached

Memcached is a distributed in-memory caching system designed to store arbitrary values associated with keys. It focuses on keeping the caching layer simple and efficient.

Unlike Redis, Memcached does not provide rich server-side data structures. Your application typically serializes an object into a value, stores it, and retrieves it later.

Example: storing a cached value

set merchant:123:config 300 0 25
{"currency":"EUR"}

This is an example of the Memcached text protocol. The parameters specify the key, expiration time, flags, and value length in bytes. In a real application, you would normally use a client library instead of manually sending protocol commands.

To retrieve the value:

get merchant:123:config

How does Memcached distribute data?

Applications commonly connect to a pool of Memcached servers. The client uses a key-based hashing strategy to choose which server holds a particular entry.

Application
     |
     v
Client-side Hashing
     |
     +----------+----------+
     |          |          |
     v          v          v
 Memcached  Memcached  Memcached
 Server A   Server B   Server C

Adding or removing servers can change the mapping of keys to servers. Consistent hashing can reduce how many keys need to be remapped.

When would you use Memcached?

  • Caching rendered pages or HTML fragments.
  • Caching database query results.
  • Caching serialized API responses.
  • Reducing repeated calls to expensive services.
  • Simple caching workloads where values can be discarded and recomputed.

Memcached is especially suitable when the application needs a fast, disposable cache without requiring richer server-side functionality.

4. Redis vs Memcached: Comparison

Feature Redis Memcached
Primary purpose In-memory data store and cache In-memory cache
Data model Strings, hashes, lists, sets, sorted sets, streams, and more Keys mapped to opaque values
Expiration Supported per key Supported per item
Atomic operations Rich operations on supported data structures Basic operations and numeric increment/decrement
Persistence Optional RDB snapshots and AOF logging Generally ephemeral; limited warm-restart options exist
Replication Supported No built-in replication mechanism
Built-in clustering Redis Cluster supports sharding and replication Typically distributed through client-side hashing across servers
Messaging Pub/Sub and Streams No native messaging system
Memory efficiency Depends on data structures and configuration Often efficient for simple key-value caching
Operational complexity More features and configuration options Relatively simple for basic caching

Neither technology is automatically faster in every workload. Actual performance depends on the data size, request patterns, serialization, network latency, concurrency, configuration, and hardware.

5. Common Use Cases: Which One Should You Choose?

Scenario A: Caching database query results

Either can work.

Suppose your application frequently retrieves a list of product categories. The database query is expensive, but the results change only occasionally.

Cache key: categories:all
Cache value: serialized category list
TTL: 300 seconds

Memcached is a good fit if you only need to store and retrieve the serialized result. Redis is equally suitable and may be preferable if you already operate Redis for other workloads.

Scenario B: Rate limiting an API

Redis is usually the more natural choice.

You want to allow each merchant a maximum number of requests within a time window.

INCR rate-limit:merchant:123
EXPIRE rate-limit:merchant:123 60

This illustrates the basic idea, but these two commands alone are not a fully robust rate limiter: concurrent requests and the creation of the expiration need to be handled safely. A Lua script or another atomic design can combine the relevant operations.

Redis is useful because it provides atomic counters, expiration, and scripting. Memcached also supports atomic increments, but implementing more sophisticated limiting logic is less convenient.

Scenario C: Storing user sessions

Redis is often preferred, but both can store sessions.

In a horizontally scaled application, any application instance should be able to retrieve a user's session.

session:abc123 -> serialized session data
TTL: 1800 seconds

Redis can provide session storage with expiration and optional persistence or replication. Memcached is also suitable when sessions can safely be discarded and recreated or when session loss is acceptable.

In either case, session expiration, security, eviction, and failure behavior must be considered.

Scenario D: Building a leaderboard

Redis.

Sorted sets maintain members associated with scores, making them useful for ranking players, sellers, or other entities.

ZADD leaderboard 1500 player:123
ZADD leaderboard 1800 player:456

ZREVRANGE leaderboard 0 9 WITHSCORES

These commands add scores and retrieve the top ten members in descending score order.

Memcached would require your application to implement the ranking logic and manage the relevant data itself.

Scenario E: Caching an external API response

Either can work.

If an external API is expensive or rate-limited, cache the response to avoid repeated network requests.

Key: exchange-rates:EUR
TTL: 60 seconds

Choose based on the complexity of the cached data, your existing infrastructure, and your operational requirements rather than assuming one product is always faster.

Scenario F: A lightweight event-processing workflow

Redis may be suitable.

Redis Streams provide an append-oriented data structure with consumer groups that can support lightweight event-processing workloads.

However, if your requirements involve extensive routing, complex acknowledgements, durable message retention, or large-scale event streaming, compare Redis with purpose-built messaging systems such as RabbitMQ and Kafka.

6. Redis Persistence vs Memcached's Ephemeral Storage

One of the most important differences is what happens when the cache process or machine restarts.

Redis persistence

Redis supports multiple persistence configurations:

  • RDB: periodically saves snapshots of the dataset.
  • AOF: records write operations so the dataset can be reconstructed during recovery.
  • Both: combines snapshots and operation logging.
  • None: disables persistence, which is common for disposable caching workloads.

Persistence settings involve trade-offs between performance, recovery time, disk usage, and the amount of data that could be lost after a failure.

Memcached storage

Memcached is designed for ephemeral data. A restart or failure can result in cached values being lost, and the application should be able to repopulate them from the original source.

For this reason, neither cache should be treated as a durable source of truth merely because it is fast. If Redis is used as a primary data store, its durability and recovery configuration must explicitly match the application's requirements.

7. Cache Eviction and TTL

Memory is limited. When a cache reaches its configured memory limit, it needs a strategy for deciding what to remove.

TTL (Time to Live)

A TTL determines how long an entry remains valid before it expires.

SET product:123 '{"price":49.99}' EX 300

This stores the value with a five-minute expiration. TTLs are useful for data that becomes stale over time, but they do not guarantee immediate consistency with the database.

Eviction policies

  • LRU: approximates least recently used, favoring the removal of entries that have not been accessed recently.
  • LFU: approximates least frequently used, favoring the removal of entries accessed less frequently.
  • TTL-based policies: can favor removing keys with expiration times, depending on the configured policy.
  • No eviction: a store may reject new writes when its configured memory limit is reached.

Redis supports several configurable eviction policies. Memcached also uses an LRU-oriented eviction mechanism, with behavior affected by its slab allocator and configuration.

Do not confuse expiration with eviction: expiration is based on a key's lifetime, while eviction removes entries to manage resource limits.

8. Cache Invalidation: The Hard Part

A cache can return stale data when the original record changes but the cached copy remains available.

Suppose the price of a product changes in your database. Your application must decide how to update or invalidate the cached value.

Option 1: TTL-based expiration

Set a short expiration time and accept that cached data may remain stale until the entry expires.

Option 2: Explicit invalidation

After updating the database, delete the corresponding cache entry.

DEL product:123

The next request will fetch the updated value from the database and repopulate the cache.

Option 3: Update the cache

Update the database and cache as part of a deliberate cache-write strategy. This can reduce cache misses but requires careful handling of failures and ordering.

For important data, a database transaction and cache update are not automatically atomic together. Cache invalidation strategies must account for concurrent writes, retries, and stale values being repopulated.

9. Is Redis Always Better?

No. Redis offers more capabilities, but additional functionality does not automatically make it the best option for every cache.

Choose Redis when:

  • You need data structures beyond simple key-value pairs.
  • You need atomic counters, scripting, or more sophisticated operations.
  • You need optional persistence, replication, or Redis Cluster.
  • You want caching and additional data-processing capabilities in one technology.
  • Your organization already operates Redis and can reuse that infrastructure.

Choose Memcached when:

  • You need a straightforward cache for serialized values.
  • Cached entries can be safely discarded and recomputed.
  • You value its simple operational model for your workload.
  • Your application already uses Memcached successfully.

For basic caching, the simpler solution can be the better engineering decision. Migrating from one cache to another is not automatically worthwhile without a measurable need.

10. Common Misconceptions

  • "Redis is always faster." Performance depends on the workload, data structures, client behavior, and configuration.
  • "Memcached cannot expire values." Memcached supports expiration times on individual items.
  • "Redis data always survives restarts." Persistence is configurable and must be enabled and configured appropriately.
  • "A cache is a database replacement." Caches usually reduce the work performed by a primary data source. Redis can serve as a primary store in some architectures, but that requires explicit data-model and durability decisions.
  • "Caching always improves performance." Cache lookups have costs, and maintaining cached data introduces complexity. Measure before adding a cache.
  • "Cache invalidation is solved by setting a TTL." TTLs bound the intended lifetime of entries but do not guarantee immediate consistency.
  • "Redis is a replacement for every message broker." Redis provides messaging and stream capabilities, but specialized brokers may better fit particular delivery and routing requirements.

11. What Should I Remember?

  • Both: in-memory key-value stores that can reduce latency and database load.
  • Redis: a versatile data structure store with atomic operations, optional persistence, replication, and messaging capabilities.
  • Memcached: a simple, distributed cache for ephemeral key-value data.
  • Choose Redis: when the workload benefits from richer functionality or its additional operational capabilities.
  • Choose Memcached: when simple caching is sufficient and its characteristics fit your workload.
  • Always consider: cache invalidation, TTLs, memory limits, eviction, failure behavior, and consistency.

The goal is not to use the most feature-rich technology. It is to choose the simplest caching solution that satisfies your application's performance and reliability requirements.
