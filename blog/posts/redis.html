Redis Use Cases Explained

15 October 2026

Redis is an in-memory data store commonly used to make backend applications faster and to coordinate work across multiple application instances.

Unlike a traditional relational database, Redis keeps its working data primarily in memory and provides operations for data structures such as strings, hashes, lists, sets and sorted sets.

Redis is much more than a cache. It can also be used for session storage, rate limiting, counters, distributed coordination, queues and real-time features.

The important question is not just "Can Redis store this data?" but "Is Redis the right place to store and manage this data?"

The Big Picture

  • Caching — avoid repeatedly calculating or fetching the same data.
  • Session storage — share user sessions across application instances.
  • Rate limiting — restrict how frequently clients can perform operations.
  • Counters — atomically increment values such as request counts or view counts.
  • Distributed locks — coordinate work between multiple processes.
  • Queues and messaging — support certain asynchronous processing patterns.
  • Real-time data — maintain leaderboards, rankings and rapidly changing state.
  • Temporary data — store verification codes, temporary tokens and short-lived application state.

How Redis Fits Into a Backend Application

Imagine a typical backend application with several application instances and a relational database. 

              Client
                |
                v
          Load Balancer
                |
          +-----+-----+
          |           |
          v           v
       App A         App B
          |           |
          +-----+-----+
                |
          +-----+-----+
          |           |

        Redis      Database
       (cache,     (durable
       sessions,    records)

Redis can reduce database load, provide shared temporary state and support fast operations. The relational database remains responsible for durable business records in many architectures.

Both application instances can access the same Redis deployment. This is important because data stored only in one application's local memory is not automatically visible to another instance.

1. Caching

Caching is one of the most common Redis use cases. Instead of querying a database or calling an external API every time, an application can temporarily store the result in Redis.

Without caching

Client Request
      |
      v
Application
      |
      v
Database Query
      |
      v
Return Result

With caching

Client Request
      |
      v
Application
      |
      v
Check Redis
      |
      +---- Cache hit ----> Return cached result
      |
      +---- Cache miss
                 |
                 v
              Database
                 |
                 v
           Store in Redis
                 |
                 v
            Return result

A cache hit means the requested data already exists in Redis. A cache miss means the application must retrieve or calculate the data another way.

Example: Caching a merchant

Suppose your application frequently loads merchant configuration from a database. 

// Simplified PHP example using a Redis client.

$key = 'merchant:123';

$merchant = $redis->get($key);

if ($merchant === false) {
    $merchant = $database->findMerchant(123);

    if ($merchant !== null) {
        $redis->setex(
            $key,
            300,
            json_encode($merchant)
        );
    }
} else {
    $merchant = json_decode($merchant, true);
}

The example uses a five-minute TTL (time to live). The cached value expires after 300 seconds.

This is illustrative code: actual Redis clients differ in their return values, method names and serialization behavior. Production code should handle database failures, serialization errors and cache failures explicitly.

What should you cache?

  • Frequently requested configuration.
  • Product or merchant information.
  • Expensive database query results.
  • Computed reports or aggregates.
  • Responses from external APIs.

Cache-aside pattern

Cache-aside is a common caching strategy. The application checks Redis first, loads missing data from the database and then populates the cache. 

function getMerchant(id) {
    cached = redis.get("merchant:" + id)

    if cached exists:
        return cached

    merchant = database.findMerchant(id)

    if merchant exists:
        redis.set("merchant:" + id, merchant, TTL)

    return merchant
}

When the merchant changes, the application must consider how to invalidate or update the cached value. 

Update merchant in database
             |
             v
Delete merchant:123 from Redis
             |
             v
Next request reloads fresh data

Invalidating the cache after a successful database update is a common approach. It is not a perfect guarantee of consistency: concurrent requests, failed invalidations and replication delays can still create stale reads.

When should you use Redis caching?

  • Many requests read the same data.
  • Database queries are expensive.
  • The data can tolerate some staleness.
  • Recomputing or retrieving the data is possible after eviction.

Avoid caching everything by default. Redis introduces another system to operate, and cache invalidation can be more complicated than the original query.

2. Session Storage

Sessions allow an application to remember information associated with a user across multiple requests.

For example, a session may contain a user identifier, a temporary authentication state or other short-lived session data.

The problem with local session storage

             Load Balancer
              /         \
             v           v
          App A         App B
             |           |
         Local Session  Local Session

      User request 1 -> App A
      User request 2 -> App B

If the session exists only in App A's local memory, App B may not be able to access it. This can cause inconsistent behavior when requests move between application instances.

Using Redis for sessions

             Load Balancer
              /         \
             v           v
          App A         App B
              \         /
               \       /
                  v
                Redis
             Shared Sessions

Both application instances can read and update session data from the shared Redis store.

This is particularly useful when horizontally scaling an application across multiple servers or containers.

Example

// Conceptual session storage.

sessionId = "session:abc123"

redis.setex(
    sessionId,
    1800,
    serializedSession
)

The session expires after 30 minutes in this example. Real session systems may refresh expiration on activity and enforce additional expiration and revocation rules.

When should you use Redis for sessions?

  • Multiple application instances need shared session state.
  • Sessions should expire automatically.
  • Fast session reads and writes are important.
  • Sessions can be reconstructed or users can reauthenticate if data is lost.

Session storage still needs appropriate security. Use secure session identifiers, avoid storing unnecessary sensitive data, and configure network access and authentication correctly.

3. Rate Limiting

Rate limiting restricts how frequently a client can perform an action within a time window.

For example:

  • Allow 100 API requests per minute per API key.
  • Allow five password reset attempts per 15 minutes.
  • Limit OTP verification attempts.
  • Protect an expensive endpoint from excessive traffic.

Why Redis is useful

Imagine running four application instances. If each instance maintains its own request counter, the user can potentially exceed the intended limit by distributing requests across them. 

Request 1 -> App A -> Local count: 1
Request 2 -> App B -> Local count: 1
Request 3 -> App C -> Local count: 1
Request 4 -> App D -> Local count: 1

Redis provides shared counters so the instances can enforce a common limit.

Simple fixed-window example

// Conceptual Redis commands.

INCR rate-limit:user123:minute
EXPIRE rate-limit:user123:minute 60

The application increments a counter and associates it with a time window. When the counter exceeds the configured limit, the request is rejected.

These commands must be coordinated correctly. If incrementing and setting the expiration are separate operations, a failure between them can leave a counter without an expiration. A Lua script or another atomic implementation can avoid that failure mode.

Common rate-limiting algorithms

Algorithm How it works Trade-off
Fixed window Counts requests within fixed time intervals. Simple, but permits bursts at window boundaries.
Sliding window Counts requests over a rolling interval. More accurate, often requires more state or computation.
Token bucket Requests consume tokens that refill over time. Allows controlled bursts while limiting average traffic.
Leaky bucket Processes or admits work at a controlled rate. Useful for smoothing traffic, depending on implementation.

When should you use Redis rate limiting?

Use Redis when limits need to be shared across application instances and the request rate is too high or too distributed for reliable in-process counters.

For strict security controls, think carefully about atomicity, key expiration, failure behavior and whether your chosen algorithm meets the intended policy.

4. Counters and Atomic Operations

Redis supports atomic increment and decrement operations. This makes it useful for counters that are updated frequently.

Examples include:

  • Page views.
  • API request counts.
  • Temporary usage metrics.
  • Number of active jobs.
  • Attempt counters.

Example: Counting page views

INCR page:123:views

Each execution increments the counter by one. Redis performs this increment atomically, so concurrent increments on the same key do not overwrite one another.

Atomic does not mean durable

Atomicity means the individual operation executes without interleaving with another operation in a way that breaks the operation itself. It does not guarantee that the value will survive every failure.

Redis persistence, replication and failover configuration affect durability. For financial balances or other critical business records, use a system with appropriate transactional guarantees and durable storage as the source of truth.

When should you use Redis counters?

Redis counters are useful for high-frequency updates where low latency matters and the counter's durability requirements fit the configured Redis deployment.

5. Distributed Locks

A distributed lock coordinates access to a resource across multiple processes or application instances.

A normal in-process mutex protects threads within one process. It does not automatically coordinate separate servers.

Example problem: Duplicate processing

Imagine two workers receive the same logical task at nearly the same time. 

Worker A                 Worker B
   |                         |
   v                         v
Process invoice         Process invoice
   |                         |
   +------------+------------+
                |
                v
        Duplicate processing

If both workers must not process the same task concurrently, a coordination mechanism may be needed.

Using a Redis lock

Redis supports conditional key creation. A client can attempt to acquire a lock only when the lock key does not already exist. 

SET lock:invoice:123 unique-token NX PX 30000
  • NX — create the key only if it does not exist.
  • PX 30000 — set a 30-second expiration.
  • unique-token — a unique ownership token generated by the client.

If Redis returns success, the client acquired the lock. If the key already exists, another client may hold it.

Why use an expiration?

Without an expiration, a crashed worker could leave a lock behind indefinitely.

An expiration helps recover from abandoned locks, but it introduces an important risk: the original worker may continue running after its lock expires, while another worker acquires the same lock.

Important lock rules

  • Generate a unique ownership token for each acquisition.
  • Release the lock only if the stored token matches your token.
  • Use an atomic compare-and-delete operation to release it.
  • Choose a lease duration that accounts for execution time.
  • Consider renewal and failure scenarios for longer-running work.
  • Use fencing tokens or resource-level protections when stale lock holders could cause damage.

Never release a lock with an unconditional DEL lock:key if another worker might have acquired the lock after your lease expired.

Redis locks are useful for coordinating work, but they are not a substitute for database uniqueness constraints, transactions or idempotency. For critical operations, the protected resource should enforce its own correctness whenever possible.

6. Queues and Asynchronous Processing

Redis can support background job processing and queue-like workflows.

Instead of making the client wait for every operation, the application can enqueue work and process it asynchronously.

Example: Sending an email

Client submits order
        |
        v
Application saves order
        |
        v
Enqueue email job
        |
        v
Return response to client

Background Worker
        |
        v
Process email job
        |
        v
Send confirmation email

Redis-backed job systems can help with tasks such as:

  • Sending emails and notifications.
  • Generating reports.
  • Processing images.
  • Calling external APIs.
  • Executing scheduled jobs.

Redis lists as a simple queue

Redis lists provide commands that can be used to enqueue and retrieve items. 

// Producer
LPUSH jobs '{"type":"send_email","userId":123}'

// Consumer
BRPOP jobs 0

This demonstrates a basic blocking queue pattern. It is not a complete production job-processing system: if a worker retrieves a job and crashes before completing it, the job may be lost.

What about retries and failed jobs?

Production job processing often needs:

  • Acknowledgements after successful processing.
  • Retries for transient failures.
  • Dead-letter handling for repeatedly failing jobs.
  • Job visibility and monitoring.
  • Idempotent handlers to tolerate duplicate delivery.

Redis Streams support consumer groups and explicit message acknowledgement. Mature Redis-backed job libraries also provide additional processing features.

Redis vs RabbitMQ vs Kafka

Technology Common strengths Typical use cases
Redis Low-latency data structures, simple queues, shared state. Caching, counters and lightweight background jobs.
RabbitMQ Message routing, acknowledgements, queueing and delivery controls. Business workflows and asynchronous service communication.
Kafka Durable event logs, replay and high-throughput event streams. Event-driven architectures, analytics and event pipelines.

These technologies overlap. Redis Streams, RabbitMQ and Kafka can all support messaging, but their operational models and guarantees differ. Choose based on delivery requirements, replay needs, throughput, routing and operational complexity.

7. Real-Time Leaderboards and Rankings

Redis sorted sets store unique members associated with scores. Members can be retrieved in score order, making sorted sets useful for rankings.

Common examples include:

  • Game leaderboards.
  • Top-selling products.
  • Popular articles.
  • Trending content.
  • Ranked search results based on application-defined scores.

Example: Game leaderboard

// Add or update a player's score.
ZADD leaderboard 1500 player:123

// Get the top 10 players, highest score first.
ZRANGE leaderboard 0 9 REV WITHSCORES

// Get a player's rank, with rank 0 being the lowest.
ZREVRANK leaderboard player:123

Redis maintains the sorted set so the application can query rankings without loading every player's score and sorting the entire collection itself.

Redis sorted sets are also useful for scheduling and prioritizing items by score, such as due timestamps or application-defined priority values.

8. Temporary Data and Expiring Keys

Many application values should exist only for a limited time. Redis supports key expiration, which is useful for automatically removing temporary data.

Examples include:

  • Password reset tokens.
  • Email verification codes.
  • Temporary API state.
  • Short-lived idempotency records.
  • Temporary workflow data.

Example: Verification code

SET verification:user123 482901 EX 300

This stores a verification code with a five-minute expiration. After the TTL expires, Redis makes the key eligible for removal.

For security-sensitive tokens, expiration alone is insufficient. The application should also enforce attempt limits, appropriate token entropy, one-time use, secure transport and the correct association with the user and intended action.

9. Idempotency and Duplicate Request Protection

Idempotency means that repeating an operation with the same identifier does not cause the business effect to happen more than once.

For example, a payment API may receive the same request multiple times because the client timed out and retried. 

Client sends payment request
          |
          v
Server processes payment
          |
          v
Response is lost
          |
          v
Client retries request
          |
          v
Could process payment twice

A Redis key can help track whether an idempotency key has already been observed. 

SET idempotency:request-abc processing NX EX 3600

If the key is created successfully, the application can proceed with the initial request. If it already exists, the application can check the existing operation's state.

This command alone is not a complete idempotency implementation. It does not atomically combine the Redis write with a database transaction or an external payment. A crash after creating the key but before completing the operation needs explicit handling.

For critical business operations, a durable database record, unique constraint or provider-supported idempotency mechanism is often necessary. Redis can provide a fast coordination layer when its failure behavior is accounted for.

10. Pub/Sub and Real-Time Notifications

Redis Pub/Sub lets publishers send messages to channels that subscribers listen to. 

// Publisher
PUBLISH notifications "New order created"

// Subscriber
SUBSCRIBE notifications

Subscribers receive messages while they are connected and subscribed. Redis Pub/Sub does not persist messages for disconnected subscribers.

It can be useful for:

  • Live dashboard updates.
  • Lightweight notifications between application instances.
  • Broadcasting cache invalidation signals.
  • Simple real-time features.

If a subscriber is disconnected when a message is published, it will not receive that missed message later.

When message persistence, replay, acknowledgements or recovery are required, consider Redis Streams or a dedicated messaging platform instead.

11. Geospatial Data

Redis supports geospatial operations for storing coordinates and querying locations within a radius or near another point.

Possible use cases include:

  • Finding nearby delivery drivers.
  • Locating nearby stores.
  • Showing nearby users or vehicles.
  • Maintaining live location data.

Example

GEOADD drivers -0.1276 51.5072 driver:123

GEOSEARCH drivers
    FROMLONLAT -0.12 51.50
    BYRADIUS 5 km
    ASC

The example adds a driver's longitude and latitude and searches for drivers within five kilometres of a specified point.

Redis can be useful for fast, frequently changing location lookups. Complex geographic analysis, advanced spatial joins and authoritative location records may be better handled by a dedicated geospatial database.

12. Frequently Accessed Configuration

Redis can hold configuration that needs to be read frequently by many application instances.

For example:

merchant:123:settings
feature:checkout:enabled
pricing:current:version

This can reduce repeated database reads when many requests need the same settings.

However, configuration changes require a clear invalidation or update strategy. If stale configuration could cause incorrect financial or security behavior, the application should define how freshness is guaranteed and what happens when Redis is unavailable.

Choosing the appropriate Redis data structure helps keep operations simple and efficient.

Redis vs a Relational Database

Redis and relational databases solve overlapping but different problems. Redis should not automatically replace a database simply because it is fast.

Requirement Redis Relational database
Fast cache lookups Excellent fit Possible, but often unnecessary for a separate cache layer
Complex joins Not its main strength Strong fit
Relational constraints Limited compared with relational databases Strong fit
Atomic counter increments Native operation Also supported through atomic SQL updates
Durable business records Possible with appropriate configuration, but requires careful evaluation Common choice for authoritative records
Expiring temporary data Native key expiration Usually requires cleanup logic or database-specific features
Complex transactions Supports atomic operations, transactions and scripts, with different semantics Strong transactional and relational capabilities
Aggregations and reporting Limited compared with SQL analytics Strong fit for relational queries and aggregations

The best architecture often uses both: the database stores authoritative business data, while Redis handles workloads that benefit from low-latency access or specialized data structures.

Redis vs Local In-Memory Caching

You do not always need Redis just because you want a cache.

Local cache Redis cache
Stored inside application memory. Stored in a separate Redis service.
Very fast to access without a network call. Requires communication with Redis.
Not automatically shared across application instances. Can be shared across instances.
Lost when the process restarts. Persistence and recovery depend on configuration.
Can be simpler to operate. Requires a separate service and operational monitoring.

A local cache is often enough for small, process-specific workloads. Redis becomes attractive when state must be shared across instances, memory needs to be managed separately, or Redis-specific operations are useful.

What Happens If Redis Goes Down?

The impact depends on what Redis is responsible for.

  • Cache: requests may fall back to the database, increasing latency and database load.
  • Sessions: users may temporarily lose access to session data, depending on the deployment and recovery setup.
  • Rate limiting: limits may become unavailable or inconsistent.
  • Locks: coordination assumptions can break during failures and failover.
  • Queues: queued jobs may become temporarily unavailable, and durability depends on persistence, replication and acknowledgement behavior.

This is why Redis should not be treated as an invisible, infallible performance layer. Applications need explicit failure behavior.

Should the application fail open or fail closed?

The right behavior depends on the feature.

  • Cache: often fail open and query the database, provided the database can handle the additional load.
  • Security rate limit: failing open may allow excessive requests; failing closed may block legitimate users. Choose deliberately.
  • Distributed lock: if lock acquisition fails, do not assume that the protected operation is safe to execute.
  • Background jobs: use recovery, retry and monitoring mechanisms appropriate to the required delivery guarantees.

Common Redis Mistakes

1. Treating the cache as the source of truth

If cached data can be deleted at any time, the application should know how to rebuild it or recover safely.

2. Never setting TTLs

Temporary keys without expiration can accumulate indefinitely. Not every key needs a TTL, but the lifetime should be intentional.

3. Using Redis for everything

A relational database is usually a better fit for complex relationships, SQL queries, constraints and durable business records.

4. Ignoring cache invalidation

Cached data can become stale after database updates. Define how the application refreshes or invalidates cached values.

5. Assuming every Redis operation is durable

Fast in-memory operations do not guarantee that acknowledged data will survive every crash or failover. Understand the configured persistence and replication guarantees.

6. Using unsafe distributed locks

A lock can expire while the original process is still working. Ownership checks, fencing where appropriate, and protections at the underlying resource matter.

7. Using Redis Pub/Sub for messages that must never be lost

Pub/Sub does not retain messages for disconnected subscribers. Use a durable messaging approach when missed messages are unacceptable.

8. Creating an unbounded cache

Redis memory is finite. Configure memory limits and eviction policies based on the workload, and monitor memory consumption.

9. Making expensive cache misses worse

If many requests simultaneously miss the same key, they may all query the database. This is known as a cache stampede. Techniques such as request coalescing, short-lived locks, randomized TTLs and stale-while-revalidate can help.

What Should I Remember?

  • Redis is an in-memory data store, not just a cache.
  • Caching reduces repeated database queries and expensive computations.
  • Session storage allows multiple application instances to share session state.
  • Rate limiting uses shared counters and atomic operations to control request frequency.
  • Counters benefit from Redis atomic increment operations.
  • Distributed locks help coordinate processes, but expiration and failure scenarios must be handled carefully.
  • Redis can support background jobs and queues, but delivery guarantees depend on the commands, libraries and configuration used.
  • Sorted sets are useful for leaderboards and ranking systems.
  • TTL allows temporary keys to expire automatically.
  • Pub/Sub is useful for transient notifications, but does not provide durable message delivery.
  • Redis can fail. Plan how the application behaves when Redis is unavailable.
  • Redis persistence, replication, eviction and failover settings influence reliability.
  • Do not use Redis as the sole source of truth for critical business data without explicitly evaluating its durability and consistency guarantees.
  • Use Redis when it solves a measurable problem, not simply because it is fast.
