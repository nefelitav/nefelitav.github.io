API Best Practices

30 September 2026

Good API design is less about memorizing rules and more about creating an interface that is predictable, consistent, secure and easy for other developers to use.

A useful principle is: design APIs around resources and intent, not implementation details.

This post is an overview of the practices I find useful when designing or reviewing APIs. Some of these topics deserve their own deeper articles, so this post focuses on the big picture.

1. Resource & URL Design

Use nouns, not actions

API endpoints should generally represent resources rather than actions. The HTTP method already describes what we want to do with the resource. 

GET /customers
GET /customers/123

is generally preferable to:

GET /getCustomers
GET /getCustomerById?id=123

Use path parameters for specific resources

Path parameters are useful when identifying a specific resource. 

GET /users/123

Query parameters are better suited for filtering, sorting and pagination. 

GET /users?country=NL
GET /users?status=active
GET /users?sort=created_at
GET /users?page=2&limit=50

Version your API deliberately

APIs evolve. Breaking changes can make existing clients stop working, so a clear versioning and deprecation strategy is important. 

/api/v1/customers
/api/v2/customers

URL versioning is only one possible approach. APIs can also use headers or other versioning mechanisms.

2. HTTP Semantics

Use HTTP methods consistently

HTTP methods have defined semantics. Following them makes an API easier to understand and allows clients and infrastructure to behave correctly.

GET

GET should retrieve data without causing state-changing side effects. 

GET /customers/123

Repeating a GET request should not create another customer, charge a payment or otherwise modify application state.

POST

POST is commonly used to create resources, but it is not limited to creation. It can also be used for operations that don't map naturally to a resource or that are not idempotent. 

POST /payments

PUT vs PATCH

PUT is generally used to replace a resource, while PATCH is used for partial modifications. 

PUT /users/123
PATCH /users/123

{
    "email": "new@example.com"
}

The exact semantics should be clearly defined and used consistently throughout the API.

Use meaningful status codes

Status codes communicate the result of a request. They should not all be treated as interchangeable.

  • 200 OK — request succeeded and a response is returned.
  • 201 Created — a resource was created.
  • 204 No Content — request succeeded without a response body.
  • 400 Bad Request — request is invalid.
  • 401 Unauthorized — authentication is required or invalid.
  • 403 Forbidden — the caller is authenticated but not allowed.
  • 404 Not Found — requested resource does not exist.
  • 409 Conflict — request conflicts with the current state.
  • 422 Unprocessable Content — request is syntactically valid but cannot be processed.
  • 429 Too Many Requests — rate limit has been exceeded.
  • 500 Internal Server Error — unexpected server-side failure.

Understand idempotency

An operation is idempotent when performing it multiple times has the same intended effect as performing it once.

This is especially important for APIs that perform financial or other important operations. 

POST /payments
Idempotency-Key: abc123

If the client sends the request, the server processes it, and the network fails before the response reaches the client, the client may retry. An idempotency key allows the server to recognize the retry and avoid performing the operation twice.

3. Request & Response Design

Validate all external input

Never assume that data received by an API is valid.

Validate:

  • path parameters
  • query parameters
  • request bodies
  • headers
  • uploaded data

Validation should happen at the API boundary before invalid data propagates deeper into the system.

Return useful error responses

A generic error such as this doesn't tell the client much: 

{
    "error": "Bad request"
}

A more useful response could provide a machine-readable code and information about what went wrong: 

{
    "error": {
        "code": "INVALID_EMAIL",
        "message": "The email address is invalid.",
        "field": "email"
    }
}

Error responses should be consistent, understandable and safe to expose. Don't expose stack traces, database errors or other internal implementation details.

Paginate large collections

Avoid endpoints that can return an unlimited number of records. 

GET /transactions

If there are millions of transactions, returning everything in one response can be expensive for both the server and the client.

Offset-based pagination:

GET /transactions?page=2&limit=100

or cursor-based pagination:

GET /transactions?cursor=eyJpZCI6MTIzfQ

Cursor-based pagination can be useful for large or frequently changing datasets. The choice between pagination strategies depends on the use case.

Support filtering and sorting

Query parameters can make collection endpoints flexible without creating a separate endpoint for every possible query. 

GET /transactions?status=paid
GET /transactions?currency=EUR
GET /transactions?sort=created_at
GET /transactions?created_after=2026-01-01

Consider bulk operations

When clients need to perform the same operation on many resources, individual requests may be inefficient. 

POST /users/bulk

Bulk APIs introduce additional questions, such as whether the operation is atomic, how partial failures are reported and what the maximum batch size should be.

4. Security

Authentication vs authorization

Authentication answers: Who are you?

Authorization answers: What are you allowed to do?

These are related but different concerns. Common API authentication mechanisms include API keys, OAuth 2.0, OpenID Connect and service-to-service credentials.

Authentication and authorization deserve their own deeper article.

Never trust the client

Anything sent by a browser or another external client should be treated as untrusted input.

Client-side validation is useful for user experience, but it is not a security boundary. Authorization and validation must be enforced server-side.

Don't put sensitive data in URLs

URLs can end up in browser history, proxy logs, server logs, analytics systems and monitoring tools.

For example, avoid:

GET /users?password=secret

Sensitive information should be handled using appropriate request bodies, headers or other secure mechanisms.

Use rate limiting

Rate limiting protects APIs from excessive traffic, accidental overload and certain types of abuse. 

429 Too Many Requests

Limits should be designed according to the API's consumers and use case rather than using a universal number.

5. Reliability

Set timeouts

Never assume that another service will respond immediately.

Without timeouts, a slow dependency can cause requests to remain open indefinitely and consume resources.

Retry carefully

Temporary failures can sometimes be handled with retries.

A common strategy is exponential backoff: 

Attempt 1 → wait 100 ms
Attempt 2 → wait 200 ms
Attempt 3 → wait 400 ms
Attempt 4 → wait 800 ms

Retries should not be applied blindly. Retrying a non-idempotent operation can create duplicate side effects.

Use backoff and jitter

If thousands of clients retry at exactly the same time, they can create another traffic spike.

Adding randomness, known as jitter, helps spread retries over time.

Think about concurrency

Multiple requests can modify the same resource at the same time. This can lead to race conditions.

Techniques such as optimistic locking, pessimistic locking, version fields and conditional requests can help manage concurrent updates.

6. API Evolution

Maintain backwards compatibility

Existing clients should not unexpectedly break when the API changes.

Be particularly careful when:

  • removing fields
  • renaming fields
  • changing field types
  • changing enum values
  • changing the meaning of existing values
  • making optional fields required

Adding a new optional field is generally less disruptive than changing the meaning or structure of an existing field.

Use contracts and schemas

An API contract defines what consumers can expect from an API: request formats, response formats, fields, types, errors and other behavior.

OpenAPI is commonly used to describe HTTP APIs and can also be used to generate documentation, clients and validation.

Have a deprecation strategy

Eventually APIs need to evolve or remove old functionality. Deprecation should be deliberate and communicated clearly.

Consumers should have enough information and time to migrate before a deprecated API is removed.

7. Observability

When something goes wrong in production, you need to understand what happened without reproducing the problem locally.

Logs

Structured logs make it easier to search and analyze application behavior.

Metrics

Metrics can show things such as:

  • request count
  • error rate
  • latency
  • throughput
  • resource usage

Tracing

In a distributed system, one request can travel through many services. Distributed tracing helps you understand that journey. 

Client
  ↓
API
  ↓
Payment Service
  ↓
Ledger Service
  ↓
Notification Service

Use request IDs

A request or correlation ID can make it much easier to connect logs across different services. 

X-Request-ID: 7f8c9d...

The same identifier can be included in relevant logs and propagated through downstream services.

8. Asynchronous APIs

Not every operation needs to complete during the original HTTP request. For long-running or event-driven operations, asynchronous communication can be more appropriate.

Webhooks

A webhook allows one system to notify another system when an event occurs. 

Your system
    ↓
External API

External event
    ↓
Webhook
    ↓
Your system

Reliable webhooks need to consider signature verification, retries, duplicate events, ordering and idempotency.

Asynchronous jobs

For long-running operations, an API can return immediately and allow the client to check the status later. 

POST /reports

→ 202 Accepted

{
    "job_id": "123",
    "status": "processing"
}

The client can then retrieve the job status separately.

9. Caching

Caching can reduce latency and server load, but it needs to be designed carefully so that clients don't receive stale or incorrect data.

HTTP provides mechanisms such as:

  • Cache-Control
  • ETag
  • Last-Modified
  • If-None-Match

Caching should always be considered together with cache invalidation and data freshness requirements.

10. Documentation

An API can be technically correct and still be difficult to use if its documentation is poor.

Useful API documentation should explain:

  • authentication
  • available endpoints
  • request parameters
  • request and response examples
  • error responses
  • pagination
  • rate limits
  • webhooks
  • versioning and deprecations

Tools such as OpenAPI can help keep the API contract and documentation aligned.

API Design Checklist

Endpoints

  • Does each endpoint represent a resource or clear operation?
  • Are path parameters used for resource identification?
  • Are query parameters used for filtering, sorting and pagination?
  • Is the versioning strategy clear?

HTTP semantics

  • Is the HTTP method appropriate?
  • Are GET requests free of state-changing side effects?
  • Are PUT and PATCH semantics clear?
  • Are status codes meaningful?
  • Are important operations idempotent?

Requests & responses

  • Is all external input validated?
  • Are error responses consistent and useful?
  • Are large collections paginated?
  • Are filtering and sorting predictable?
  • Are bulk operations handled deliberately?

Security

  • Are authentication and authorization enforced server-side?
  • Is sensitive information kept out of URLs?
  • Is rate limiting used where appropriate?
  • Are internal implementation details hidden from clients?

Reliability

  • Are timeouts configured?
  • Are retries limited and safe?
  • Is exponential backoff used where appropriate?
  • Are race conditions considered?
  • Are asynchronous operations handled appropriately?

Evolution & observability

  • Are breaking changes avoided or explicitly versioned?
  • Is there a deprecation strategy?
  • Is the API contract documented?
  • Can requests be traced through the system?
  • Are useful logs and metrics available?

Final Thought

Good API design ultimately makes an API predictable.

A developer should be able to interact with an API without needing to understand how the underlying system is implemented. Consistent conventions, clear contracts and well-defined behavior make APIs easier to build, integrate, operate and evolve.
