Design Patterns Explained

15 October 2026

Design patterns are reusable approaches to common software design problems. They are not libraries, frameworks, or code that you must copy exactly. They are blueprints that help you organize responsibilities, reduce coupling, and make code easier to change.

For example, imagine your application supports payments through several providers. You could put every provider's logic inside one enormous PaymentService. Alternatively, you could use a design pattern to isolate provider-specific behavior behind a common interface.

Understanding patterns helps you recognize recurring problems and communicate solutions with other engineers. The goal is not to use as many patterns as possible; it is to choose the simplest design that handles the problem well.

1. The Three Main Categories

The classic Gang of Four design patterns are grouped into three categories.

Creational patterns

Concerned with how objects are created. They help separate object construction from the code that uses those objects.

Examples: Factory Method, Abstract Factory, Builder, Singleton.

Structural patterns

Concerned with how objects and classes are combined to form larger structures.

Examples: Adapter, Decorator, Facade, Proxy.

Behavioral patterns

Concerned with how objects communicate, delegate work, and select behavior.

Examples: Strategy, Observer, Command, State, Chain of Responsibility.

These are the classic object-oriented patterns. Backend applications also use enterprise and architectural patterns, such as Repository, Unit of Work, Service Layer, and Transactional Outbox.

2. Strategy Pattern

Problem: You have several ways to perform an operation, and you want to choose the appropriate algorithm without filling your code with conditional branches.

The Strategy pattern defines a common interface for interchangeable algorithms. Each strategy implements the same contract, and a caller selects which one to use.

Example: Payment providers

Without Strategy, you might have code like this:

function pay(string $provider, int $amount): void
{
    if ($provider === 'card') {
        // Call card provider API
    } elseif ($provider === 'bank_transfer') {
        // Initiate bank transfer
    } elseif ($provider === 'wallet') {
        // Process wallet payment
    }
}

As providers and their rules grow, this method accumulates branches and becomes harder to test.

With Strategy, each implementation follows the same interface:

interface PaymentStrategy
{
    public function pay(int $amount): void;
}

final class CardPayment implements PaymentStrategy
{
    public function pay(int $amount): void
    {
        // Process card payment
    }
}

final class BankTransferPayment implements PaymentStrategy
{
    public function pay(int $amount): void
    {
        // Process bank transfer
    }
}

final class PaymentService
{
    public function __construct(
        private PaymentStrategy $strategy
    ) {}

    public function pay(int $amount): void
    {
        $this->strategy->pay($amount);
    }
}

The application can inject the appropriate implementation into PaymentService.

Use it when:

  • You have multiple interchangeable algorithms.
  • New variants are likely to be added.
  • You want to test each implementation independently.

Common examples: payment methods, discount calculations, shipping cost calculations, pricing rules, and different retry policies.

Don't use it automatically: if there are only two simple branches and no expectation of growth, a straightforward conditional may be easier to understand.

3. Factory Pattern

Problem: The calling code should not need to know all the details of constructing a particular object.

A factory centralizes object creation and returns an object that the caller can use. The term "Factory" is also commonly used for simple factory methods, which are useful even when they are not the formal Gang of Four Factory Method pattern.

Example: Choosing a payment provider

final class PaymentStrategyFactory
{
    public function create(string $provider): PaymentStrategy
    {
        return match ($provider) {
            'card' => new CardPayment(),
            'bank_transfer' => new BankTransferPayment(),
            default => throw new InvalidArgumentException(
                'Unsupported payment provider'
            ),
        };
    }
}

The caller asks the factory for a strategy instead of constructing provider-specific classes itself.

Use it when:

  • Object creation involves non-trivial logic.
  • The concrete implementation depends on configuration or input.
  • You want to centralize construction rules.

Common examples: selecting payment clients, choosing file parsers, constructing notification senders, or creating exporters based on an output format.

In a dependency-injection framework, the container may already handle much of the construction. Avoid adding a factory that merely forwards every call without simplifying anything.

4. Adapter Pattern

Problem: An external library or service has an interface that does not match what your application expects.

An Adapter translates one interface into another. It lets your application work with a consistent contract while hiding provider-specific details.

Example: Integrating different invoicing providers

Imagine one provider returns a field called invoice_id, while another returns documentReference. Their SDKs may also expose different method names and error formats.

Your application defines its own contract:

interface InvoiceProvider
{
    public function submit(Invoice $invoice): string;
}

Each provider has an adapter:

final class ProviderAAdapter implements InvoiceProvider
{
    public function __construct(
        private ProviderAClient $client
    ) {}

    public function submit(Invoice $invoice): string
    {
        $response = $this->client->createInvoice(
            $invoice->toProviderPayload()
        );

        return $response['invoice_id'];
    }
}

A second adapter can translate another provider's API into the same InvoiceProvider contract.

Use it when:

  • You integrate with third-party APIs or SDKs.
  • You need to support multiple vendors.
  • You want to keep external API details out of business logic.
  • You need to isolate a legacy interface.

This pattern is particularly useful in backend systems that integrate with payment providers, tax services, ERP systems, or messaging platforms.

5. Decorator Pattern

Problem: You want to add behavior to an object without modifying its original implementation or creating many subclasses.

A decorator wraps an object that implements the same interface. It can add behavior before or after delegating to the wrapped object.

Example: Logging an HTTP client

interface HttpClient
{
    public function get(string $url): Response;
}

final class LoggingHttpClient implements HttpClient
{
    public function __construct(
        private HttpClient $inner,
        private LoggerInterface $logger
    ) {}

    public function get(string $url): Response
    {
        $this->logger->info('Sending HTTP request', [
            'url' => $url,
        ]);

        $response = $this->inner->get($url);

        $this->logger->info('HTTP request completed', [
            'status' => $response->statusCode(),
        ]);

        return $response;
    }
}

The wrapped client performs the actual request. The decorator adds logging without changing that client's implementation.

Other possible decorators can add:

  • Metrics and tracing.
  • Retry behavior.
  • Caching.
  • Request or response transformations.

Use it when: you want to add optional, composable behavior around an implementation.

Be careful when combining retries, logging, and HTTP requests. Retrying a non-idempotent operation can accidentally create duplicate side effects.

6. Observer Pattern

Problem: When something happens, several independent parts of the application need to react to it.

The Observer pattern allows one object to notify interested observers when an event occurs. The publisher does not need to know all the details of each observer.

Example: An order is placed

When an order is placed, several actions may be needed:

  • Send a confirmation email.
  • Update analytics.
  • Record an audit event.

In a simple in-process implementation, listeners subscribe to an event such as OrderPlaced. When that event is dispatched, the registered listeners are invoked. 

OrderPlaced
    |
    +--> SendOrderConfirmation
    |
    +--> UpdateSalesMetrics
    |
    +--> RecordAuditEvent

Framework event systems often use this pattern or a closely related event-dispatching design.

Use it when:

  • Multiple components react to the same event.
  • You want to avoid tightly coupling the publisher to every reaction.
  • New reactions should be easy to add.

Important distinction: in-process observers run within your application process. They are not automatically durable or asynchronous. If a listener fails or the process crashes, you need an explicit failure strategy. For reliable cross-service communication, you may need a message broker and patterns such as the Transactional Outbox.

7. Chain of Responsibility

Problem: A request needs to pass through several processing steps, and each step should be able to handle, reject, or pass it onward.

Chain of Responsibility organizes handlers into a sequence. Each handler decides whether to process the request or continue the chain.

Example: An HTTP request pipeline

Incoming Request
       |
       v
Authentication
       |
       v
Authorization
       |
       v
Validation
       |
       v
Controller

Middleware pipelines in web frameworks are a common practical example. A handler can stop the request—for example, when authentication fails—or pass it to the next handler.

Other examples include:

  • Validation rules.
  • Fraud checks.
  • Approval workflows.
  • Escalation and support routing.

Use it when: processing steps are ordered, independently configurable, or likely to change.

Watch out for: a request silently passing through every handler without being handled, or a long chain becoming difficult to trace.

8. Command Pattern

Problem: You want to represent an action as an object so that it can be queued, retried, logged, scheduled, or executed later.

A command encapsulates a request and the data needed to execute it.

Example: Generating an invoice asynchronously

final class GenerateInvoice
{
    public function __construct(
        public readonly string $invoiceId
    ) {}

    public function handle(InvoiceGenerator $generator): void
    {
        $generator->generate($this->invoiceId);
    }
}

The application can dispatch the command to a background queue rather than generate the invoice during the HTTP request.

Commands are useful for:

  • Background jobs.
  • Scheduled tasks.
  • Retryable operations.
  • Auditable business actions.
  • Separating the request to perform an action from its execution.

Many job-queue systems use command-like objects. However, a command object alone does not guarantee durable delivery, exactly-once execution, or safe retries. Those properties depend on the execution infrastructure and application design.

9. State Pattern

Problem: An object's behavior depends on its current state, and many conditional branches are becoming difficult to maintain.

The State pattern represents states as separate objects or otherwise encapsulates state-specific behavior. The object delegates behavior to its current state.

Example: An invoice lifecycle

Draft
  |
  v
Issued
  |
  +------> Paid
  |
  +------> Overdue
  |
  +------> Cancelled (if allowed)

The rules for each state may differ. For example, a draft invoice may be editable, while an issued invoice may require a correction process instead of direct editing.

A state-oriented design can keep those rules close to the relevant state rather than scattering them throughout the application.

Use it when:

  • An entity has a meaningful lifecycle.
  • Allowed operations depend on its state.
  • State transitions have different business rules.

Examples include payment lifecycles, subscriptions, order processing, document approval, and account activation.

You do not always need separate state classes. For a small lifecycle, an enum and explicit transition validation may be simpler.

10. Builder Pattern

Problem: Constructing an object requires many parameters, optional settings, or a sequence of configuration steps.

A Builder separates the construction process from the final object. It is especially helpful when an object has many optional properties or must be assembled in a readable way.

Example: Building an API request

$request = ApiRequestBuilder::create()
    ->withMethod('POST')
    ->withPath('/invoices')
    ->withHeader('Idempotency-Key', $key)
    ->withJsonBody($payload)
    ->build();

The builder can apply defaults, validate required fields, and produce a complete request object.

Use it when:

  • An object has many optional settings.
  • Construction has multiple steps.
  • You want readable test fixtures or configuration objects.

If an object only requires two or three straightforward parameters, a regular constructor is often enough.

11. Facade Pattern

Problem: A subsystem contains many classes and steps, but callers need only a simple operation.

A Facade provides a simplified interface over a more complicated subsystem.

Example: Checkout

Completing checkout may require inventory checks, payment authorization, order persistence, and confirmation. 

final class CheckoutService
{
    public function __construct(
        private InventoryService $inventory,
        private PaymentService $payments,
        private OrderRepository $orders
    ) {}

    public function checkout(Cart $cart): Order
    {
        $this->inventory->assertAvailable($cart);

        $payment = $this->payments->authorize($cart);

        return $this->orders->createFromCart($cart, $payment);
    }
}

The caller invokes one high-level method instead of coordinating all the subsystem classes itself.

Use it when: a subsystem has a complicated API or a common workflow needs a simpler entry point.

A Facade should simplify orchestration, not become a giant class that accumulates every business rule in the application.

12. Proxy Pattern

Problem: You need to control access to an object, add lazy initialization, or perform work before delegating to the real object.

A Proxy provides an interface compatible with the object it represents, while controlling access to it.

Example: Lazy-loading an expensive resource

An application may defer creating an expensive client or loading a resource until it is first needed. A proxy can also enforce access control or forward calls to a remote service.

Common examples include:

  • Lazy-loaded objects in ORM systems.
  • Access-control proxies.
  • Remote service proxies.
  • Framework-generated proxies used for interception.

Use it when: controlling access or deferring expensive work is a real requirement.

13. Repository Pattern

Problem: Business logic is tightly coupled to SQL queries and persistence details, making it harder to test or change data access.

A Repository provides a domain-oriented interface for retrieving and persisting entities. It separates the code that uses those entities from the details of how they are stored.

Example: Loading an invoice

interface InvoiceRepository
{
    public function findById(string $id): ?Invoice;

    public function save(Invoice $invoice): void;
}

final class IssueInvoice
{
    public function __construct(
        private InvoiceRepository $invoices
    ) {}

    public function execute(string $id): void
    {
        $invoice = $this->invoices->findById($id);

        if ($invoice === null) {
            throw new RuntimeException('Invoice not found');
        }

        $invoice->issue();

        $this->invoices->save($invoice);
    }
}

The use case depends on the repository contract, not on a particular SQL implementation. A MySQL-backed repository can implement that contract.

Use it when:

  • Domain logic should be independent of persistence details.
  • Data-access logic is duplicated across the application.
  • You need a clear boundary for testing or swapping implementations.

Not every application needs a custom repository class for every database table. ORM models and query builders may already provide enough abstraction. Avoid creating repositories that merely duplicate every ORM method without adding meaningful value.

14. Dependency Injection

Problem: A class constructs its own dependencies, making it difficult to replace them for tests or change implementations.

Dependency Injection means that a class receives the objects it needs from the outside rather than constructing those dependencies internally. It is a technique, not one of the classic 23 Gang of Four patterns.

Example

// Tightly coupled
final class InvoiceService
{
    private MySqlInvoiceRepository $repository;

    public function __construct()
    {
        $this->repository = new MySqlInvoiceRepository();
    }
}

The class above decides which concrete repository to use.

// Dependency injected
final class InvoiceService
{
    public function __construct(
        private InvoiceRepository $repository
    ) {}
}

Now the caller or dependency-injection container supplies the repository implementation.

Benefits:

  • Dependencies are explicit.
  • Unit tests can provide fakes or mocks.
  • Implementations can be replaced with less impact on business logic.
  • Object creation can be centralized in a container.

Dependency Injection works particularly well with interfaces, but not every dependency needs an interface. Introduce abstractions where they provide a useful boundary, not merely because every class must have one.

15. How These Patterns Fit Together

Patterns are not isolated recipes. A single backend feature can use several patterns because each addresses a different design problem.

Example: Issuing an invoice

HTTP Controller
      |
      v
IssueInvoice Use Case
      |
      +----> InvoiceRepository
      |
      +----> InvoiceProviderFactory
                    |
                    v
              Provider Adapter
                    |
                    v
             External E-invoicing API
  • Dependency Injection: supplies the repository and other dependencies.
  • Repository: isolates persistence operations.
  • Factory: selects or constructs a provider implementation when needed.
  • Adapter: translates your application's interface to the provider's API.
  • Strategy: can make provider-specific submission behavior interchangeable.
  • Command: can represent invoice issuance as an asynchronous job.
  • Observer: can notify in-process listeners when issuance succeeds.

You do not necessarily need all of these in one feature. Use only the patterns that solve actual problems in the design.

17. Other Patterns Worth Knowing

Once you understand the patterns above, these are useful additions to your software-engineering vocabulary.

  • Singleton: restricts a class to one instance and exposes a shared access point. Use carefully because global mutable state can complicate testing and concurrency.
  • Template Method: defines the skeleton of an algorithm in a base class while allowing subclasses to customize particular steps.
  • Composite: treats individual objects and groups of objects through a common interface, often using a tree structure.
  • Bridge: separates an abstraction from its implementation so both can evolve independently.
  • Abstract Factory: creates families of related objects without exposing their concrete classes.
  • Mediator: centralizes communication between components to reduce direct dependencies.
  • Iterator: provides a way to traverse a collection without exposing its internal representation.

There are also important distributed-system patterns that solve problems beyond individual objects and classes:

  • Transactional Outbox: records an event in the same database transaction as the business change, then publishes it asynchronously to help avoid lost events.
  • Retry with Backoff: retries transient failures while spacing out attempts, often with increasing delays.
  • Circuit Breaker: temporarily stops calls to a failing dependency to limit cascading failures.
  • Bulkhead: isolates resources or workloads so that failures in one area do not exhaust the whole system.
  • Saga: coordinates a business process across multiple independent transactions, using compensating actions when needed.

These are often discussed alongside design patterns, but they operate at different levels. The first group mostly structures code and objects; the second group addresses workflows, resilience, and distributed systems.

18. When Should You Avoid a Design Pattern?

A design pattern is useful only when it makes the design easier to understand, test, extend, or maintain.

Common warning signs include:

  • Premature abstraction: you introduce interfaces and layers for hypothetical future requirements.
  • Too many classes: a simple operation becomes difficult to follow because every line delegates to another object.
  • Indirection without a benefit: a factory or facade adds another layer but hides no meaningful complexity.
  • Pattern overfitting: you force a problem into a familiar pattern even though a simpler design works better.

Start with clear code and a well-defined responsibility. Introduce a pattern when a recurring problem becomes visible or when it clearly simplifies the design.

Conclusion

You do not need to memorize every design pattern to become a good software engineer. Focus first on recognizing the problems they solve.

For backend development, start with Strategy, Factory, Adapter, Decorator, Observer, Chain of Responsibility, Command, Repository, and Dependency Injection. These are practical tools for handling integrations, business rules, asynchronous work, and maintainable application boundaries.

As your systems grow, learn the patterns that address the problems you encounter—whether that is state management, distributed messaging, concurrency, or resilience.
