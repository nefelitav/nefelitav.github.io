Synchronous vs Asynchronous APIs

30 September 2026

When designing an API, ask: does the client need to wait for the operation to finish?

In a synchronous API, the client waits for the result. In an asynchronous API, the client can continue while the operation is processed in the background.

Synchronous APIs

The client sends a request and waits for the server to return the result. 

Client ─── Request ───► Server
Client ◄── Response ─── Server
              waits

Good for operations that are quick and need an immediate result:

  • Fetching a resource
  • Updating a resource
  • Creating a simple resource
  • Validating data
  • Short calculations
GET /customers/123
PUT /customers/123
POST /payments

Asynchronous APIs

The client starts an operation without waiting for it to complete. This is useful for long-running or resource-intensive work. 

Client ─── Request ───► Server
Client ◄── 202 Accepted ─ Server

        ... work happens later ...

             Worker
                ↓
             Processing

For example, generating a large report:

POST /reports

HTTP/1.1 202 Accepted

{
    "job_id": "job_123",
    "status": "processing"
}

What Does 202 Accepted Mean?

  • 200 OK — request completed and a result is returned.
  • 201 Created — a resource was created.
  • 202 Accepted — request was accepted, but processing may still be running.

Getting the Result

Common approaches for asynchronous operations include:

Polling

The client periodically checks the status of the operation. 

POST /reports
→ 202 Accepted

GET /reports/job_123
→ { "status": "processing" }

GET /reports/job_123
→ { "status": "completed" }

Polling is simple, but the client may discover completion with some delay.

Webhooks

Instead of repeatedly checking, the server notifies the client when something happens. 

Client
   │
   │ POST /reports
   ▼
Server
   │
   │ 202 Accepted
   ▼
Client

... later ...

Server ─── POST /webhooks/report-completed ───► Client

Webhooks are particularly useful when another backend service needs to react to an event.

Message Queues

Work can be placed on a queue and processed by a background worker. 

Client
   ↓
 API
   ↓
Queue
   ↓
Worker
   ↓
Database

Queues help handle large workloads, traffic spikes, retries and independent worker scaling.

Asynchronous ≠ Queue

An asynchronous API describes when the client receives the result. A queue is only one possible implementation.

Asynchronous workflows can use:

  • Polling
  • Webhooks
  • Message queues
  • Background workers
  • Event-driven processing

When Should You Use Asynchronous APIs?

Asynchronous processing is useful when an operation:

  • Takes a long time
  • Is computationally expensive
  • Processes large amounts of data
  • Doesn't require an immediate result
  • Can run in the background
  • Benefits from independent workers or retries
Generate a large report   → Asynchronous
Process millions of records → Asynchronous
Send an email              → Often asynchronous
Process a video            → Asynchronous
Fetch a customer           → Usually synchronous

Synchronous vs Asynchronous

Synchronous Asynchronous
Client waits Yes No
Immediate result Usually Not necessarily
Long-running work Less suitable Well suited
Polling / webhooks Usually unnecessary Common
Queues Not required Often used
Complexity Lower Higher

Retries & Idempotency

Asynchronous systems can introduce additional failure scenarios. A request may be retried if the client doesn't receive a response. 

POST /payments
Idempotency-Key: abc123

An idempotency key allows the server to recognize duplicate requests representing the same operation.

This is especially important for operations such as payments, where processing the same request twice can have serious consequences.

Challenges of Asynchronous Systems

  • Retries — what happens when processing fails?
  • Duplicates — can the same operation run twice?
  • Ordering — does operation order matter?
  • Dead-letter queues — where do repeatedly failing messages go?
  • Eventual consistency — when do systems see the same state?
  • Backpressure — what happens when work arrives too quickly?

What Should I Remember?

  • Synchronous — the client waits for the result.
  • Asynchronous — the client doesn't wait for completion.
  • 202 Accepted — work was accepted but may not be complete.
  • Polling, webhooks and queues are common asynchronous patterns.
  • Asynchronous systems require careful handling of retries, duplicates and ordering.
  • Idempotency is important when operations can be retried.
