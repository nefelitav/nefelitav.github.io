HTTP Headers

30 September 2026

HTTP headers are key-value pairs that allow clients and servers to exchange metadata about an HTTP request or response. 


            Content-Type: application/json
            Accept: application/json
            Authorization: Bearer

Headers provide information about authentication, content formats, caching, cookies, security, tracing and more.

Request vs Response Headers

Request headers provide information or instructions to the server. Response headers provide information or instructions to the client. 

POST /users HTTP/1.1

Content-Type: application/json
Accept: application/json
Authorization: Bearer eyJ...

{
"name": "Nefeli"
}
HTTP/1.1 201 Created

Content-Type: application/json
Location: /users/123

{
"id": "123",
"name": "Nefeli"
}

Content & Representation

Content-Type

Describes the format of the request or response body. 

Content-Type: application/json

Accept

Specifies which response formats the client accepts. 

Accept: application/json

Remember: Content-Type = what is being sent, Accept = what the client wants back.

Authentication

Authorization

Authorization: Bearer eyJhbGciOi...

Commonly used to send access tokens. Authentication answers who are you?, while authorization answers what are you allowed to do?

Cookies

Cookies allow browsers to store and send small pieces of state. 

Set-Cookie: session_id=abc123; Secure; HttpOnly; SameSite=Lax

Cookie: session_id=abc123
  • Secure — only send over HTTPS.
  • HttpOnly — prevents JavaScript access.
  • SameSite — controls cross-site cookie sending.
  • Domain / Path — controls where the cookie is sent.
  • Max-Age / Expires — controls its lifetime.

Caching

Cache-Control

Controls how responses can be cached. 

Cache-Control: max-age=3600

Cache-Control: no-cache
Cache-Control: no-store
Cache-Control: private
Cache-Control: public

no-cache does not mean "don't cache". It generally means the cached response must be revalidated before reuse.

ETag

Identifies a specific representation of a resource and can be used for efficient caching and concurrency control. 

ETag: "abc123"

If-None-Match: "abc123"

→ 304 Not Modified

Last-Modified

Last-Modified: Wed, 30 Sep 2026 10:00:00 GMT

If-Modified-Since: Wed, 30 Sep 2026 10:00:00 GMT

Conditional Requests

Headers such as If-Match allow requests to depend on the current version of a resource. 

GET /users/123

ETag: "version-42"

PUT /users/123
If-Match: "version-42"

If another client already changed the resource to version 43, the server can reject the update instead of overwriting the newer data. This is a form of optimistic concurrency control.

CORS

Cross-Origin Resource Sharing (CORS) controls how browsers allow web pages from one origin to make requests to another origin. 

Origin: https://example.com
Access-Control-Allow-Origin: https://example.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Allow-Credentials: true

An origin consists of scheme + host + port. CORS is primarily a browser security mechanism; it does not prevent non-browser clients such as backend services or curl from making requests.

Security Headers

Common browser security headers include:

Strict-Transport-Security: max-age=31536000

Content-Security-Policy: default-src 'self'

X-Content-Type-Options: nosniff

X-Frame-Options: DENY

Referrer-Policy: strict-origin-when-cross-origin
  • HSTS — tells browsers to use HTTPS.
  • CSP — controls allowed resources and scripts.
  • X-Content-Type-Options — prevents MIME sniffing.
  • X-Frame-Options — helps protect against clickjacking.
  • Referrer-Policy — controls referrer information.

Redirects

Location tells the client where a resource or redirect points. 

HTTP/1.1 302 Found

Location: https://example.com/new-location

It is also commonly returned after creating a resource: 

HTTP/1.1 201 Created

Location: /users/123

Rate Limiting

APIs can limit how many requests a client can make. When the limit is exceeded: 

HTTP/1.1 429 Too Many Requests

Retry-After: 60

Retry-After tells the client when it should retry.

Client & Request Information

  • Host — identifies the target host.
  • User-Agent — provides information about the client.
  • Referer — indicates the page that initiated a request.
  • Origin — identifies the origin of a browser request.

Client-provided headers such as User-Agent should not generally be treated as trustworthy security information.

Idempotency

APIs can use Idempotency-Key to make retries of non-idempotent operations safe. 

POST /payments

Idempotency-Key: abc123

If a request is retried after a network failure, the server can recognize the same key and avoid performing the operation twice.

This is especially important for payments, orders and other operations with important side effects.

Custom Headers

Applications can define custom headers when standard HTTP mechanisms don't solve the problem. 

Idempotency-Key: abc123

X-Request-ID: 7f8c9d...

The historical X- prefix is no longer generally recommended for new custom headers.

Proxies & Forwarded Headers

Requests often pass through CDNs, load balancers, reverse proxies or API gateways before reaching the application. 

Client

Common headers include:

Forwarded

X-Forwarded-For
X-Forwarded-Proto
X-Forwarded-Host

These should not be blindly trusted. Their trustworthiness depends on which proxies are allowed to set or sanitize them.

HTTP/2 & HTTP/3

HTTP/2 uses pseudo-headers such as: 

:method

:path
:scheme
:authority
:status

These are not ordinary HTTP headers. HTTP/2 and HTTP/3 also use binary protocols rather than HTTP/1.1's textual wire format.

A Useful Mental Model

POST /payments?currency=EUR HTTP/1.1

Authorization: Bearer ...
Content-Type: application/json
Accept: application/json
Idempotency-Key: abc123
X-Request-ID: 7f8c9d...

{
"amount": 1000,
"currency": "EUR"
}
  • Method: What operation are we performing?
  • URL / path: What resource are we interacting with?
  • Query parameters: How should the request be filtered or modified?
  • Headers: What metadata or instructions accompany the request?
  • Body: What data are we sending?

What Should I Remember?

  • HTTP headers are metadata exchanged between clients and servers.
  • Content-Type describes the body being sent.
  • Accept describes the response formats the client accepts.
  • Authorization is commonly used for authentication credentials.
  • Cookie and Set-Cookie handle browser cookies.
  • Cache-Control and ETag are important for caching.
  • If-Match can help prevent concurrent updates from overwriting newer data.
  • CORS controls browser cross-origin requests.
  • Security headers communicate browser security policies.
  • Retry-After helps clients handle rate limits.
  • Request and tracing headers help debug distributed systems.
  • Idempotency keys make certain retries safe.
  • Use custom headers carefully when standard HTTP mechanisms aren't enough.
