Deployment Strategies

14 October 2026

Deploying a new application version is not simply a matter of replacing the old code with the new code. A deployment can introduce bugs, increase latency, cause errors, or affect every user at once.

Deployment strategies describe how application versions are introduced into an environment and how traffic moves between them. Different strategies offer different trade-offs in terms of risk, infrastructure cost, rollback speed, and complexity.

A useful principle is: deploy changes in a way that limits their impact, allows you to detect problems, and makes recovery predictable.

1. How Does a Deployment Work?

Before exploring deployment strategies, it helps to understand the components involved in a typical software release.

  • Application: The code that implements your business logic and serves requests.
  • Container image: A packaged version of the application and its runtime dependencies.
  • Infrastructure: The machines or containers that run the application.
  • Traffic routing: The mechanism that determines which application instances receive requests.
  • CI/CD pipeline: The automated process that builds, tests, and deploys changes.

Consider an application running version 1: 

Users

  v
Application v1
  |
  v
Database

You have developed version 2 and want to release it. The main question is how to introduce v2 without unnecessarily disrupting the users who are still using v1.

This is where deployment strategies become useful.

2. Rolling Deployment

A rolling deployment gradually replaces instances of the old application version with instances of the new version.

Instead of stopping every old instance and starting every new instance at once, the deployment system replaces them in stages. 

Initial state:

[v1] [v1] [v1] [v1]

During deployment:

[v2] [v1] [v1] [v1]

[v2] [v2] [v1] [v1]

[v2] [v2] [v2] [v1]

Final state:

[v2] [v2] [v2] [v2]

How does it work?

The deployment system starts new instances, waits for them to become ready, and gradually removes old instances. During the transition, both versions may serve traffic simultaneously.

How do you implement it?

Kubernetes supports rolling updates through its Deployment resource. A Deployment manages ReplicaSets, which manage the application's Pods. 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: app
          image: my-app:v1
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /health
              port: 8080

Here, maxSurge: 1 allows Kubernetes to temporarily run one additional Pod beyond the desired four replicas. maxUnavailable: 0 prevents the rollout from intentionally reducing the number of available replicas below four.

These settings work together with the readiness probe, which helps Kubernetes determine whether a Pod is ready to receive traffic.

To deploy a new version: 

kubectl set image deployment/my-app \
  app=my-app:v2

kubectl rollout status deployment/my-app

To undo the most recent rollout: 

kubectl rollout undo deployment/my-app

When should you use it?

  • When you want a straightforward deployment process.
  • When you want to gradually replace application instances.
  • When you do not need sophisticated traffic splitting.
  • When your infrastructure cannot afford to run two complete environments.

Trade-off: Old and new application versions coexist during the rollout. They must be compatible with the same database and any shared dependencies. A rollback also does not automatically undo database changes or reverse side effects that have already occurred.

3. Blue-Green Deployment

A blue-green deployment maintains two separate application environments. One serves production traffic, while the other receives the new version and is prepared for release.

  • Blue: The currently active production version.
  • Green: The new version being prepared.
Before deployment:

Users
  |
  v
Blue environment (v1)

Green environment (v2)
Not serving production traffic


After switching:

Users
  |
  v
Green environment (v2)

Blue environment (v1)
Kept available for rollback

How does it work?

  1. Keep v1 serving production traffic.
  2. Deploy v2 into the separate green environment.
  3. Run health checks and smoke tests against v2.
  4. Switch production traffic from blue to green.
  5. Keep blue available temporarily in case rollback is needed.

How do you implement it with Kubernetes?

You can create separate Deployments for each version and use a Service to select which version receives traffic. 

# Blue Deployment labels
app: my-app
version: blue

# Green Deployment labels
app: my-app
version: green

The production Service initially selects blue: 

apiVersion: v1
kind: Service
metadata:
  name: my-app
spec:
  selector:
    app: my-app
    version: blue
  ports:
    - port: 80
      targetPort: 8080

After green has been tested, change the selector to version: green. The Service will route new connections to the green Pods once the corresponding endpoints are updated.

In practice, you can use a deployment controller such as Argo Rollouts to automate the process and manage traffic switching.

When should you use it?

  • When you want a clear separation between the current and new versions.
  • When you need a fast way to switch back to the previous version.
  • When you can afford the additional infrastructure during deployment.
  • When you want to test a new environment before directing production traffic to it.

Trade-off: Running two environments can be expensive. Switching traffic does not guarantee that rollback is safe if the new version has already changed the database schema or produced irreversible side effects.

4. Canary Deployment

A canary deployment introduces the new version to a small portion of production traffic before exposing it to everyone.

The idea is to limit the number of users affected if something goes wrong. 

Initial state:

100% of traffic --> v1

First stage:

95% of traffic --> v1
 5% of traffic --> v2

Second stage:

80% of traffic --> v1
20% of traffic --> v2

Third stage:

50% of traffic --> v1
50% of traffic --> v2

Final state:

100% of traffic --> v2

How does it work?

  1. Deploy the new version alongside the stable version.
  2. Send a small percentage of production traffic to the new version.
  3. Monitor error rates, latency, resource usage, and business metrics.
  4. Increase traffic if the new version behaves as expected.
  5. Stop the rollout and return traffic to the stable version if problems appear.

How do you implement it?

Kubernetes can run both versions, but its standard Service does not provide arbitrary percentage-based traffic splitting between two Deployments. A Service generally distributes traffic among its eligible endpoints.

For controlled traffic splitting, you can use a rollout controller and a compatible traffic router, such as Argo Rollouts with an appropriate ingress controller or service mesh.

For example, an Argo Rollouts configuration can define a canary strategy with progressively increasing traffic weights. 

strategy:
  canary:
    steps:
      - setWeight: 5
      - pause:
          duration: 5m
      - setWeight: 20
      - pause:
          duration: 10m
      - setWeight: 50
      - pause:
          duration: 10m

This is an illustrative fragment of an Argo Rollouts resource, not a complete Kubernetes manifest. Traffic splitting requires a configured traffic-management integration.

When should you use it?

  • When deploying changes with a potentially large impact.
  • When production traffic is necessary to detect realistic problems.
  • When you have sufficient traffic and monitoring to evaluate the new version.
  • When you want to limit the number of users exposed to a faulty release.

Trade-off: Canary deployments require reliable monitoring and traffic routing. A small percentage of traffic may not expose rare bugs, and the percentage of requests does not necessarily equal the percentage of affected users.

5. Feature Flags

A feature flag allows you to enable or disable a feature through configuration rather than requiring a new application deployment.

This separates two activities:

  • Deployment: Putting code into an environment.
  • Release: Making a feature available to users.

You can deploy new code while keeping the feature disabled. Later, you can enable it for internal users, selected customers, or a percentage of users.

Example in PHP

if ($featureFlags->isEnabled('new_checkout', $user)) {
    return $newCheckout->handle($request);
}

return $oldCheckout->handle($request);

The flag service evaluates whether the feature is enabled for the current user. The application then selects the appropriate implementation.

A simple configuration-based implementation might look like this: 

return [
    'new_checkout' => false,
];

A dedicated feature-flag platform can provide more advanced behavior, including user targeting, percentage rollouts, and configuration updates without redeploying the application.

How does this relate to Kubernetes?

Kubernetes can supply configuration through environment variables or ConfigMaps, but it does not provide a complete feature-flag management system by itself.

For example, you could change a ConfigMap value and arrange for the application to reload its configuration. However, an application that only reads the value at startup may require a restart. A dedicated flag service can support dynamic updates.

When should you use it?

  • When deploying a feature before it is ready for all users.
  • When enabling functionality for internal users first.
  • When gradually releasing a feature to selected customers.
  • When you need an operational kill switch for a feature.

Trade-off: Flags introduce conditional logic and configuration complexity. Old flags should be removed when they are no longer needed, and sensitive functionality must still be protected by proper authorization checks.

6. Progressive Delivery

Progressive delivery is a broader release approach in which changes are introduced gradually, evaluated using metrics or checks, and promoted or rolled back based on the results.

It is not a completely separate deployment mechanism. Instead, it can combine techniques such as canary deployments, feature flags, automated analysis, and approval steps. 

Deploy v2
    |
    v
Send 5% of traffic to v2
    |
    v
Check error rate and latency
    |
    +---- Metrics look good ----> Increase traffic
    |
    +---- Metrics look bad -----> Abort rollout
                                      |
                                      v
                              Keep v1 serving traffic

How do you implement it?

A typical setup combines:

  • A CI/CD pipeline to build and deploy the application.
  • A rollout controller to manage deployment steps.
  • Monitoring tools to collect metrics such as latency and errors.
  • Automated analysis or approval rules to control promotion.

For example, Argo Rollouts can pause a canary deployment while analysis evaluates metrics from a monitoring system such as Prometheus.

A rollout might proceed only if the error rate stays below a configured threshold. If the analysis fails, the rollout can be aborted.

When should you use it?

  • When deployments need automated safety checks.
  • When you want to reduce reliance on manual monitoring.
  • When you deploy frequently and want consistent release procedures.
  • When you can define meaningful health and performance metrics.

Trade-off: Progressive delivery requires trustworthy metrics and carefully designed promotion rules. Poorly chosen thresholds can either block healthy releases or allow problematic ones to proceed.

7. Shadow Deployment

A shadow deployment sends copies of production requests to a new application version while continuing to return responses from the stable version to users.

Unlike a canary deployment, the new version does not normally serve its response as the actual response to the user. 

                  +--> v1 (stable) --> Response to user
Production request |
                  +--> v2 (shadow) --> Response discarded
                                         |
                                         v
                                   Compare results

How does it work?

  1. Keep v1 serving real production traffic.
  2. Duplicate selected production requests and send them to v2.
  3. Capture the new version's results and performance.
  4. Compare the behavior of v1 and v2.
  5. Use the findings to fix problems before a real rollout.

How do you implement it?

You need a mechanism that can mirror traffic to the new version. This might be a reverse proxy, an ingress controller, or a service mesh with traffic-mirroring support.

Kubernetes can run both versions, but it does not automatically duplicate production requests to the shadow version.

When should you use it?

  • When replacing a critical service implementation.
  • When comparing query performance or response generation.
  • When testing a new version against realistic request patterns.
  • When you want to find compatibility issues before serving real responses.

Trade-off: Shadow traffic consumes additional resources. Mirrored requests must not cause unintended side effects, such as duplicate payments, emails, database writes, or external API calls. Sensitive request data must also be handled appropriately.

8. A/B Testing

A/B testing compares two or more variants to determine which performs better against a defined objective.

For example, an e-commerce application might test two checkout flows to see which results in more completed purchases. 

Users
  |
  v
Experiment assignment
  |
  +---- Group A ----> Checkout A
  |
  +---- Group B ----> Checkout B
                         |
                         v
                 Measure outcomes

How does it work?

  1. Define a hypothesis and a measurable success metric.
  2. Assign eligible users to different variants.
  3. Keep each user's assignment consistent throughout the experiment.
  4. Collect data about outcomes such as conversion rate.
  5. Analyze the results before deciding which variant to adopt.

How do you implement it?

You can use a feature-flag or experimentation platform to assign users to variants and record experiment exposure. The application then serves the assigned variant. 

$variant = $experimentService->getVariant(
    experiment: 'checkout_experiment',
    userId: $user->getId()
);

if ($variant === 'B') {
    return $checkoutB->handle($request);
}

return $checkoutA->handle($request);

The exact implementation depends on the experimentation system. A production experiment should also track exposure, avoid inconsistent assignments, and account for the possibility that other changes affect the results.

Can you combine A/B testing with a canary deployment?

Yes, but they answer different questions.

  • Canary: Is the new version safe and technically healthy?
  • A/B testing: Which variant produces better user or business outcomes?

A canary may expose a small portion of traffic to a new version to validate its health. Once it is stable, an experiment can compare different user experiences.

When should you use it?

  • When evaluating alternative user interfaces or workflows.
  • When measuring conversion, engagement, or retention.
  • When a product decision can be informed by controlled experiments.

Trade-off: A/B testing requires enough observations to draw meaningful conclusions. You must also avoid biased assignment, premature conclusions, and overlapping experiments that make results difficult to interpret.

9. Immutable Deployments

An immutable deployment replaces existing application instances with new instances instead of modifying the running instances in place.

The principle is to build a known artifact and deploy that artifact consistently. If the application needs to change, build a new artifact rather than manually modifying the old one. 

Build image v1
      |
      v
Deploy image v1
      |
      v
Build image v2
      |
      v
Create new instances using v2
      |
      v
Remove old instances using v1

How do you implement it?

A common approach is to build a versioned container image in the CI pipeline and deploy it to Kubernetes. 

# Build a versioned image
docker build -t my-app:abc123 .

# Push it to a container registry
docker push my-app:abc123

# Deploy the exact image
kubectl set image deployment/my-app \
  app=my-app:abc123

Here, abc123 represents a version identifier, such as a commit SHA. In a production pipeline, the image should be built, tested, and published before deployment.

For stronger artifact integrity, teams often deploy by immutable image digest rather than relying only on a mutable tag.

Is immutable deployment the same as rolling deployment?

No. They describe different aspects of deployment.

  • Immutable deployment: Describes how application instances and artifacts are managed.
  • Rolling deployment: Describes how the old instances are replaced by new instances.

You can use immutable application images with a rolling deployment, a blue-green deployment, or a canary deployment.

When should you use it?

  • When you want reproducible application releases.
  • When you want to avoid configuration drift between instances.
  • When you need to identify exactly which artifact is running.
  • When you want predictable recovery and easier debugging.

Trade-off: Immutable deployments still require careful configuration, secret management, image retention, and compatibility between application versions and their dependencies.

10. Comparing the Strategies

Strategy             Main purpose
-------------------------------------------------------
Rolling              Gradually replace application instances
Blue-green           Switch between separate environments
Canary               Gradually expose production traffic
Feature flags        Control feature availability
Progressive delivery Automate safe, gradual releases
Shadow               Test using mirrored production traffic
A/B testing          Compare user or product outcomes
Immutable            Replace instances using known artifacts

These strategies are not all mutually exclusive. Some define how instances are replaced, others define how traffic is routed, and others control which features users can access.

Important differences

  • Rollback: Blue-green deployments can make traffic switching back straightforward. Rolling and canary deployments can also roll back, but recovery depends on the deployment tooling and the state of the application and database.
  • Infrastructure cost: Blue-green deployments may require two full environments. Canary deployments need capacity for both versions, while rolling deployments often need less additional capacity.
  • Traffic control: Standard Kubernetes Deployments support rolling updates, but percentage-based canary traffic and shadow traffic require additional routing capabilities.
  • Business measurement: A/B testing focuses on outcomes such as conversion, rather than merely whether the deployment is technically healthy.

11. What Tools Do You Actually Need?

You do not need a separate tool for every strategy. The tools depend on the infrastructure and release requirements.

CI/CD pipeline

Tools such as GitHub Actions, GitLab CI, and Jenkins can build application artifacts, run tests, publish images, and initiate deployments.

A CI/CD pipeline automates the release process, but it does not automatically provide every traffic-routing or release-control capability.

Kubernetes

Kubernetes provides the foundation for running containerized applications. Its Deployment resource supports rolling updates, readiness checks, and rollout status.

You can also create separate Deployments and Services to support blue-green releases. More sophisticated traffic routing requires suitable networking components or additional tools.

Argo Rollouts

Argo Rollouts extends Kubernetes deployment capabilities with strategies such as canary and blue-green releases, along with pauses, analysis, and promotion controls.

Monitoring

Tools such as Prometheus and Grafana can help you observe application health, error rates, latency, and resource usage. These metrics can support automated promotion and rollback decisions when integrated with a rollout controller.

Feature-flag and experimentation tools

Feature-flag platforms manage feature availability independently of application deployments. Some also support percentage-based rollouts, user targeting, and A/B experiments.

Remember that feature flags and traffic routing solve different problems: a traffic router chooses an application instance, while a feature flag determines which functionality the application exposes.

12. A Real-World Example

Imagine you are deploying a new checkout service. The existing version handles payments correctly, but you have rewritten the checkout flow to support a new payment method.

A possible release process could look like this:

  1. Build an immutable artifact: The CI pipeline tests the code and publishes a versioned container image.
  2. Deploy a canary: Kubernetes runs the new version alongside the stable version. A traffic router sends a small percentage of requests to it.
  3. Monitor health: The team checks errors, latency, and payment-processing metrics.
  4. Control the feature: A feature flag keeps the new payment method disabled until the team is ready to expose it.
  5. Evaluate the product change: An A/B experiment compares eligible checkout variants using appropriate business metrics.
  6. Recover if needed: If the new version causes problems, stop the rollout and return traffic to the stable version. Disable the feature flag if the issue is specific to the new functionality.

Not every application needs all these techniques. For a small service, a rolling deployment with good health checks may be sufficient. For a critical payment service, canary releases, strong monitoring, and controlled feature activation may provide additional safety.

13. Database Migrations and Backward Compatibility

One of the most important deployment problems occurs when old and new application versions run simultaneously.

Consider a database migration that renames a column from customer_name to name. The old version may still expect the original column while the new version expects the new one.

A safer approach is often the expand-and-contract pattern:

  1. Add the new column while keeping the old column.
  2. Deploy code that can work with the compatible schema.
  3. Backfill or synchronize the data as required.
  4. Move all application instances to the new implementation.
  5. Remove the old column only after no running code needs it.

The exact steps depend on the database and migration. You must also consider concurrent writes, data consistency, long-running transactions, and rollback requirements.

A successful application rollback does not necessarily mean that the database or external side effects have been rolled back.

14. Common Misconceptions

"Kubernetes supports every deployment strategy out of the box."

Kubernetes Deployments support rolling updates, but advanced canary traffic splitting, shadow traffic, and feature-flag management require additional capabilities or tooling.

"Blue-green and canary are the same."

Blue-green switches between separate environments. Canary gradually exposes production traffic to the new version.

"Feature flags are deployment strategies."

Feature flags control functionality independently of deployment. They can complement many deployment strategies.

"A rollback always restores the previous state."

Rolling back application code does not automatically reverse database migrations, completed payments, published events, or other irreversible side effects.

"A healthy deployment means the feature is successful."

Monitoring can tell you whether a release is technically healthy. A/B testing and product analytics can help determine whether a feature achieves its intended outcome.

15. A Practical Learning Path

If you want to learn these techniques hands-on, start with the simplest workflow and gradually introduce more advanced release controls.

  1. Start with rolling deployments. Deploy two versions of a small application to Kubernetes. Inspect Pods, readiness, rollout status, and rollback behavior.
  2. Implement blue-green deployment. Run two Deployments and switch a Service between them.
  3. Explore canary releases. Install Argo Rollouts and configure a gradual rollout with a compatible traffic router.
  4. Add monitoring. Track error rates and latency, and use the metrics to evaluate whether a rollout should continue.
  5. Implement a feature flag. Add a feature that can be enabled for a selected group of users without deploying new application code.
  6. Explore shadow traffic and A/B testing. Compare application behavior and product outcomes while ensuring that experiments do not cause unintended production side effects.

16. Deployment Strategies Checklist

  • Can the old and new application versions run simultaneously?
  • Are readiness checks configured correctly?
  • Can the team detect increased errors and latency?
  • Is traffic routing configured for the intended rollout strategy?
  • Is rollback possible without losing important data?
  • Are database migrations compatible with both versions?
  • Are external side effects safe during retries or mirrored requests?
  • Are container images versioned and reproducible?
  • Are feature flags monitored and removed when no longer needed?
  • Are A/B experiments measured against a clearly defined objective?
  • Has the team tested the recovery procedure before relying on it?

Final Thought

Deployment strategies are about managing the risk of changing a running system. Some techniques control how application instances are replaced, others control which traffic reaches a version, and others control which features users can access.

Kubernetes provides a foundation for running and updating applications, while CI/CD pipelines, traffic routers, monitoring systems, and feature-flag platforms provide additional release capabilities.

The most useful mindset is: understand what each strategy controls, choose the simplest approach that meets your reliability requirements, and make sure you can detect and recover from failures.
