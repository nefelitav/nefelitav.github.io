API Best Practices

30 September 2026

Good API design is about creating an interface that is predictable, consistent, secure and easy to use.

A useful principle is: design APIs around resources and intent, not implementation details.

1. Resource & URL Design

Use nouns for resources rather than actions.

GET /customers
GET /customers/123

Use path parameters for specific resources and query parameters for filtering, sorting and pagination. 

GET /users/123
GET /users?status=active&page=2

Have a clear versioning and deprecation strategy for breaking changes.

2. HTTP Semantics

Use HTTP methods according to their intended purpose:

  • GET — retrieve data
  • POST — create or perform an operation
  • PUT — replace a resource
  • PATCH — partially update a resource
  • DELETE — remove a resource

Use meaningful HTTP status codes:

  • 200 — OK
  • 201 — Created
  • 204 — No Content
  • 400 — Bad Request
  • 401 — Unauthorized
  • 403 — Forbidden
  • 404 — Not Found
  • 409 — Conflict
  • 422 — Unprocessable Content
  • 429 — Too Many Requests
  • 500 — Internal Server Error

Understand idempotency, especially for important operations such as payments. Idempotency keys can prevent duplicate operations when requests are retried.

3. Requests & Responses

  • Validate all external input.
  • Return consistent and useful error responses.
  • Never expose internal implementation details.
  • Paginate large collections.
  • Support filtering and sorting.
  • Consider bulk operations when appropriate.
{
    "error": {
        "code": "INVALID_EMAIL",
        "message": "The email address is invalid.",
        "field": "email"
    }
}

4. Security

  • Authentication answers "Who are you?"
  • Authorization answers "What are you allowed to do?"
  • Never trust client-side validation.
  • Keep sensitive information out of URLs.
  • Enforce security rules server-side.
  • Use rate limiting where appropriate.

5. Reliability

  • Set timeouts for external calls.
  • Retry temporary failures carefully.
  • Use exponential backoff and jitter.
  • Avoid blindly retrying non-idempotent operations.
  • Consider concurrency and race conditions.

6. API Evolution

Try to avoid breaking existing clients.

Be careful when:

  • Removing or renaming fields
  • Changing field types
  • Changing enum values
  • Making optional fields required
  • Changing the meaning of existing values

Use API contracts and schemas such as OpenAPI, and have a clear deprecation strategy.

7. Observability

Make APIs easy to understand and debug in production.

  • Logs — what happened?
  • Metrics — how often and how much?
  • Traces — where did the request go?
  • Request IDs — connect logs across services.

8. Asynchronous APIs

Long-running or event-driven operations don't always need to complete during the original HTTP request.

Common approaches include:

  • Webhooks
  • Queues
  • Asynchronous jobs
POST /reports

→ 202 Accepted

{
    "job_id": "123",
    "status": "processing"
}

Reliable webhooks should consider signatures, retries, duplicate events, ordering and idempotency.

9. Caching

Caching can reduce latency and server load, but requires careful consideration of data freshness and invalidation.

  • Cache-Control
  • ETag
  • Last-Modified
  • If-None-Match

10. Documentation

Good API documentation should explain:

  • Authentication
  • Endpoints
  • Parameters
  • Request and response examples
  • Errors
  • Pagination
  • Rate limits
  • Webhooks
  • Versioning and deprecations

Tools such as OpenAPI can help keep the API contract and documentation aligned.

API Design Checklist

  • Are endpoints predictable and resource-oriented?
  • Are HTTP methods and status codes used correctly?
  • Is input validated and are errors consistent?
  • Are large collections paginated?
  • Are authentication and authorization enforced server-side?
  • Are timeouts and safe retries configured?
  • Is the API backwards compatible?
  • Is the API contract documented?
  • Can requests be traced through the system?
  • Are asynchronous operations handled appropriately?

Final Thought

Good API design ultimately makes an API predictable. Developers should be able to use an API without needing to understand how the underlying system is implemented.
