Database Normalization

8 October 2026

Database normalization is a set of principles for structuring relational data in a way that reduces unnecessary duplication and keeps data consistent.

The goal is not simply to create more tables. A useful principle is: store each piece of information in the right place and represent relationships explicitly.

1. The Problem: Duplicated Data

Imagine storing orders like this: 

orders
| order_id | customer_name | customer_email                                | product               |
| -------- | ------------- | --------------------------------------------- | --------------------- |
| 1        | Alice         | [alice@example.com](mailto:alice@example.com) | Laptop                |
| 2        | Alice         | [alice@example.com](mailto:alice@example.com) | Mouse                 |
| 3        | Bob           | [bob@example.com](mailto:bob@example.com)     | Keyboard              |

Alice's information is repeated for every order she makes.

This creates a problem when her email address changes. We now need to update multiple rows.

If only some rows are updated, the database can contain contradictory information.

2. Normalization

Instead, we can separate customers from orders: 

customers
| id | name  | email                                                  |
| -- | ----- | ------------------------------------------------------ |
| 1  | Alice | [alice@example.com](mailto:alice@example.com)          |
| 2  | Bob   | [bob@example.com](mailto:bob@example.com)              |

orders
| id | customer_id | product               |
| -- | ----------- | --------------------- |
| 1  | 1           | Laptop                |
| 2  | 1           | Mouse                 |
| 3  | 2           | Keyboard              |

The order stores the customer's ID rather than duplicating the customer's information. 

orders.customer_id
    │
    ↓
customers.id

This relationship is usually represented using a foreign key.

3. Why Normalize?

Normalization helps prevent several types of data problems.

  • Unnecessary duplication
  • Inconsistent data
  • Difficult updates
  • Accidental data loss
  • Unclear relationships

These problems are often described as update, insert and delete anomalies.

4. First Normal Form — 1NF

First Normal Form is commonly described using two important ideas:

  • Each column contains atomic values.
  • There are no repeating groups of values in a column.

For example, avoid: 

users
| id | name  | phone_numbers               |
| -- | ----- | --------------------------- |
| 1  | Alice | 123456, 987654              |

Instead, phone numbers could be represented separately: 

user_phone_numbers
| user_id | phone_number        |
| ------- | ------------------- |
| 1       | 123456              |
| 1       | 987654              |

This allows each phone number to be represented as an individual value.

5. Second Normal Form — 2NF

Second Normal Form builds on 1NF.

A table is in 2NF when it is in 1NF and every non-key attribute depends on the whole primary key, rather than only part of it.

This becomes especially important when a table has a composite primary key.

Consider: 

order_items
| order_id | product_id | order_date | product_name       |
| -------- | ---------- | ---------- | ------------------ |
| 1        | 10         | 2026-10-08 | Laptop             |
| 1        | 20         | 2026-10-08 | Mouse              |

Suppose the primary key is: 

(order_id, product_id)

order_date depends only on order_id, not on the entire composite key.

product_name depends only on product_id.

These attributes therefore belong in separate tables.

6. Third Normal Form — 3NF

Third Normal Form builds further on 2NF.

A common way of describing 3NF is: non-key attributes should depend on the key, the whole key, and nothing but the key.

Consider: 

employees

| employee_id | department_id | department_name      |
| ----------- | ------------- | -------------------- |
| 1           | 10            | Engineering          |
| 2           | 10            | Engineering          |
| 3           | 20            | Finance              |

department_name does not really depend on employee_id.

It depends on department_id. 

employee_id
 ↓
department_id
↓
department_name

This is a transitive dependency.

A normalized design would separate the departments: 

departments

| id | name                 |
| -- | -------------------- |
| 10 | Engineering          |
| 20 | Finance              |

employees

| id | department_id   |
| -- | --------------- |
| 1  | 10              |
| 2  | 10              |
| 3  | 20              |

7. Primary Keys

A normalized relational design usually needs a clear way to identify each row. 

CREATE TABLE customers (
id BIGINT PRIMARY KEY,
name VARCHAR(255),
email VARCHAR(255)


);

The primary key uniquely identifies a customer.

Other tables can reference it: 

CREATE TABLE orders (
id BIGINT PRIMARY KEY,
customer_id BIGINT,
FOREIGN KEY (customer_id)
    REFERENCES customers(id)


);

8. Relationships

Normalized databases represent relationships explicitly.

One-to-One

user
│
│ 1
↓
profile
│
│ 1

One-to-Many

customer
│
│ 1
↓
orders
│
│ many

A customer can have many orders.

Many-to-Many

Many-to-many relationships are usually represented using a junction table. 

students
│
↓
student_courses
↑
│
courses

For example: 

student_courses
| student_id | course_id       |
| ---------- | --------------- |
| 1          | 10              |
| 1          | 20              |
| 2          | 10
|

9. Normalization vs Denormalization

Normalization is not always the final answer.

Sometimes we intentionally duplicate data to improve read performance.

This is called denormalization.

For example, instead of joining several tables every time we display an order: 

orders
↓
customers
↓
addresses

we might store some frequently accessed information directly on the order. 

orders
| id | customer_id | customer_name | shipping_country         |
| -- | ----------- | ------------- | ------------------------ |
| 1  | 100         | Alice         | Netherlands
|

This introduces duplication, but may reduce expensive joins for specific workloads.

10. Why Denormalize?

Denormalization can be useful when:

  • Read performance is critical.
  • The same data is repeatedly joined.
  • Queries are extremely frequent.
  • The duplicated value changes rarely.
  • A read-heavy system benefits from simpler queries.

But duplicated data introduces a new responsibility: keeping the copies consistent.

11. Normalization Is a Trade-off

Highly normalized data may require more joins: 

orders
↓
customers
↓
addresses
↓
countries

Denormalized data may require fewer joins but more duplicated data: 

orders
| id | customer_name | country         |
| -- | ------------- | --------------- |
| 1  | Alice         | NL              |
| 2  | Alice         | NL              |
| 3  | Bob           | GR
|

The right design depends on the workload and business requirements.

15. Normalization and Query Performance

Normalization itself does not automatically make a database faster or slower.

A normalized design may require joins, but those joins can often be made efficient using appropriate indexes. 

SELECT orders.*
FROM orders
JOIN customers
ON orders.customer_id = customers.id
WHERE customers.email = '[alice@example.com](mailto:alice@example.com)';

An index on the relevant columns can make this query efficient.

Database design and indexing therefore work together.

12. Normalization and Data Integrity

One of the biggest benefits of normalization is that there is usually a single authoritative location for a piece of data.

For example: 

customers
| id | email                                                      |
| -- | ---------------------------------------------------------- |
| 1  | [alice@example.com](mailto:alice@example.com)
|

If Alice changes her email, there is one row to update. 

UPDATE customers
SET email = '[new@example.com](mailto:new@example.com)'
WHERE id = 1;

All orders referencing customer 1 continue to refer to the same customer.

14. When Should You Normalize?

Normalization is generally a good starting point when:

  • Designing a new relational database.
  • Data is frequently updated.
  • Consistency is important.
  • The same information appears in many places.
  • Relationships between entities matter.

Start with a clean normalized model and introduce denormalization when there is a demonstrated reason.

18. Common Normalization Mistakes

  • Duplicating the same business data across many tables
  • Storing multiple values in a single column
  • Ignoring relationships between entities
  • Using strings instead of foreign keys for relationships
  • Putting attributes in the wrong table
  • Over-normalizing without considering query patterns
  • Denormalizing before measuring a real performance problem

Normalization Checklist

  • Does each table represent a clear entity or relationship?
  • Does every row have a clear primary key?
  • Are relationships represented using foreign keys?
  • Is the same information unnecessarily duplicated?
  • Can updating one piece of data leave inconsistent copies?
  • Are columns storing individual values rather than lists?
  • Do non-key attributes depend on the appropriate key?
  • Are many-to-many relationships represented explicitly?
  • Have normalization decisions considered actual query patterns?
  • If data is intentionally duplicated, is there a strategy for keeping it consistent?

Final Thought

Database normalization is fundamentally about organizing information so that each fact has a clear and authoritative place.

Normalization reduces duplication and makes changes safer, while denormalization can be introduced deliberately when performance or access patterns justify it.

The most useful mindset is: start with a correct data model, understand the access patterns, and denormalize only when there is a reason to.
