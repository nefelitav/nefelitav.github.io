Authentication: SSO vs OAuth vs OIDC vs SAML

15 October 2026

Authentication is about establishing who a user is. Authorization is about deciding what that user is allowed to do. In modern systems, several standards work together to make login and access delegation possible.

1. The Big Picture

  • SSO (Single Sign-On): lets a user authenticate once and access multiple applications without independently logging in to each one.
  • OAuth 2.0: lets an application obtain limited access to a resource on behalf of a user or as itself.
  • OIDC (OpenID Connect): adds an identity layer on top of OAuth 2.0 so an application can authenticate a user.
  • SAML: an XML-based standard for exchanging authentication and authorization-related assertions, commonly used for enterprise SSO.

These are not four competing solutions. SSO is a capability or experience, while OAuth, OIDC, and SAML are standards that can help implement identity and access flows.

2. SSO — Single Sign-On

Imagine your company uses an internal dashboard, a ticketing tool, and a documentation platform. Instead of signing in separately to each application, you sign in through a central identity provider (IdP), and the other applications trust that provider.

Employee
   |
   v
Identity Provider
   |
   +----> Dashboard
   |
   +----> Ticketing Tool
   |
   +----> Documentation

Typical flow

  1. The user opens an application.
  2. The application redirects the user to the identity provider if authentication is needed.
  3. The user authenticates with the provider.
  4. The provider establishes an authenticated session and returns the user to the application with an appropriate response.
  5. The application validates the response and establishes its own session.

The exact flow depends on the protocol. The application does not simply trust arbitrary user-supplied identity information.

When to use SSO

  • Employees access multiple company applications.
  • A SaaS product offers enterprise login through a customer's identity provider.
  • An organization wants centralized account policies and easier account deactivation.

3. OAuth 2.0 — Delegated Authorization

OAuth 2.0 is primarily an authorization framework. It allows a client application to obtain an access token with specific permissions to access a resource.

For example, a calendar application wants permission to read your calendar without asking for your password.

Calendar App
    |
    | Requests permission
    v
Authorization Server
    |
    | Issues access token
    v
Calendar App
    |
    | Authorization: Bearer <access_token>
    v
Calendar API

Example request

GET /api/events HTTP/1.1
Host: calendar.example.com
Authorization: Bearer eyJ...

The access token represents granted access. The API validates it and checks whether it permits the requested operation.

Important OAuth concepts

  • Access token: credential used to access a protected resource.
  • Scope: describes the permissions requested or granted, such as calendar.read.
  • Authorization server: issues tokens after the relevant authorization flow.
  • Resource server: API that accepts and validates access tokens.
  • Refresh token: may be used to obtain new access tokens without repeating the full authorization interaction.

For user-facing applications, Authorization Code Flow with PKCE is generally the recommended starting point. Avoid the old implicit flow and never collect a user's third-party password to obtain access to another service.

4. OIDC — OpenID Connect

OIDC builds on OAuth 2.0 and adds a standardized way for a client to verify a user's identity.

OAuth access tokens are for accessing resources; they should not automatically be treated as proof of a user's identity. OIDC introduces the ID token for that identity purpose.

Example ID token claims

{
  "iss": "https://identity.example.com",
  "sub": "user_123",
  "aud": "my-application",
  "exp": 1792000000
}
  • iss: the issuer of the token.
  • sub: the subject identifier for the user.
  • aud: the intended audience.
  • exp: the expiration time.

These claims are illustrative. A real client must validate the token's signature and relevant claims, including issuer, audience, and expiration, according to the OIDC specification.

Typical OIDC login

  1. The application redirects the user to an identity provider.
  2. The user authenticates and grants any required consent.
  3. The application receives an authorization code.
  4. The application exchanges the code for tokens.
  5. The client validates the ID token and establishes a login session.

When to use OIDC

  • Adding "Sign in with Google" or another identity provider.
  • Enterprise login when the identity provider supports OIDC.
  • Authenticating users across web and mobile applications.

5. SAML — Enterprise Identity Federation

SAML is an XML-based standard widely used for enterprise SSO. It allows an identity provider to issue a signed assertion about an authenticated user to a service provider.

  • Identity Provider (IdP): authenticates the user and issues a SAML response.
  • Service Provider (SP): application that relies on the validated response.
  • SAML assertion: contains statements about the user and authentication.

Typical flow

User -> Service Provider
          |
          | Redirect to IdP
          v
     Identity Provider
          |
          | User authenticates
          v
     SAML Response
          |
          v
     Service Provider
          |
          v
     Application Session

The SAML response is commonly returned through the browser to the service provider. The service provider validates the response, including its signature, audience, destination, and time constraints, before creating a session.

When to use SAML

  • Integrating a SaaS application with enterprise identity systems.
  • Supporting organizations whose existing SSO configuration is SAML-based.
  • Integrating with established enterprise applications that require SAML.

SAML is not inherently insecure or obsolete. OIDC is often simpler for modern application development, but SAML remains important for enterprise interoperability.

7. Common Misconceptions

  • "OAuth is a login protocol." OAuth is primarily for authorization. OIDC adds a standardized identity layer.
  • "SSO is a protocol." SSO is a capability that can be implemented using protocols such as SAML or OIDC.
  • "An access token and an ID token are interchangeable." They serve different purposes and have different intended audiences.
  • "JWT means OAuth." JWT is a token format. It can be used in many contexts and is not synonymous with OAuth.
  • "SAML is always the best enterprise option." Choose based on the identity provider and integration requirements; many support both SAML and OIDC.

8. What Should I Remember?

  • SSO: sign in once to access multiple applications.
  • OAuth 2.0: delegate access to protected resources.
  • OIDC: standardize user authentication on top of OAuth 2.0.
  • SAML: exchange XML-based identity assertions, often for enterprise SSO.

For a new application that needs user login through an identity provider, I'd generally start by evaluating OIDC. If a customer's enterprise system requires SAML, support SAML for that integration.
