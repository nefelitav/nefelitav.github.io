Cookies vs Local Storage vs Session Storage

15 October 2026

Web applications need to remember information between page loads and requests. Browsers offer cookies, local storage, and session storage, but they have different behaviors and security implications.

2. Cookies

Cookies are small pieces of data stored by the browser and sent automatically with matching HTTP requests according to their domain, path, security, and SameSite rules.

Example

Set-Cookie: session_id=abc123; Path=/; HttpOnly; Secure; SameSite=Lax

On a later request, the browser may send:

Cookie: session_id=abc123

The backend can use this session identifier to find the authenticated user's server-side session.

Important cookie attributes

  • HttpOnly: prevents ordinary JavaScript from reading the cookie.
  • Secure: instructs the browser to send it only over HTTPS, except for special localhost behavior.
  • SameSite: controls cross-site sending behavior and helps mitigate CSRF.
  • Expires / Max-Age: determine persistence and lifetime.
  • Domain / Path: restrict where the cookie applies. Omitting Domain creates a host-only cookie.

Advantages

  • Automatically sent with matching requests.
  • HttpOnly can protect session credentials from direct JavaScript reads.
  • Useful for browser-based session authentication.

Trade-offs

  • Cookies take up space on HTTP requests when they match.
  • Automatically sent credentials introduce CSRF considerations.
  • Domain, path, SameSite, and expiration behavior must be configured correctly.

3. Local Storage

Local storage is a browser key-value store. Data persists across page reloads and browser restarts until the application or user clears it.

// Save a preference
localStorage.setItem("theme", "dark");

// Read it
const theme = localStorage.getItem("theme");

// Remove it
localStorage.removeItem("theme");

When to use it

  • Theme and display preferences.
  • Non-sensitive UI settings.
  • Small amounts of client-side state that should persist across visits.

Security concern

Any JavaScript running in the same origin can generally read local storage. If an attacker exploits cross-site scripting (XSS), they may be able to steal a token stored there. Avoid storing long-lived sensitive credentials in local storage unless you have carefully considered the threat model.

4. Session Storage

Session storage works similarly to local storage, but it is scoped to an individual page session, generally associated with a browser tab. It is cleared when that tab's page session ends.

// Save temporary state
sessionStorage.setItem("checkoutStep", "payment");

// Read it
const step = sessionStorage.getItem("checkoutStep");

// Remove it
sessionStorage.removeItem("checkoutStep");

When to use it

  • Temporary multi-step form state.
  • Per-tab navigation state.
  • Short-lived UI information that should not persist across separate tab sessions.

Session storage is still accessible to JavaScript. Its shorter lifetime does not make it a secure vault for authentication secrets.

5. XSS vs CSRF

XSS — Cross-Site Scripting

XSS occurs when an attacker can cause malicious JavaScript to run in your application's origin.

  • JavaScript-accessible local storage and session storage can be read by injected scripts.
  • HttpOnly cookies cannot ordinarily be read directly by JavaScript.
  • HttpOnly does not prevent malicious JavaScript from making authenticated requests through the victim's browser.

CSRF — Cross-Site Request Forgery

CSRF tricks a browser into making an unwanted request to a site where the browser has credentials. Cookies can be attached automatically, which is why cookie-based authentication needs CSRF-aware design.

  • Use appropriate SameSite cookie settings.
  • For sensitive operations, use CSRF tokens or another suitable defense when required by your architecture.
  • Validate request origins where appropriate and never rely on CORS alone as a general CSRF defense.

6. Where Should I Store Authentication Credentials?

There is no single answer for every architecture, but for a conventional browser application backed by your own server, an HttpOnly, Secure session cookie is often a strong default.

The browser does not need to read the session identifier in JavaScript. It sends the cookie automatically when the request matches the cookie's rules.

For token-based architectures, decide where tokens should live based on the application's threat model. An in-memory token has different persistence trade-offs from local storage; a backend-for-frontend (BFF) can also keep OAuth tokens server-side and expose a browser session instead.

7. Common Misconceptions

  • "Cookies are always safer." Not automatically. Cookie attributes help, but CSRF and other risks still need to be addressed.
  • "Local storage is sent to the server automatically." No. Application code must read and send it.
  • "Session storage is safe for tokens because it disappears." It remains accessible to JavaScript and may be exposed by XSS.
  • "HttpOnly prevents XSS." It limits cookie reading; it does not prevent XSS itself.
  • "Cookies and JWTs are alternatives." A JWT can be stored in a cookie. Cookies are a storage and transport mechanism; JWT is a token format.

8. What Should I Remember?

  • Cookies: useful for credentials sent automatically with HTTP requests.
  • Local storage: persistent client-side storage for non-sensitive preferences and state.
  • Session storage: temporary per-tab state.
  • XSS: especially threatens data accessible to JavaScript.
  • CSRF: especially relevant when credentials are sent automatically by the browser.

Choose storage based on the data's sensitivity, required lifetime, and how the browser communicates with the backend. Do not choose a storage mechanism based on persistence alone.
