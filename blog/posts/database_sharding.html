Database Sharding

October 15, 2026

As an application grows, its database may eventually become too large or too busy for a single server. Adding more CPU and memory can help, but there are limits to how much a single machine can scale.

Database sharding addresses this problem by splitting a dataset across multiple database servers. Each server stores and manages only a portion of the data.

Let's explore how sharding works, how applications find the correct shard, and why this technique introduces additional complexity.

1. What Is Database Sharding?

Database sharding is a form of horizontal scaling in which data is distributed across multiple database instances. Each instance is called a shard.

Imagine a system that stores millions of users. Instead of storing every user in one database, we distribute users across several databases. 

Before sharding:

Application ──► Database
                 ├── User 1
                 ├── User 2
                 ├── User 3
                 ├── ...
                 └── User 1,000,000


After sharding:

                 ┌──► Shard 1: Users 1–333,333
Application ─────┼──► Shard 2: Users 333,334–666,666
                 └──► Shard 3: Users 666,667–1,000,000

Each shard is responsible for a subset of the dataset. Together, the shards hold the application's complete dataset.

The ranges above are just an illustration. In a real system, the distribution depends on the sharding strategy.

2. Why Use Sharding?

Horizontal scaling

Instead of relying on a single increasingly powerful database server, you can distribute data and workload across multiple servers.

Each shard can handle queries for its own data, allowing the system to increase its total storage and processing capacity as more shards are added.

Handling large datasets

A single database may eventually run into storage, memory, or maintenance constraints. Sharding distributes the dataset so that each server is responsible for a smaller portion.

Distributing workload

If requests can be routed directly to the appropriate shard, multiple database servers can process requests concurrently instead of sending every request to one server.

However, sharding does not automatically make every query faster. A query that needs data from every shard may actually become more expensive.

3. How Does Sharding Work?

The application needs a rule for deciding which shard stores a particular record. This rule is based on a shard key.

For example, suppose we shard users by their user ID. Whenever the application wants to retrieve a user, it uses that ID to determine which database contains the record. 

Request: Get user with ID 105

1. The application receives the user ID.
2. The sharding rule maps ID 105 to Shard 2.
3. The application queries Shard 2.
4. Shard 2 returns the user.

The application does not need to search every shard.

The routing logic can live in the application, a database proxy, a sharding middleware layer, or a database system that supports sharding.

The important point is that the application must know how to locate the data, either directly or through an infrastructure component.

4. What Is a Shard Key?

A shard key is the field or combination of fields used to determine where a record belongs.

Choosing the right shard key is one of the most important decisions in a sharded architecture because it affects data distribution, query performance, and scalability.

Example: Sharding by user ID

Shard 1: user_id 1, 4, 7, 10, ...
Shard 2: user_id 2, 5, 8, 11, ...
Shard 3: user_id 3, 6, 9, 12, ...

This is an illustrative distribution. A real system might use a hash function rather than assigning IDs in a repeating pattern.

What makes a good shard key?

  • Even distribution: Data and traffic should be spread reasonably evenly across shards.
  • Query compatibility: Frequently used queries should ideally include the shard key, allowing the application to target one shard.
  • Stable assignment: The key should not change frequently, because moving records between shards can be expensive.
  • Sufficient cardinality: The key should provide enough distinct values to distribute data effectively.

A poor shard key can create a hot shard: one database receives a disproportionate amount of traffic while other shards remain underutilized.

5. Common Sharding Strategies

Range-based sharding

Data is divided into ranges of the shard key. 

Shard 1: user_id 1–100,000
Shard 2: user_id 100,001–200,000
Shard 3: user_id 200,001–300,000

Advantages:

  • Easy to understand.
  • Range queries can often target a subset of shards.

Disadvantages:

  • Some ranges may contain much more data than others.
  • Sequential IDs can cause recent writes to concentrate on one shard.

Hash-based sharding

A hash function transforms the shard key into a value used to determine the destination shard. 

shard = hash(user_id) % number_of_shards

For example, with three shards, a hash-based rule distributes user IDs according to the hash result.

Advantages:

  • Can distribute data more evenly when the key and hash function are suitable.
  • Can reduce the hot-shard problem caused by sequential keys.

Disadvantages:

  • Range queries may need to access many shards.
  • Changing the number of shards can require substantial data movement if a simple modulo rule is used.

Systems may use consistent hashing or a partition map to reduce the amount of data that must move when capacity changes.

Directory-based sharding

A lookup service or directory stores the mapping between records or key ranges and their shards. 

Shard directory:

Tenant A ──► Shard 1
Tenant B ──► Shard 3
Tenant C ──► Shard 2

This allows the mapping to be changed without relying entirely on a fixed calculation.

The trade-off is that the directory itself must be reliable, fast, and kept consistent with the actual data placement.

6. Sharding vs. Replication vs. Partitioning

These concepts are related, but they solve different problems.

  • Sharding: Distributes different portions of a dataset across database instances.
  • Replication: Copies the same data to multiple database instances.
  • Partitioning: Divides a table or dataset into smaller pieces according to a rule. Those pieces may remain within one database server.
  • Read replicas: Replicated database instances used to serve read traffic. 
Sharding:

Shard 1: Users A, B
Shard 2: Users C, D


Replication:

Primary: Users A, B, C, D
Replica: Users A, B, C, D


Partitioning in one database:

Users table
    ├── Partition 1
    ├── Partition 2
    └── Partition 3

Sharding and partitioning are sometimes used as overlapping terms. In this blog, partitioning refers primarily to dividing data within a database, while sharding means distributing data across separate database instances.

A system can also partition data within each shard and replicate each shard for availability.

7. What Happens When You Add More Shards?

Adding a database server is not always as simple as creating an instance and sending it traffic.

If the sharding strategy depends on the number of servers, changing that number may change where records belong. Existing records might need to be moved.

For example, consider this rule:

shard = user_id % 3

If you change it to use four shards, many IDs will map to different destinations. 

Before: user_id % 3
After:  user_id % 4

Moving data while the application continues to read and write creates additional challenges. Systems may use consistent hashing, virtual shards, or a shard directory to make rebalancing easier.

A production migration needs a plan for moving data, routing requests, validating records, and avoiding lost or duplicated writes during the transition.

8. Challenges of Database Sharding

Cross-shard queries

A query that requires records from multiple shards may need to execute on each shard and combine the results. This is often called a scatter-gather query. 

SELECT COUNT(*)
FROM users
WHERE created_at >= '2026-01-01';

If the table is sharded by user ID, this query may need to inspect every shard because it does not specify the shard key.

Cross-shard transactions

Transactions involving records on different shards are more complicated. A normal local database transaction cannot automatically guarantee atomicity across independent database instances.

Distributed transactions are possible in some architectures, but they introduce additional coordination and availability trade-offs. Some applications instead redesign operations so that related records are colocated on the same shard.

Unique constraints and IDs

A unique constraint on one database does not automatically guarantee uniqueness across every shard. For example, independently generated auto-increment IDs may collide unless the design prevents it.

Applications may use globally unique identifiers, shard-aware ID generation, or a centralized allocation mechanism, depending on their requirements.

Operational complexity

You now need to monitor multiple databases, manage migrations, distribute backups, handle failover, and rebalance data when necessary.

Debugging can also become more difficult because a request may interact with multiple database instances.

9. When Should You Use Sharding?

Sharding may be appropriate when:

  • Your dataset exceeds the practical capacity of one database server.
  • Your write throughput cannot be handled by a single primary.
  • You need to distribute workload across multiple database instances.
  • You have a clear shard key that matches your access patterns.
  • Your team can operate and monitor a distributed database architecture.

When should you avoid it?

  • Your database can still scale vertically at a reasonable cost.
  • Query performance problems can be solved with better indexes or SQL.
  • Your workload frequently requires joins and transactions across unrelated data.
  • You do not have a clear way to distribute and rebalance data.

Sharding is powerful, but it is usually an architectural decision rather than the first performance optimization to try.

10. Real-World Example: A Multi-Tenant Application

Imagine a SaaS application used by thousands of businesses. Each business has users, invoices, and configuration data.

One possible approach is to shard by tenant ID. 

Tenant 101 ──► Shard 1
Tenant 202 ──► Shard 2
Tenant 303 ──► Shard 1
Tenant 404 ──► Shard 3

When the application loads invoices for Tenant 202, it routes the request to Shard 2.

This can work well because most operations are scoped to one tenant. Keeping a tenant's related data on the same shard may also simplify queries and transactions.

However, a very large tenant may overload its shard, and global reporting across all tenants may require queries across multiple shards or a separate analytical data store.

11. Summary

Database sharding distributes a dataset across multiple database instances, allowing a system to scale beyond the limits of a single server.

The key concepts to remember are:

  • Sharding splits data across database instances.
  • Shard keys determine where records are stored and are critical to query performance.
  • Range-based, hash-based, and directory-based sharding are common ways to distribute data.
  • Cross-shard queries and transactions introduce additional complexity.
  • Rebalancing must be considered when adding capacity or changing data placement.
  • Sharding is not the same as replication: one distributes different data, while the other copies data.

The goal is to distribute data in a way that matches how the application accesses it. A good shard key and a clear routing strategy can make sharding effective; a poor design can make even simple operations difficult.
