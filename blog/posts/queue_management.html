RabbitMQ vs Kafka vs Pub/Sub

15 October 2026

RabbitMQ, Apache Kafka, and Google Cloud Pub/Sub all enable asynchronous communication between services. Instead of one service waiting for another to finish its work, a producer publishes a message or event that consumers can process independently.

However, they are designed around different models:

  • RabbitMQ: a message broker focused on queues, flexible routing, acknowledgements, and task distribution.
  • Apache Kafka: a distributed event-streaming platform designed to store, distribute, and replay streams of events.
  • Google Cloud Pub/Sub: a fully managed messaging service for decoupled communication between applications, particularly useful in Google Cloud environments.

Understanding these differences helps you choose the right technology for background jobs, microservices, event-driven architectures, and data pipelines.

1. Why Do We Need Messaging Systems?

Imagine that an e-commerce application receives an order. After the order is placed, the system needs to send a confirmation email, update analytics, and notify the warehouse.

Without asynchronous messaging, the API might call every service directly.

Client
  |
  v
Order API
  |
  +----> Email Service
  |
  +----> Analytics Service
  |
  +----> Warehouse Service
  |
  v
Return Response

This creates several problems:

  • The API may need to wait for multiple services.
  • A slow downstream service can increase request latency.
  • A failing service can interfere with the order workflow.
  • Each service needs to know how to contact its dependencies.

With asynchronous messaging, the API publishes an event or message and lets independent consumers process the work.

Client
  |
  v
Order API
  |
  v
Messaging System
  |
  +----> Email Consumer
  |
  +----> Analytics Consumer
  |
  +----> Warehouse Consumer

The producer and consumers can now scale and fail independently to a greater extent. The exact guarantees depend on the messaging technology and its configuration.

2. Message Queue vs Event Stream vs Pub/Sub

Before comparing the products, distinguish the underlying messaging models.

Message queue

A queue holds work until a consumer processes it. Multiple workers can share the workload, so each message is normally assigned to one worker in a competing-consumer group.

Producer
   |
   v
  Queue
   |
   +----> Worker 1
   |
   +----> Worker 2
   |
   +----> Worker 3

For example, a queue can distribute 10,000 invoice-generation jobs across several workers.

Event stream

An event stream is an ordered, retained sequence of records. Consumers track their progress and can often read events again while they remain available.

Producer
   |
   v
Event Stream
   |
   +----> Billing Consumer
   |
   +----> Analytics Consumer
   |
   +----> Reporting Consumer

This is useful when different applications need to process the same events independently or replay historical data.

Publish/subscribe (Pub/Sub)

In the general publish/subscribe pattern, a publisher sends a message to a topic, and multiple subscribers can receive it.

The term describes a messaging pattern, not one specific technology. RabbitMQ can implement publish/subscribe through exchanges and queues, Kafka distributes topic events to consumer groups, and Google Cloud Pub/Sub implements topics and subscriptions.

3. RabbitMQ

RabbitMQ is a message broker. It receives messages from producers, routes them through exchanges, and delivers them to queues for consumers to process.

How RabbitMQ works

Producer
   |
   v
Exchange
   |
   | Routing rules
   |
   +----------+----------+
   |          |          |
   v          v          v
 Queue A    Queue B    Queue C
   |          |          |
   v          v          v
Worker A   Worker B   Worker C

The exchange determines where a message goes. Queues hold messages until they are delivered and acknowledged according to the configured behavior.

Exchange types

  • Direct exchange: routes messages using an exact routing-key match.
  • Topic exchange: routes using routing-key patterns, such as invoice.created or invoice.*.
  • Fanout exchange: broadcasts a message to all bound queues.
  • Headers exchange: routes messages according to message headers.

Example: background invoice generation

Suppose an application needs to generate invoices without making the API request wait for PDF creation.

API
 |
 | Publish GenerateInvoice
 v
RabbitMQ Queue
 |
 +----> Invoice Worker 1
 |
 +----> Invoice Worker 2
 |
 +----> Invoice Worker 3

The API publishes a job. A worker consumes it, generates the invoice, stores the result, and acknowledges the message after successful processing.

Important RabbitMQ features

  • Acknowledgements: consumers can acknowledge messages after processing them.
  • Publisher confirms: publishers can learn when the broker has accepted responsibility for published messages.
  • Routing: exchanges support flexible message distribution.
  • Dead-letter exchanges: can route messages that are rejected, expire, or otherwise meet configured dead-letter conditions.
  • Prefetch: limits outstanding deliveries to avoid overwhelming consumers.
  • Durable queues and persistent messages: can improve recovery after restarts when configured correctly.

When would you use RabbitMQ?

  • Background jobs and task processing.
  • Sending emails, generating PDFs, and processing files.
  • Routing commands to different workers.
  • Retrying failed work with appropriate queue and dead-letter configuration.
  • Microservice communication where acknowledgement and routing behavior matter.

Think of RabbitMQ when your primary question is: "How do I reliably route this job to a worker and know whether it has been processed?"

4. Apache Kafka

Apache Kafka is a distributed event-streaming platform. It stores events in topics and distributes them to consumers, allowing data to be processed in real time or replayed later.

How Kafka works

Producer
   |
   v
Kafka Topic
   |
   +----> Consumer Group A
   |        +-- Consumer 1
   |        +-- Consumer 2
   |
   +----> Consumer Group B
   |        +-- Consumer 1
   |
   +----> Consumer Group C

Each consumer group tracks its own progress. Different groups can independently consume the same topic, which makes Kafka suitable for event-driven architectures and data pipelines.

Topics and partitions

A Kafka topic is divided into partitions. Each partition is an ordered log of records, and consumers can read records using offsets.

Topic: orders
   |
   +----> Partition 0
   |        Event 1 -> Event 4 -> Event 7
   |
   +----> Partition 1
   |        Event 2 -> Event 5 -> Event 8
   |
   +----> Partition 2
            Event 3 -> Event 6 -> Event 9

Kafka guarantees ordering within a partition, not across every partition in a topic. Using a consistent message key, such as an order ID, can route related events to the same partition.

Retention and replay

Unlike a traditional queue, Kafka does not normally remove a record simply because one consumer has processed it. Records remain available according to the topic's retention and storage configuration.

This means a new consumer, or an existing consumer that resets its offset, can replay retained events.

Example: order events

Whenever an order changes, the application publishes an event to Kafka.

{
  "event": "OrderPaid",
  "orderId": "order-123",
  "amount": 49.99,
  "currency": "EUR"
}

Independent consumer groups can process the event:

  • Analytics: update sales dashboards.
  • Reporting: build reporting datasets.
  • Notifications: trigger customer communications.
  • Fraud detection: analyze transaction patterns.

Each group maintains its own progress and can process the same retained event independently.

Important Kafka features

  • Durable event retention: store events for a configured period or according to storage policies.
  • Partitions: scale throughput and distribute processing.
  • Consumer groups: divide partition processing among consumers in a group.
  • Replay: reprocess retained data by adjusting consumer offsets.
  • Replication: replicate partitions for fault tolerance when configured.
  • Stream processing: integrate with tools such as Kafka Streams and other data-processing systems.

When would you use Kafka?

  • High-volume event ingestion.
  • Central event streams shared by multiple applications.
  • Analytics and data pipelines.
  • Change data capture (CDC) and integration between systems.
  • Audit and business-event histories with appropriate retention.
  • Workloads where replay and independent consumer progress are important.

Think of Kafka when your primary question is: "How do I store and distribute an ongoing stream of events so multiple systems can process and replay it independently?"

5. Google Cloud Pub/Sub

Google Cloud Pub/Sub is a fully managed messaging service. Google operates the underlying infrastructure, allowing developers to publish and consume messages without managing their own broker cluster.

How Pub/Sub works

Publisher
    |
    v
   Topic
    |
    +----------+----------+
    |                     |
    v                     v
Subscription A       Subscription B
    |                     |
    v                     v
Worker Pool A         Analytics Service

Each subscription receives its own logical copy of messages published to the topic. Multiple subscriber instances attached to the same subscription share the work; they do not each receive every message independently.

Push vs pull subscriptions

  • Pull: the subscriber client requests messages and processes them.
  • Push: Pub/Sub sends messages to a configured HTTPS endpoint.

For pull subscriptions, subscribers acknowledge messages after processing them. Messages that are not acknowledged within the relevant deadline can be redelivered.

Example: order processing on Google Cloud

Order API
    |
    v
Pub/Sub Topic: orders
    |
    +----> Subscription: emails
    |             |
    |             v
    |        Email Worker
    |
    +----> Subscription: analytics
    |             |
    |             v
    |        Analytics Pipeline
    |
    +----> Subscription: fulfillment
                  |
                  v
             Fulfillment Worker

The order service publishes an event once. Pub/Sub distributes it to each subscription, allowing each downstream system to operate independently.

Important Pub/Sub features

  • Managed infrastructure: no self-managed broker cluster is required.
  • Independent subscriptions: different services can process the same published messages.
  • Push and pull delivery: support different consumer architectures.
  • Acknowledgements and redelivery: support reliable processing workflows.
  • Dead-letter topics: can isolate messages after configured delivery attempts, with the appropriate policy and permissions.
  • Optional ordering: ordering can be enabled for messages sharing an ordering key, subject to service constraints.
  • Integration with Google Cloud: works with services such as Dataflow, BigQuery, and Cloud Run.

When would you use Pub/Sub?

  • Event-driven applications hosted on Google Cloud.
  • Decoupling independently deployed services.
  • Distributing events to several downstream systems.
  • Cloud-native background processing.
  • Ingesting events into analytics and data-processing pipelines.
  • Messaging workloads where managed infrastructure is preferable to operating brokers.

Think of Pub/Sub when your primary question is: "How can I distribute messages reliably without operating my own messaging infrastructure?"

7. Delivery Guarantees: At-Most-Once, At-Least-Once, and Exactly-Once

Understanding delivery semantics is essential when building asynchronous systems.

At-most-once

A message is delivered zero or one times. It will not be redelivered, but it can be lost if a failure occurs.

At-least-once

A message is retried until it is acknowledged or another terminal policy applies. It can be delivered more than once.

This is common in reliable messaging systems. Consumers should be designed to tolerate duplicate processing.

Exactly-once

The term depends on the system and the scope of the guarantee. Kafka supports exactly-once processing capabilities for particular Kafka workflows, and Google Cloud Pub/Sub offers an optional exactly-once delivery feature for supported pull subscriptions.

Neither feature automatically guarantees that an external side effect, such as charging a credit card or sending an email, happens exactly once. That requires appropriate application-level safeguards.

Example: duplicate invoice processing

A worker receives an invoice-generation message and creates the invoice. Before it acknowledges the message, the process crashes.

The messaging system may deliver the message again. Without protection, the worker might generate a duplicate invoice.

Possible safeguards include:

  • Use a stable business identifier or idempotency key.
  • Record completed processing in a database with a uniqueness constraint.
  • Make repeated operations safe.
  • Acknowledge only after the required processing has completed.
  • Use transactional outbox or inbox patterns when coordinating database changes and message delivery.

These patterns matter regardless of which messaging technology you choose.

8. Retries and Dead-Letter Queues

What happens when a consumer cannot process a message?

For example, an invoice worker might encounter a temporary database outage or a permanently invalid payload.

Retry

A retry attempts the operation again. Transient failures can succeed later, but repeatedly retrying a permanently invalid message wastes resources.

Dead-letter handling

A dead-letter queue or topic isolates messages that cannot be processed according to the configured policy. Operators can inspect them, fix the underlying issue, and replay them if appropriate.

Message
   |
   v
Consumer
   |
   +---- Success ----> Acknowledge
   |
   +---- Failure ----> Retry with backoff
                           |
                           v
                      Retry limit reached
                           |
                           v
                    Dead-letter destination

The implementation differs by platform:

  • RabbitMQ: queue dead-letter configuration and retry queues can route failed messages to a dead-letter exchange.
  • Kafka: consumers typically implement retry topics, retry handling, or a dead-letter topic as part of the application architecture.
  • Google Cloud Pub/Sub: a subscription can be configured with a dead-letter topic and a maximum delivery-attempt policy.

Retries should generally use backoff and have clear handling for permanent failures. Also consider poison messages, which repeatedly fail and can block progress or consume resources.

9. Which One Should You Choose?

Scenario A: Send emails asynchronously

Good fit: RabbitMQ or Google Cloud Pub/Sub.

Your API publishes an email job, and background workers process it. RabbitMQ is a natural choice for queue-based task distribution. Pub/Sub is attractive when your application already runs on Google Cloud and you prefer managed messaging.

Scenario B: Process millions of business events and replay them

Good fit: Kafka.

Multiple consumer groups need to independently process a retained history of events. Kafka's partitioned log and offset model make it a strong fit.

Scenario C: Route jobs according to business rules

Good fit: RabbitMQ.

You want to route different messages to different queues based on routing keys, message headers, or fanout behavior.

Scenario D: Build an event-driven application on Google Cloud

Good fit: Google Cloud Pub/Sub.

You want publishers and consumers to remain independent without managing a broker cluster. Managed operations and Google Cloud integrations may outweigh the need for more specialized broker behavior.

Scenario E: Build analytics and data pipelines

Good fit: Kafka or Google Cloud Pub/Sub.

Kafka is particularly attractive when you need retained event streams, replay, and partition-based processing. Pub/Sub is attractive when you want a managed ingestion and distribution service integrated with Google Cloud data tools.

Scenario F: Coordinate background processing between PHP services

Good fit: RabbitMQ or Google Cloud Pub/Sub, depending on your infrastructure.

For example, a billing service can publish an invoice-generation job and return without waiting for a worker to finish. The worker processes the message independently and records the result.

Kafka can also support asynchronous service workflows, especially when invoice events must be retained and consumed by multiple systems. However, it may be unnecessary if the only requirement is distributing simple background jobs.

10. Common Misconceptions

  • "Kafka is just a message queue." Kafka's retained, partitioned log and replay model are central to its design.
  • "RabbitMQ cannot do publish/subscribe." Exchanges and queues can implement publish/subscribe patterns.
  • "Pub/Sub is a generic name for one product." Publish/subscribe is a messaging pattern; Google Cloud Pub/Sub is one specific managed implementation.
  • "Every consumer receives every message." Multiple consumers on the same queue or subscription typically share work. Independent queues or subscriptions are needed for separate copies of the workload.
  • "Messages are always processed in order." Ordering depends on the technology, configuration, partitions or queues, and consumer concurrency.
  • "At-least-once means no messages are lost under every circumstance." Guarantees depend on publishing confirmation, durable configuration, acknowledgement behavior, retention, and failure handling.
  • "Exactly-once delivery means every business operation happens once." External side effects still require idempotency or transactional safeguards.
  • "The most scalable system is always the best." Operational complexity, delivery semantics, routing needs, and the team's existing infrastructure matter just as much.

11. What Should a Software Developer Learn First?

  1. Asynchronous communication: understand producers, consumers, queues, topics, and acknowledgements.
  2. Delivery semantics: learn at-most-once, at-least-once, duplicate delivery, and idempotency.
  3. Retries and failure handling: understand backoff, dead-letter destinations, and poison messages.
  4. RabbitMQ: learn exchanges, queues, bindings, routing keys, acknowledgements, and prefetch.
  5. Kafka: learn topics, partitions, offsets, consumer groups, retention, and replay.
  6. Google Cloud Pub/Sub: learn topics, subscriptions, push vs pull, acknowledgement deadlines, and dead-letter policies.
  7. Reliability patterns: study the transactional outbox, inbox/idempotency patterns, and how database transactions interact with messaging.

As a backend developer, the most important skill is not memorizing every broker feature. It is designing a workflow that remains correct when a service crashes, a message is duplicated, a consumer is slow, or a dependency is unavailable.

12. What Should I Remember?

  • RabbitMQ: choose it for queue-based work distribution, flexible routing, and broker-managed message delivery.
  • Kafka: choose it for durable event streams, replay, high-volume processing, and multiple independent consumers.
  • Google Cloud Pub/Sub: choose it for managed asynchronous messaging, especially in Google Cloud architectures.
  • All three: require thoughtful handling of acknowledgements, retries, ordering, duplicates, and failures.
  • Start with the workload: choose based on whether you need task processing, retained event streams, or managed cloud messaging.

The right messaging system is the one whose delivery model and operational characteristics match your application's needs. You rarely need all three in the same application unless different workloads justify the added complexity.
