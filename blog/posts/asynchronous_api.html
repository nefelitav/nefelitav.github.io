Synchronous vs Asynchronous APIs

30 September 2026

When designing an API, one of the first questions to answer is: does the client need to wait for the operation to finish?

In a synchronous API, the client sends a request and waits for the operation to complete. In an asynchronous API, the client starts an operation and can continue without waiting for the operation itself to finish.

The choice affects API design, error handling, retries, scalability, queues, webhooks and the overall user experience.

Synchronous APIs

A synchronous API follows the traditional request-response model: the client sends a request and waits for the server to return the result. 

Client ────── Request ──────► Server
Client ◄───── Response ────── Server
              waits

For example, retrieving a user is usually a synchronous operation: 

GET /users/123

The server processes the request and returns the result:

HTTP/1.1 200 OK
Content-Type: application/json

{
    "id": 123,
    "name": "Alice"
}

The client gets the result as part of the same interaction.

When is synchronous appropriate?

Synchronous APIs work well when the operation is relatively quick and the client needs the result immediately.

  • Fetching a resource
  • Updating a resource
  • Creating a simple resource
  • Validating data
  • Performing a short calculation

For example:

GET /customers/123

PUT /customers/123

POST /payments

Asynchronous APIs

An asynchronous API allows the client to start an operation without waiting for the operation itself to complete. 

Client ────── Request ──────► Server
Client ◄───── Accepted ────── Server

              ... work happens later ...

Worker ──────► Processing

This is useful when an operation can take a significant amount of time or does not need to produce its final result immediately.

For example, imagine an API that generates a large report. Generating the report could take several minutes. 

POST /reports

Instead of keeping the HTTP request open while the report is generated, the API can immediately respond: 

HTTP/1.1 202 Accepted
Content-Type: application/json

{
    "job_id": "job_123",
    "status": "processing"
}

The operation has been accepted, but it has not necessarily completed yet.

What Does 202 Accepted Mean?

202 Accepted is commonly used when an API has accepted a request for processing, but the processing has not necessarily completed.

This is different from:

  • 200 OK — the request was successfully processed and the response contains the result.
  • 201 Created — a resource was successfully created.
  • 202 Accepted — the request was accepted for processing, but the operation may still be running.

How Does the Client Get the Result?

Once an operation becomes asynchronous, the API needs a way for the client to find out what happened.

There are several common approaches.

1. Polling

The client periodically asks the server for the status of the operation. 

POST /reports

202 Accepted

{
    "job_id": "job_123",
    "status": "processing"
}

The client can then request:

GET /reports/job_123

While the operation is running:

{
    "status": "processing"
}

And eventually:

{
    "status": "completed",
    "download_url": "/reports/job_123/download"
}

Polling is simple and works well when clients can tolerate some delay between the operation completing and discovering the result.

2. Webhooks

Instead of the client repeatedly asking whether the operation has finished, the server can notify the client when something happens. 

Client
   │
   │ POST /reports
   ▼
Server
   │
   │ 202 Accepted
   ▼
Client

       ... later ...

Server ───── POST /webhooks/report-completed ─────► Client

The client provides a webhook endpoint, and the server sends a request to that endpoint when the operation completes.

Webhooks are especially useful when the client is another backend service that needs to react to an event.

3. Message Queues

Another common approach is to put the work onto a message queue and process it in the background. 

Client
   │
   ▼
API
   │
   ▼
Queue
   │
   ▼
Worker
   │
   ▼
Database

The API can acknowledge the request quickly while a worker processes the job independently.

Queues are useful when you need to handle large amounts of work, smooth out traffic spikes, retry failed processing, or scale workers independently from the API.

Asynchronous Does Not Mean "Using a Queue"

These concepts are related, but they are not the same thing.

An asynchronous API is about when the client receives the result. A queue is one possible implementation mechanism for processing work asynchronously.

An asynchronous workflow could use:

  • Polling
  • Webhooks
  • Message queues
  • Background workers
  • Event-driven processing

When Should You Use Asynchronous APIs?

Asynchronous processing is particularly useful when an operation:

  • Can take a long time to complete
  • Is computationally expensive
  • Processes a large amount of data
  • Does not require an immediate result
  • Can be processed in the background
  • Benefits from retries or independent workers

Examples might include:

Generate a large report
        ↓
Asynchronous

Process millions of transactions
        ↓
Asynchronous

Send an email
        ↓
Often asynchronous

Process an uploaded video
        ↓
Asynchronous

Fetch a customer
        ↓
Usually synchronous

Synchronous vs Asynchronous

Synchronous Asynchronous
Client waits for operation Yes No
Result immediately available Usually Not necessarily
Long-running operations Less suitable Well suited
Polling Usually unnecessary Sometimes used
Webhooks Usually unnecessary Common
Queues Not required Often used
Implementation complexity Lower Higher
Failure handling Relatively simple More involved

Retries and Idempotency

Asynchronous systems introduce additional failure scenarios. For example, a client might send a request and never receive the response because of a network failure.

The client may then retry the request. 

POST /payments

Idempotency-Key: abc123

An idempotency key allows the server to recognize that multiple requests represent the same operation.

This is particularly important for operations such as payments, where accidentally processing the same request twice could have serious consequences.

Other Challenges of Asynchronous Systems

Asynchronous processing provides flexibility and scalability, but it also introduces additional complexity.

  • Retries — what happens when processing fails?
  • Duplicate messages — can the same operation be processed twice?
  • Ordering — does the order of operations matter?
  • Timeouts — how long should an operation be allowed to run?
  • Dead-letter queues — where do repeatedly failing messages go?
  • Eventual consistency — when will all systems see the same state?
  • Backpressure — what happens when work arrives faster than it can be processed?

Choosing Between Them

A useful starting point is to ask whether the client actually needs the result before it can continue. 

Does the client need the result immediately?
            │
       ┌────┴────┐
      Yes        No
       │          │
       ▼          ▼
Synchronous   Consider
              asynchronous

This is not an absolute rule. A synchronous API can still be appropriate for an operation that takes some time, and an asynchronous API can be useful even for relatively quick operations when decoupling or background processing provides other benefits.

What Should I Remember?

  • Synchronous means the client waits for the operation's result.
  • Asynchronous means the client can continue without waiting for the operation itself to finish.
  • 202 Accepted is commonly used when work has been accepted but is not yet complete.
  • Polling, webhooks and queues are common ways to handle asynchronous workflows.
  • Asynchronous processing introduces additional concerns such as retries, duplicate processing, ordering and eventual consistency.
  • Idempotency becomes particularly important when requests or messages can be retried.
