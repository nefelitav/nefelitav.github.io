Webhooks, Queues & Events

30 September 2026

Webhooks, queues, Pub/Sub and events are common building blocks for asynchronous and distributed systems. They allow systems to communicate without requiring every operation to happen inside a single synchronous request.

Although these concepts are related, they solve different problems. Understanding the distinction is important when designing integrations and distributed systems.

The Big Picture

A useful way to think about them is:

  • Webhook — "Tell this specific system when something happens."
  • Queue — "Give this work to a consumer to process."
  • Pub/Sub — "Tell everyone interested that something happened."
  • Event — "Something happened."

These concepts can also be combined. For example, an event can be published through a Pub/Sub system, consumed by a service, and eventually delivered to another system through a webhook.

Webhooks

A webhook is an HTTP callback. Instead of a client repeatedly asking whether something has happened, a server sends an HTTP request to a URL provided by the client. 

Client                    Server
```

│                          │
│  POST /payments          │
├─────────────────────────►│
│                          │
│       200 OK              │
│◄─────────────────────────┤
│                          │
│                          │ payment completed
│                          │
│  POST /webhook            │
│◄─────────────────────────┤
│                          │
```

For example, a payment provider might notify a merchant when a payment changes status. 

POST /webhooks/payment
```

{
"event": "payment.completed",
"payment_id": "pay_123"
}
```

The merchant does not need to continuously poll the payment provider. The provider sends the notification when the event occurs.

Webhooks Are HTTP

A webhook is not a special transport protocol. It is usually just an HTTP request sent by one system to another. 

POST https://merchant.example.com/webhooks/payment

Because webhooks use HTTP, they inherit many of the same concerns as normal APIs:

  • Authentication
  • Authorization
  • Retries
  • Timeouts
  • Idempotency
  • Monitoring
  • Signature verification

Webhook Signatures

A webhook endpoint is often publicly reachable, so the receiving system needs a way to verify that the request actually came from the expected sender.

A common approach is to include a cryptographic signature. 

Webhook-Signature: t=1727683200,v1=abc123...

The receiver can calculate the expected signature using a shared secret and compare it with the signature sent by the provider.

This prevents an arbitrary client from simply sending a fake payment.completed request to the webhook endpoint.

Why Use a Queue?

Queues provide several useful properties.

Decoupling

The producer does not need to know exactly when or where the consumer will process the message.

Buffering

If 10,000 requests arrive at once but workers can only process 1,000 at a time, the queue can temporarily hold the remaining work. 

10,000 requests
   │
   ▼
 Queue
   │
   ├── Worker
   ├── Worker
   ├── Worker
   └── Worker

Retries

If processing fails, a message can often be retried rather than being lost immediately.

Scaling

Multiple workers can consume from the same queue. They can process different messages in parallel, allowing the system to scale horizontally. 

Queue
```

│
├── Worker 1
├── Worker 2
├── Worker 3
└── Worker 4
```

In this model, the workers are often called competing consumers: a particular message is generally processed by one of the available workers rather than by all of them.

Events

An event represents something that happened in a system.

For example: 

payment.created
```

payment.completed
invoice.generated
customer.updated
order.cancelled
```

An event describes a fact rather than a command.

Compare: 

CreatePayment

with: 

PaymentCreated

The first is a command: "Please create this payment."

The second is an event: "This payment was created."

A useful mental model is:

  • Queue: "Here is work. Someone process it."
  • Pub/Sub: "Something happened. Everyone interested can react."

Topics and Subscriptions

In many Pub/Sub systems, a topic and a subscription are separate concepts. 

                 PaymentCompleted
                  Topic
                    │
         ┌──────────┴──────────┐
         │                     │
   Subscription A        Subscription B
         │                     │
         ▼                     ▼
   Notification            Accounting

This allows each subscriber to have its own processing state, retry behavior and backlog.

For example, if the Accounting service is temporarily unavailable, its subscription can retain messages until the service is able to process them.

Event-Driven Architecture

In an event-driven architecture, systems communicate by producing and consuming events. 

Payment Service
  │
  │ PaymentCompleted
  ▼
```

Event Broker
│
├──────────────► Billing Service
│
├──────────────► Notification Service
│
└──────────────► Analytics Service
```

The payment service does not necessarily need to know that these other services exist.

Each consumer can independently decide whether it is interested in the event.

This can reduce coupling between services and make it easier to add new consumers.

Events, Queues and Pub/Sub Are Not the Same Thing

These concepts are related, but they describe different things.

  • An event describes what happened.
  • A queue describes a way of delivering work to consumers.
  • Pub/Sub describes a way of distributing messages to multiple subscribers.
  • A webhook is typically an HTTP request used to notify a specific external system.

Message Brokers

A message broker is infrastructure that receives, stores and delivers messages between producers and consumers. 

Producer
│
▼
```

┌──────────────┐
│    Broker    │
└──────────────┘
│
▼
Consumer
```

Message brokers can support different messaging patterns, including queues and Pub/Sub.

Common examples include RabbitMQ, Apache Kafka, Google Cloud Pub/Sub, Amazon SQS and Azure Service Bus. These technologies have different models and capabilities, so they should not be treated as interchangeable.

How They Can Work Together

These concepts are not alternatives that must always be chosen independently. A real system can use all of them.

└──────────► Webhook Service

```

For example:

  1. A payment is completed.
  2. The payment service publishes a PaymentCompleted event.
  3. The event is delivered through a messaging system.
  4. The billing service consumes it and creates an invoice.
  5. The webhook service sends a notification to the merchant.

Important Challenges

Distributed asynchronous systems introduce failure modes that do not usually exist in a simple synchronous request-response flow.

Duplicate Messages

A message may sometimes be delivered more than once. Consumers should therefore often be designed to handle duplicate processing safely.

Retries

Temporary failures should often trigger a retry. However, unlimited retries can make a problem worse.

Dead-Letter Queues

Messages that repeatedly fail can be moved to a dead-letter queue for investigation or later processing. 

Queue
```

│
├── success ─────► Consumer
│
└── repeated failure
│
▼
Dead-Letter Queue
```

Ordering

Sometimes the order of events matters. 

PaymentCreated
  ↓
```

PaymentAuthorized
↓
PaymentCompleted
```

Processing these events in the wrong order could produce an inconsistent state.

Idempotency

Consumers should often be able to process the same message more than once without producing an incorrect result.

What Should I Remember?

  • A webhook is typically an HTTP callback used to notify a specific system.
  • A queue is a messaging pattern for buffering and distributing work to consumers.
  • Pub/Sub is a messaging pattern for distributing messages to multiple independent subscribers.
  • An event represents something that happened.
  • A command asks a system to do something, while an event describes something that already happened.
  • Message brokers can implement or support different messaging patterns, including queues and Pub/Sub.
  • Webhooks, queues, Pub/Sub and events can be combined to build asynchronous, loosely coupled systems.
  • Retries, duplicates, ordering and idempotency are important considerations in distributed systems.
