NGINX, Reverse Proxies, Load Balancers and API Gateways

14 October 2026

When a client sends an HTTP request, it does not always communicate directly with the application that processes it. Requests often pass through infrastructure components responsible for routing traffic, distributing requests and controlling access to backend services.

Three important concepts are reverse proxies, load balancers and API gateways. They have overlapping responsibilities, but each emphasizes a different problem.

NGINX is a popular tool that can act as a reverse proxy and load balancer, while also providing features such as TLS termination, caching and rate limiting.

Understanding these components helps explain how applications scale, expose APIs and communicate with backend services.

1. The Big Picture

Imagine an application with a frontend, a payments service and a users service.

Instead of allowing clients to communicate directly with every backend service, we can introduce an entry point that receives incoming requests and forwards them to the appropriate destination. 

Client
  |
  v
Reverse Proxy / API Gateway
  |
  +----> Payments Service
  |
  +----> Users Service
  |
  +----> Orders Service

If the payments service has multiple instances, another concern appears: deciding which instance should receive each request. This is where load balancing becomes important. 

Client
  |
  v
Load Balancer
  |
  +----> Payments Instance 1
  |
  +----> Payments Instance 2
  |
  +----> Payments Instance 3

These responsibilities can be implemented by separate infrastructure components or combined in one product.

2. What Is a Reverse Proxy?

A reverse proxy is a server that receives requests from clients and forwards them to backend servers.

The client communicates with the proxy rather than needing to know the internal address of the backend. 

Client
  |
  v
Reverse Proxy
  |
  v
Backend Application

For example, a browser might send a request to: 

https://example.com/api/users

The reverse proxy forwards the request to an internal application: 

http://users-service:8080/api/users

The backend processes the request and returns a response through the proxy to the client.

Why use a reverse proxy?

  • Hide internal backend addresses from clients.
  • Provide a single entry point to multiple services.
  • Route requests based on hostnames or URL paths.
  • Terminate TLS connections.
  • Apply common request-handling rules.
  • Cache responses or limit request rates when appropriate.

Example: NGINX as a reverse proxy

server {
    listen 80;
    server_name example.com;

    location /api/ {
        proxy_pass http://localhost:8080;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

The location block matches requests beginning with /api/. The proxy_pass directive forwards them to the backend on port 8080.

The forwarding headers communicate information about the original request. For example, X-Forwarded-For can preserve the client's IP address across proxy hops.

Applications should only trust forwarded headers from known, trusted proxies.

When should you use a reverse proxy?

Use one when you want to expose an application through a controlled entry point without exposing its internal network structure.

A reverse proxy is useful even if you have only one backend server. You do not need multiple instances to benefit from it.

3. What Is a Load Balancer?

A load balancer distributes incoming requests or connections across multiple backend instances.

Suppose a single application instance cannot handle all incoming traffic. Instead of relying on one server, we can run multiple instances of the same application. 

                 +--> Application Instance 1
                 |
Client --> Load Balancer --> Application Instance 2
                 |
                 +--> Application Instance 3

The load balancer chooses which instance should receive each request according to a configured algorithm.

Round-robin

Round-robin distributes requests across servers in rotation. 

Request 1 --> Instance 1
Request 2 --> Instance 2
Request 3 --> Instance 3
Request 4 --> Instance 1

This is a simple strategy when backend instances have similar capacity and requests have reasonably similar processing costs.

Least connections

Least connections prefers the server with the fewest active connections. 

Instance 1: 12 active connections
Instance 2:  4 active connections
Instance 3:  8 active connections

New connection --> Instance 2

This can help when some requests take longer than others. However, active connection counts are not necessarily a perfect measure of actual application workload.

Example: NGINX as a load balancer

http {
    upstream payments_backend {
        least_conn;

        server payments-1:8080;
        server payments-2:8080;
        server payments-3:8080;
    }

    server {
        listen 80;

        location /payments/ {
            proxy_pass http://payments_backend;
        }
    }
}

The upstream block defines a group of backend servers. NGINX distributes requests across the group using the least_conn strategy.

Notice that NGINX is also acting as a reverse proxy here. Load balancing is an additional responsibility, not a replacement for reverse proxying.

Health checks and availability

Load balancing can improve availability, but it does not automatically guarantee it.

If a backend fails, traffic needs to be directed away from unavailable instances. NGINX provides passive failure detection in its standard upstream configuration. Active health checks and other advanced features depend on the NGINX edition or infrastructure platform being used.

The application must also be designed to run safely across multiple instances. For example, relying on local in-memory session state can cause problems when consecutive requests reach different instances.

When should you use a load balancer?

  • You run multiple instances of the same application.
  • You need to distribute traffic as demand increases.
  • You want to avoid depending on one application instance.
  • You need to route traffic away from failed instances.

4. What Is an API Gateway?

An API gateway is an entry point designed to manage how clients access APIs.

Like a reverse proxy, an API gateway receives requests and forwards them to backend services. However, API gateways commonly provide additional capabilities for managing API consumers and enforcing API-specific policies. 

Web Client --------+
                   |
Mobile App --------+--> API Gateway --> Payments Service
                   |                 +--> Users Service
Third-Party API ---+                 +--> Orders Service

Common API gateway responsibilities

  • Authentication: Validate credentials or tokens.
  • Authorization: Enforce configured access policies.
  • Rate limiting: Restrict request rates.
  • Consumer quotas: Limit API usage per customer or application.
  • Request validation: Reject requests that violate configured rules.
  • Routing: Forward requests to the appropriate service.
  • Observability: Collect API usage metrics and logs.
  • Transformations: Modify requests or responses when needed.

The exact capabilities depend on the gateway product. Some also provide developer portals, API keys, subscription plans and centralized API lifecycle management.

Example: An API gateway in a coupon application

Imagine a customer wants to redeem a reward: 

POST /api/coupons/123/redeem
Authorization: Bearer <token>

The gateway might validate the access token, enforce a rate limit and forward the request to the coupon service. 

Client
  |
  v
API Gateway
  |
  +-- Validate access token
  |
  +-- Enforce API quota
  |
  +-- Route request
  |
  v
Coupon Service

However, validating the token does not necessarily mean that the customer is entitled to redeem the reward.

The coupon service must still enforce business rules, such as whether the customer has enough stamps, whether the reward has already been redeemed and whether the offer is still valid.

An API gateway should not replace authorization and business validation inside the application.

When should you use an API gateway?

  • You expose APIs to mobile apps, web clients or third parties.
  • You need API keys, token validation or centralized access policies.
  • You need usage quotas per customer or API consumer.
  • You manage multiple APIs with different access requirements.
  • You need centralized API analytics or developer-facing tooling.

5. Reverse Proxy vs Load Balancer vs API Gateway

These concepts are related, but their primary purposes differ.

Capability Reverse Proxy Load Balancer API Gateway
Primary purpose Forward requests Distribute traffic Manage API access
Forward requests to backends Yes Commonly Yes
Distribute traffic across instances Optional Core responsibility Often
Route by URL or hostname Common Often Common
TLS termination Common Common Common
Rate limiting Possible Product-dependent Common
Consumer-specific quotas Custom configuration Not usually the main purpose Common
API keys and developer portals Not usually built in Not usually built in Common in API management products

These are typical roles, not strict boundaries. A single product can implement several of these capabilities.

The simplest way to remember the distinction is:

  • Reverse proxy: Where should this request go?
  • Load balancer: Which instance should handle it?
  • API gateway: How should access to this API be managed?

6. Can One Component Do All Three?

Yes. These terms describe roles and responsibilities rather than mutually exclusive types of software.

NGINX, for example, can act as a reverse proxy and load balancer and can implement some API gateway features.

Consider this simplified configuration: 

http {
    upstream payments_backend {
        least_conn;

        server payments-1:8080;
        server payments-2:8080;
    }

    limit_req_zone $binary_remote_addr
        zone=api_limit:10m
        rate=10r/s;

    server {
        listen 80;
        server_name api.example.com;

        location /api/payments/ {
            limit_req zone=api_limit burst=20 nodelay;

            proxy_pass http://payments_backend;
        }
    }
}

This configuration combines three responsibilities:

  • Reverse proxy: proxy_pass forwards requests to the backend group.
  • Load balancing: The upstream group distributes requests across two payments instances.
  • Traffic control: limit_req applies a rate limit based on client IP.

However, this does not automatically provide a complete API management platform with customer-specific API keys, subscription plans, developer portals and API consumer analytics.

For those requirements, a dedicated API gateway may be a better fit.

7. Other Important NGINX Use Cases

NGINX can do more than proxying and load balancing. Several other features are useful in production systems.

TLS termination

NGINX can accept HTTPS connections, handle TLS encryption and forward requests to backend services. 

server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;

    location / {
        proxy_pass http://localhost:8080;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

In this example, TLS is terminated at NGINX. The connection between NGINX and the backend uses HTTP, so use HTTPS upstream connections when encryption on that hop is required.

Static file serving

NGINX can serve HTML, CSS, JavaScript, images and other files directly, without sending every request to the application. 

server {
    listen 80;
    server_name example.com;

    root /var/www/frontend;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}

The fallback to index.html is useful for single-page applications whose frontend router handles URLs.

Response caching

NGINX can cache eligible responses so repeated requests do not always reach the backend. 

http {
    proxy_cache_path /var/cache/nginx
        keys_zone=public_cache:10m
        max_size=500m
        inactive=30m;

    server {
        listen 80;

        location /api/public/products/ {
            proxy_cache public_cache;
            proxy_cache_valid 200 30s;

            proxy_pass http://products_backend;
        }
    }
}

Caching is especially useful for public data that changes infrequently. Personalized or sensitive responses need careful cache policies to prevent one user's data from being served to another user.

Rate limiting

NGINX can restrict request rates to reduce excessive traffic reaching an application. 

http {
    limit_req_zone $binary_remote_addr
        zone=login_limit:10m
        rate=5r/m;

    server {
        listen 80;

        location /api/login {
            limit_req zone=login_limit burst=3 nodelay;

            proxy_pass http://auth_backend;
        }
    }
}

This example defines a rate of five requests per minute per client IP, with a small burst allowance.

Rate limiting is not a complete security solution. Configure trusted client IP handling when running behind other proxies, and choose limits that do not unnecessarily block legitimate users.

8. Load Balancing Does Not Solve Every Scaling Problem

Adding a load balancer and more application instances can increase processing capacity, but it introduces new considerations.

Shared state

Suppose a user logs in and the application stores the session only in the memory of Instance 1. 

Request 1 --> Instance 1
               Session stored in memory

Request 2 --> Instance 2
               Session not found

The second request may fail because the two instances do not share the same session state.

Possible solutions include using a shared session store, such as Redis, or using an appropriately designed stateless authentication mechanism.

Database bottlenecks

Increasing the number of application instances does not automatically increase database capacity. 

                 +--> Application 1 --+
                 |                    |
Client --> Load Balancer              +--> Database
                 |                    |
                 +--> Application 2 --+

If every application instance sends more queries to the same overloaded database, the database can remain the bottleneck.

Scaling therefore requires understanding the entire request path, not just the number of application servers.

9. Common Mistakes

  • Assuming a reverse proxy is always a load balancer. A reverse proxy can forward every request to one backend.
  • Assuming a load balancer provides API management. Distributing traffic does not automatically provide API keys, consumer quotas or developer portals.
  • Assuming an API gateway replaces application security. Business rules and authorization still need to be enforced by the appropriate application services.
  • Assuming more instances always improve performance. Shared databases, network capacity and other dependencies can become bottlenecks.
  • Ignoring forwarded headers. Applications behind proxies need a secure and correct strategy for determining the original client IP, hostname and protocol.
  • Caching sensitive responses without a clear policy. Incorrect cache keys or authorization rules can expose data.
  • Assuming a rate limit is a complete security solution. Rate limiting complements authentication, authorization and other security controls.

10. When Should You Use Each?

Use a reverse proxy when:

  • You want one entry point for backend applications.
  • You need to route requests by URL or hostname.
  • You want to centralize TLS termination or request handling.
  • You have one backend and want to keep its address internal.

Use a load balancer when:

  • You run multiple instances of an application.
  • You need to distribute incoming traffic.
  • You want to scale application capacity horizontally.
  • You need to route traffic away from unavailable instances.

Use an API gateway when:

  • You expose APIs to different clients or third parties.
  • You need centralized API authentication or access policies.
  • You need quotas per API consumer.
  • You want API usage analytics or developer management features.

You may not need three separate components. A small application might use NGINX alone. A larger platform might use a cloud load balancer, an API gateway and internal load balancing for its backend services.

11. Quick Comparison Checklist

If you encounter one of these terms in an architecture diagram, ask what problem the component is solving.

  • Is it forwarding requests to internal services? Think reverse proxy.
  • Is it choosing between multiple instances of the same service? Think load balancer.
  • Is it enforcing API access policies and managing consumers? Think API gateway.
  • Is it handling HTTPS, serving static files, caching responses or limiting traffic? These are additional capabilities that products such as NGINX can provide.

Final Thought

Reverse proxies, load balancers and API gateways all help control how requests reach backend services, but they emphasize different responsibilities.

A reverse proxy forwards traffic, a load balancer distributes traffic, and an API gateway manages API access and policies. These responsibilities overlap, so one product can perform multiple roles.

NGINX is a useful starting point because it demonstrates how request routing, load balancing, TLS termination, caching and rate limiting work in practice.

The most useful mindset is: understand the problem each component solves, and choose the simplest architecture that satisfies your application's security, availability and scaling requirements.
