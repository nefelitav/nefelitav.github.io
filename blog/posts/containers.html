Docker vs Kubernetes vs Helm vs Argo CD vs VMs

15 October 2026

Docker, Kubernetes, Helm, Argo CD, and virtual machines (VMs) are often mentioned together when discussing infrastructure and deployment. However, they solve different problems.

Some package applications, some run and manage them, and others automate deployment. Understanding their responsibilities makes it easier to decide which tools your application actually needs.

1. The Big Picture

Think of deploying an application as a series of responsibilities:

  • Virtual machines: provide virtualized computers on which you can run operating systems and applications.
  • Docker: packages an application and its dependencies into a container image.
  • Kubernetes: orchestrates containers across a cluster of machines.
  • Helm: packages and configures Kubernetes resources using reusable charts.
  • Argo CD: automatically reconciles a Kubernetes cluster with the configuration stored in Git.

These tools are complementary rather than direct replacements for one another. You can use Docker without Kubernetes, Kubernetes without Helm, and Kubernetes without Argo CD.

2. Virtual Machines (VMs)

A virtual machine is a software-defined computer with virtualized hardware, its own operating system, memory, CPU allocation, and storage. A hypervisor manages the virtual machines running on a physical host.

Physical Server
       |
       v
    Hypervisor
       |
       +-------------------+
       |                   |
       v                   v
     VM 1                 VM 2
  Linux OS              Linux OS
       |                   |
       v                   v
   Application A       Application B

When would you use VMs?

  • Running traditional applications: applications that expect a full operating system or are not containerized.
  • Isolation: separating workloads into distinct operating system environments.
  • Legacy systems: applications that depend on specific operating system configurations.
  • Running Kubernetes: cloud Kubernetes clusters commonly use VMs as worker nodes.
  • Full OS control: when you need to manage system services, kernel settings, or OS-level software.

Advantages

  • Strong isolation boundaries compared with ordinary containers sharing a host kernel.
  • Independent operating system environments.
  • Suitable for a wide variety of workloads, including legacy applications.

Trade-offs

  • Typically require more resources than individual containers.
  • Operating systems need patching, configuration, and maintenance.
  • Managing many VMs can become operationally complex.

3. Docker

Docker is a platform and ecosystem for building, distributing, and running containers. A container packages an application with the libraries and other dependencies it needs.

Unlike a VM, a typical Linux container does not run its own guest operating system. Containers share the host kernel while providing process and filesystem isolation.

Host Operating System
          |
          v
     Container Runtime
          |
     +----+----+
     |         |
     v         v
 Container A  Container B
 App + libs   App + libs

Example: Dockerfile

A Dockerfile describes how to build an application image.

FROM php:8.4-cli

WORKDIR /app

COPY . .

CMD ["php", "app.php"]

Build and run the image:

# Build an image
docker build -t my-app:1.0 .

# Run a container
docker run --rm my-app:1.0

This is a simplified example. A production PHP web application may need a web server, PHP-FPM, dependencies installed through Composer, and additional configuration.

When would you use Docker?

  • Consistent environments: reduce differences between development, testing, and production.
  • CI/CD: build a deployable artifact once and promote it across environments.
  • Microservices: package each service with its own dependencies.
  • Local development: run databases, caches, and application services without installing everything directly on your machine.
  • Deployment: distribute an application image to a server or container platform.

Important distinction: image vs container

  • Image: the packaged, versioned template used to start containers.
  • Container: a running or stopped instance created from an image.
  • Registry: a place to store and distribute images, such as Docker Hub or a cloud container registry.

Docker alone does not automatically provide multi-machine orchestration, automatic recovery across a cluster, or sophisticated rolling deployments. Those capabilities require additional infrastructure or a platform.

4. Kubernetes

Kubernetes is a container orchestration platform. It manages containerized workloads across a cluster and continuously tries to make the actual system match the desired configuration.

Instead of manually starting containers on individual servers, you describe what should run and let Kubernetes manage scheduling, restarts, networking, and scaling.

Kubernetes Cluster
       |
       +----------------------+
       |                      |
       v                      v
    Worker Node 1          Worker Node 2
       |                      |
       v                      v
   Application Pod        Application Pod
   Application Pod        Application Pod

Important Kubernetes concepts

  • Cluster: the collection of machines managed by Kubernetes.
  • Node: a machine, physical or virtual, that runs workloads.
  • Pod: the smallest deployable Kubernetes unit, containing one or more closely related containers.
  • Deployment: manages replicated application Pods and supports controlled rollouts.
  • Service: provides a stable network endpoint for accessing a group of Pods.
  • Ingress / Gateway: provides HTTP routing into the cluster when the corresponding controller or implementation is installed.
  • ConfigMap / Secret: provide configuration and references to sensitive configuration data.
  • Horizontal Pod Autoscaler: adjusts replica counts based on configured metrics and policies.

Example: Kubernetes Deployment

This manifest asks Kubernetes to maintain three replicas of an application.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: my-app
          image: my-registry/my-app:1.0
          ports:
            - containerPort: 8080

Apply the manifest:

kubectl apply -f deployment.yaml

kubectl get deployments
kubectl get pods

Kubernetes attempts to maintain three replicas. If a Pod fails, the controller can create a replacement. This does not guarantee that the application itself is healthy or that requests will never fail.

When would you use Kubernetes?

  • Multiple services: manage many containerized workloads consistently.
  • High availability: replace failed Pods and distribute workloads across nodes when configured appropriately.
  • Scaling: increase or decrease replicas based on traffic or metrics.
  • Rolling deployments: gradually replace application versions.
  • Service discovery: let services communicate through stable names and endpoints.
  • Platform standardization: provide common deployment mechanisms across development teams.

Trade-offs

  • Significant learning and operational complexity.
  • Networking, storage, permissions, upgrades, and observability require careful setup.
  • A cluster does not automatically make an application highly available; replicas, topology, health checks, capacity, and dependencies matter.
  • Managed Kubernetes reduces control-plane maintenance but does not remove all operational responsibilities.

Rule of thumb: Docker packages and runs containers; Kubernetes manages containerized workloads across a cluster.

5. Helm

Helm is a package manager for Kubernetes. It helps you define, configure, version, install, upgrade, and roll back collections of Kubernetes resources.

Without Helm, you might maintain many YAML files for each application and environment. Helm charts let you reuse templates and provide different values for development, staging, and production.

Example: Helm chart structure

my-app/
  Chart.yaml
  values.yaml
  templates/
    deployment.yaml
    service.yaml
    ingress.yaml

The values.yaml file contains configurable values:

replicaCount: 3

image:
  repository: my-registry/my-app
  tag: "1.0"

service:
  port: 80

A template can reference those values:

spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: my-app
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"

Helm renders the templates into ordinary Kubernetes manifests using the selected values.

Common commands

# Install a chart
helm install my-app ./my-app

# Upgrade an existing release
helm upgrade my-app ./my-app \
  --set image.tag=1.1

# Inspect the rendered manifests
helm template my-app ./my-app

# List releases
helm list

# Roll back to a previous release revision
helm rollback my-app 1

When would you use Helm?

  • Reusable configuration: deploy the same application with different settings.
  • Complex applications: package multiple Kubernetes resources together.
  • Third-party software: install applications distributed as Helm charts.
  • Environment-specific values: vary replicas, image tags, resource limits, and other settings.
  • Versioned releases: track chart versions and manage upgrades.

What Helm does not do

Helm does not run containers, schedule Pods, or provide a continuous deployment controller by itself. Kubernetes still performs those responsibilities.

Helm also does not inherently provide GitOps. It can be used directly from a CI/CD pipeline or through tools such as Argo CD.

6. Argo CD

Argo CD is a declarative continuous delivery tool for Kubernetes. It implements a GitOps workflow: the desired application configuration is stored in Git, and Argo CD compares that configuration with the live cluster.

When the cluster differs from the desired state, Argo CD can report the difference and, when configured, synchronize the cluster to the desired configuration.

Developer changes application
          |
          v
   Build and push image
          |
          v
   Update configuration in Git
          |
          v
        Argo CD
          |
          v
 Compare Git with live cluster
          |
          v
    Synchronize if configured
          |
          v
   Kubernetes applies changes

What is GitOps?

GitOps uses a version-controlled repository as the source of truth for declarative infrastructure and application configuration.

Instead of relying only on a CI pipeline to issue deployment commands directly to the cluster, an agent inside or associated with the cluster observes the repository and reconciles the live state.

Example workflow

  1. A developer merges a code change.
  2. A CI pipeline runs tests and builds a Docker image.
  3. The image is pushed to a container registry.
  4. The deployment repository is updated with the new image tag.
  5. Argo CD detects the configuration change.
  6. Argo CD synchronizes the application if automatic synchronization is enabled, or an operator triggers synchronization.
  7. Kubernetes performs the rollout.

When would you use Argo CD?

  • GitOps deployments: make Git the source of truth for deployed configuration.
  • Auditability: review configuration changes through pull requests and Git history.
  • Drift detection: identify differences between Git and the live cluster.
  • Multiple environments or clusters: manage deployments using consistent declarative configuration.
  • Controlled releases: combine manual approvals, automated synchronization, and repository protections.

Trade-offs

  • Introduces another component to configure, monitor, and maintain.
  • Requires a sensible repository structure and clear ownership of configuration changes.
  • Secrets must be handled securely; putting plaintext secrets in Git is not safe.
  • Automatic synchronization can apply unintended changes if repository protections and validation are inadequate.

Important: Argo CD is not a replacement for CI. CI typically builds and tests the application, while Argo CD focuses on synchronizing the desired state of Kubernetes applications.

8. How Do They Work Together in Production?

Imagine you are building a backend API with a database, a cache, and background workers.

Step 1: Package the application

You create a Docker image containing the application and its runtime dependencies. CI builds the image, runs tests, and pushes the versioned image to a registry.

Step 2: Provide computing infrastructure

You provision machines. They might be cloud VMs in a managed Kubernetes cluster, physical servers, or infrastructure provided by a cloud platform.

Step 3: Run the application with Kubernetes

Kubernetes schedules Pods on worker nodes and manages their lifecycle. Services provide stable network access, and Deployments manage replicated stateless application instances.

Step 4: Define reusable resources with Helm

You package the application's Deployments, Services, and other resources into a Helm chart. Different values configure staging and production.

Step 5: Deploy with Argo CD

You store the chart configuration and environment-specific values in Git. Argo CD monitors the repository and reconciles the cluster with the desired configuration.

9. Do You Always Need All Five?

No. The right setup depends on your application's scale, reliability requirements, team size, and operational capacity.

Scenario A: Small application or side project

Possible choice: a VM running Docker Compose, or a managed application platform.

You can deploy your API and supporting services without introducing a Kubernetes cluster, Helm, or Argo CD.

VM
 |
 +-- Docker container: API
 +-- Docker container: Worker
 +-- Docker container: Cache

This is often easier to operate for a small number of services.

Scenario B: Several services and growing operational needs

Possible choice: managed Kubernetes, with Helm if reusable templating is useful.

Kubernetes can standardize deployment, scaling, networking, and recovery across many services. However, adopting it is worthwhile only if its benefits outweigh the additional complexity.

Scenario C: Many services and frequent releases

Possible choice: Kubernetes + Helm + Argo CD.

Helm standardizes application configuration, while Argo CD automates reconciliation and gives teams a consistent GitOps deployment workflow.

Scenario D: Legacy application with OS-level requirements

Possible choice: VMs, possibly without Docker or Kubernetes.

If an application requires a particular operating system configuration or is difficult to containerize, running it directly on a VM can be the simpler solution.

10. Common Misconceptions

  • "Docker and Kubernetes are alternatives." Docker packages applications into containers; Kubernetes orchestrates workloads. They solve different problems.
  • "Kubernetes requires Docker Engine." Kubernetes uses a compatible container runtime, commonly containerd or CRI-O. Docker Engine is not required on Kubernetes nodes.
  • "Helm is a container runtime." Helm manages Kubernetes application packages and configuration; it does not run containers.
  • "Argo CD replaces Kubernetes." Argo CD deploys and reconciles resources in Kubernetes; Kubernetes runs and manages the workloads.
  • "Argo CD replaces CI." CI normally tests and builds artifacts. Argo CD focuses on continuous delivery through GitOps.
  • "Kubernetes automatically scales everything." Scaling requires appropriate replica settings, autoscaling configuration, metrics, and enough cluster capacity.
  • "Containers are VMs." Containers generally share a host kernel, while VMs run separate guest operating systems.
  • "Every application needs Kubernetes." Simpler deployment options may be cheaper and easier to maintain.

11. What Should a Software Developer Learn First?

You do not need to become a DevOps engineer to understand how your application gets deployed. A practical learning order is:

  1. Docker: understand images, containers, Dockerfiles, registries, volumes, networking, and Docker Compose.
  2. Deployment fundamentals: learn environment variables, secrets, health checks, logs, resource limits, and CI pipelines.
  3. Kubernetes basics: understand Pods, Deployments, Services, ConfigMaps, Secrets, and how rolling updates work.
  4. Helm: learn how charts and values make Kubernetes configuration reusable.
  5. Argo CD: understand GitOps, synchronization, drift detection, and how a Git change reaches a running application.
  6. Infrastructure fundamentals: understand VMs, networking, load balancing, storage, permissions, and monitoring.

You should be able to follow the path from a code change to a running application, diagnose a failed deployment, inspect logs, and understand which system is responsible for each step.

12. What Should I Remember?

  • VMs: provide virtual computers and operating system environments.
  • Docker: packages applications into portable container images.
  • Kubernetes: orchestrates containerized workloads across a cluster.
  • Helm: packages and configures Kubernetes resources.
  • Argo CD: reconciles Kubernetes deployments with configuration stored in Git.

The most important idea is that these tools operate at different layers. Start with the simplest deployment architecture that meets your needs, and introduce additional tools when they solve a real problem.
