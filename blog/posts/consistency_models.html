Consistency Models

7 October 2026

Consistency models describe the guarantees a distributed system provides about what data reads can see and how operations are ordered.

In a distributed system, the same data may exist on multiple servers. Because updates can take time to propagate between replicas, different clients may temporarily see different values. 

Server A                 Server B
X = 20                   X = 10

        <---------->
   replication

A consistency model defines what behavior is considered valid when this happens.

1. Strong Consistency

With strong consistency, a read always returns the latest successful write. 

WRITE X = 20
    ↓
READ X
→ 20

A client should never observe an older value after a newer write has become visible.

Strong consistency makes systems easier to reason about, but maintaining it across distributed nodes can require coordination, which can increase latency and reduce availability during failures.

2. Linearizability

Linearizability is a particularly strong consistency guarantee.

It makes operations appear as though they happened atomically at a single point in time, while respecting real-time ordering. 

Client A:
WRITE X = 20
↓
done

Client B:
READ X
↓
20

Once the write has completed, a later read cannot return the old value.

Linearizability is often what people mean when they say that a system provides strong consistency.

3. Eventual Consistency

With eventual consistency, replicas are allowed to temporarily contain different values. 

After a write:

Server A → X = 20
Server B → X = 10
    ↓
synchronization

Server A → X = 20
Server B → X = 20

The guarantee is that if no new updates occur, the replicas will eventually converge to the same value.

This can allow systems to remain highly available and continue serving requests while replicas synchronize.

The trade-off is that a client may temporarily receive stale data.

4. Read-Your-Writes Consistency

Read-your-writes consistency guarantees that after a client successfully writes data, that same client will subsequently see its own update. 

Client:
WRITE profile.name = "Nefeli"
↓
done

READ profile.name
↓
"Nefeli"

Without this guarantee, a user could update their profile and immediately refresh the page only to see the old value because the read was served by a replica that had not synchronized yet.

5. Monotonic Reads

Monotonic read consistency guarantees that once a client has seen a particular version of data, subsequent reads will not return an older version. 

First read:
X = 20

Second read:
X = 20
or newer

Never:
X = 10

Without monotonic reads, a user could observe data moving backwards in time: 

READ → X = 20

READ → X = 10  ❌

This can happen when requests are routed to different replicas that are at different points in the replication process.

6. Causal Consistency

Causal consistency preserves the ordering of operations that are causally related.

Consider a social media application: 

1. User creates a post
      ↓
2. User comments on the post

The comment depends on the post existing first.

A causally consistent system ensures that another user does not observe the comment before observing the post it refers to. 

Valid:

Post
↓
Comment

Invalid:

Comment
↓
Post

Operations that are unrelated do not necessarily need to be observed in the same order by every client.

7. Session Consistency

Session consistency describes guarantees provided within a client's session.

It is often discussed using guarantees such as:

  • Read-your-writes
  • Monotonic reads
  • Monotonic writes
  • Writes-follow-reads

These guarantees can provide a more predictable user experience without requiring every operation across the entire system to have the strongest possible consistency.

9. Choosing a Consistency Model

The strongest consistency model is not always necessary. The appropriate model depends on the requirements of the system.

Strong consistency may be important for:

  • Financial balances
  • Inventory where overselling must be prevented
  • Distributed locks
  • Critical configuration

Eventual consistency may be acceptable for:

  • Social media feeds
  • View counts
  • Search indexes
  • Recommendations
  • Analytics

The goal is not always to maximize consistency. It is to choose the weakest consistency model that still satisfies the application's requirements.

10. Consistency Models vs CAP

Consistency models and the CAP theorem are related, but they describe different things.

  • CAP theorem: describes the trade-off between consistency and availability when a network partition occurs.
  • Consistency models: describe the guarantees provided to clients about reads, writes and operation ordering. 
CAP
│
└── What happens during a network partition?
│
├── Consistency
└── Availability

Consistency Models
│
└── What can clients observe?
│
├── Linearizability
├── Eventual consistency
├── Read-your-writes
├── Monotonic reads
└── Causal consistency

Final Thought

Consistency is not simply about whether data is "correct" or "incorrect". It is about what guarantees a system makes about what clients can observe.

Different applications need different guarantees, so distributed systems often choose a consistency model that provides the right balance between correctness, performance, latency and availability.
