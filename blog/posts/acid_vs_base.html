ACID vs BASE: What They Actually Guarantee

15 October 2026

When working with databases, you will often hear about ACID transactions and BASE systems. They describe different approaches to handling data correctness, consistency and availability, particularly when multiple operations or distributed servers are involved.

ACID is commonly associated with relational databases such as PostgreSQL and MySQL. BASE is commonly associated with distributed NoSQL databases such as Cassandra and DynamoDB.

However, the distinction is not simply "SQL is consistent, NoSQL is eventually consistent." Many NoSQL databases support transactions, and many databases let you choose between different consistency guarantees.

The important question is: What exactly does the database guarantee when requests succeed, transactions overlap, or servers fail?

The Big Picture

Concept Main idea Typical priority
ACID Reliable transactions with defined correctness guarantees. Atomicity, isolation and durable commits.
BASE A distributed-systems approach that can tolerate temporarily inconsistent views of data. High availability and scalability, with convergence where applicable.
Strong consistency Reads respect a defined ordering of completed writes. Predictable visibility of updates.
Eventual consistency If updates stop and the system recovers, replicas will eventually converge under the model's assumptions. Replication flexibility and availability trade-offs.

ACID and BASE are useful conceptual models, but they are not exact opposites. ACID describes transaction properties, while BASE describes a broad approach to distributed data management. A system can provide ACID transactions and still replicate data asynchronously to other systems.

1. ACID Explained

ACID stands for Atomicity, Consistency, Isolation and Durability. These properties help ensure that database transactions behave reliably.

A — Atomicity

Either all changes in a transaction happen, or none of them do.

Imagine transferring €100 from Account A to Account B. The database must subtract €100 from A and add €100 to B as one transaction. 

BEGIN TRANSACTION;

UPDATE accounts
SET balance = balance - 100
WHERE id = 'A';

UPDATE accounts
SET balance = balance + 100
WHERE id = 'B';

COMMIT;

If the second update fails and the transaction is rolled back, the first update is also undone. 

Account A: €500
Account B: €200

Transfer €100
      |
      v
Account A: €400
Account B: €300
      |
      v
Both updates commit together

Without atomicity, the application might subtract money from A and fail before crediting B.

What atomicity does not guarantee: it does not make an entire business workflow atomic if that workflow also includes an external payment provider, an email service or another independent database.

C — Consistency

A committed transaction must preserve the database's defined integrity rules.

In ACID, consistency means that a transaction takes the database from one valid state to another, assuming the transaction correctly implements the required rules.

For example, a database might enforce:

CREATE TABLE accounts (
    id BIGINT PRIMARY KEY,
    balance DECIMAL(12, 2) NOT NULL,
    CONSTRAINT non_negative_balance
        CHECK (balance >= 0)
);

If the constraint is enforced by the database, an update that would make the balance negative is rejected.

Other examples include:

  • Primary keys must be unique.
  • Foreign keys must reference valid records.
  • Required fields cannot be NULL.
  • Check constraints must be satisfied.

Important: ACID consistency does not mean every read across every server immediately returns the latest global value. It is about preserving defined integrity rules, not a blanket guarantee of distributed read consistency.

It also does not automatically enforce every business rule. If the application allows an invalid state and the database has no constraint preventing it, ACID does not magically discover the mistake.

I — Isolation

Concurrent transactions are controlled so that their interactions follow the database's isolation guarantees.

Imagine two customers trying to purchase the last item in stock. 

Initial stock: 1

Transaction A              Transaction B
     |                           |
     v                           v
Read stock = 1             Read stock = 1
     |                           |
     v                           v
Purchase item              Purchase item
     |                           |
     +-------------+-------------+
                   |
                   v
          Potential overselling

Without appropriate concurrency control, both transactions might make decisions based on the same stock value.

A conditional update can help prevent overselling: 

UPDATE products
SET stock = stock - 1
WHERE id = 123
  AND stock > 0;

The application checks the number of affected rows. If zero rows were affected, the item was not available for purchase. The database evaluates the update atomically.

Other approaches include row locks, optimistic locking, unique constraints and transactions with suitable isolation.

Isolation levels matter

ACID does not mean every transaction runs as if it were the only transaction in the entire system. Databases provide different isolation levels with different trade-offs.

Isolation level What it generally permits
READ UNCOMMITTED May allow dirty reads, depending on the database.
READ COMMITTED Prevents dirty reads, but repeated reads may see different committed values.
REPEATABLE READ Provides stronger repeat-read guarantees; exact behavior varies by database.
SERIALIZABLE Provides behavior equivalent to some serial ordering of transactions, possibly by aborting transactions that must be retried.

For example, PostgreSQL and MySQL's InnoDB engine have different implementations of REPEATABLE READ. Do not assume an isolation level has identical behavior across every database.

Even SERIALIZABLE transactions may fail with a serialization error and need to be retried. The application must handle those failures correctly.

D — Durability

Once a transaction is successfully committed, its changes are expected to survive subsequent failures according to the database's durability configuration.

Suppose an invoice is committed successfully and the database server immediately crashes. After recovery, the committed invoice should still exist. 

BEGIN TRANSACTION;

INSERT INTO invoices (id, total)
VALUES (123, 250.00);

COMMIT;

-- The server crashes.

-- After recovery:
-- The committed invoice should still exist.

Durability relies on mechanisms such as write-ahead logging, persistent storage and recovery procedures.

The exact failure guarantees depend on configuration. Asynchronous replication, storage guarantees and acknowledged-commit settings can affect whether the most recent writes survive a server or regional failure.

Durability also does not mean protection against every possible disaster. Backups, recovery testing and replication are still important.

2. What ACID Actually Guarantees — and What It Doesn't

This is the most important distinction to understand: ACID guarantees are scoped to the transactions and database configuration that provide them.

Requirement Does ACID guarantee it? Explanation
Two database updates succeed or fail together Yes, within one transaction Atomicity prevents partial commits.
Enforced constraints remain valid Yes, when correctly defined and enforced Consistency preserves database integrity rules.
Concurrent updates are handled safely With the chosen isolation guarantees Some isolation levels permit anomalies that stronger levels prevent.
Committed data survives a crash According to durability configuration Storage and replication settings matter.
Every read from every replica is immediately up to date No, not automatically Replica consistency is a separate concern.
An external payment and a database update commit together No, not by a local transaction alone They are independent systems unless a distributed protocol coordinates them.
A request is processed exactly once No Retries and external side effects require idempotency and other safeguards.
The application implements the correct business logic No The database cannot automatically correct incorrect application decisions.

3. BASE Explained

BASE is a conceptual model often associated with highly distributed databases. It stands for:

  • Basically Available
  • Soft State
  • Eventually Consistent

BASE emphasizes designing systems that can continue serving requests and distributing updates even when some nodes are temporarily unavailable or replicas have not yet converged.

BASE is not a precise, universally implemented database specification. The actual guarantees depend on the database, configuration, consistency level and operation being performed.

B — Basically Available

The system aims to continue providing useful responses despite certain failures or partial outages.

For example, an application might still allow users to browse a product catalog when one replica is unavailable.

However, availability does not mean every request must always succeed or return the latest data. A system may return stale information, reject a write or fail when a required quorum cannot be reached.

S — Soft State

The system's observed state may change over time even when no new application request is made, as distributed updates propagate between replicas or background reconciliation runs.

Imagine a product's stock count being replicated to several locations. One replica may temporarily show an older value while synchronization is still in progress.

Soft state does not mean the data is random or that it must disappear. It means the visible state may evolve as synchronization and reconciliation occur.

E — Eventually Consistent

If updates stop and the system can successfully complete synchronization, replicas will eventually converge under the system's assumptions and conflict-resolution rules.

Imagine a user changing their profile picture. 

User updates profile picture
             |
             v
        Primary node
             |
             +------> Replica A updated
             |
             +------> Replica B still old
             |
             v
        Replication continues
             |
             v
        Replica B updated

During replication, a read from Replica B might return the old picture. Once replication catches up, both replicas can return the new picture.

Eventual consistency does not guarantee a fixed convergence time, and it does not automatically resolve every conflicting update correctly. Conflict-resolution policies are important.

4. A Real Example: Updating a User Profile

Suppose a user changes their display name from "Alex" to "Alexandra". The application stores the update and replicates it to several database nodes.

With a strongly consistent read

Write: name = "Alexandra"
              |
              v
      Write acknowledged
              |
              v
      Subsequent guaranteed
      consistent read
              |
              v
      name = "Alexandra"

Under an appropriate strong consistency guarantee, a read that occurs after the successful write must respect that write, subject to the database's documented semantics.

With an eventually consistent replica

Write: name = "Alexandra"
              |
              v
      Primary accepts update
              |
              v
      Replica has not caught up
              |
              v
      Read returns "Alex"
              |
              v
      Replication completes
              |
              v
      Read returns "Alexandra"

The second behavior can be acceptable for some workloads, such as recommendations, analytics dashboards or cached profile information.

It may be unacceptable for an operation where the user immediately expects to read back a security setting or a financial state they just changed.

5. ACID vs BASE: The Practical Differences

Aspect ACID-oriented design BASE-oriented design
Primary concern Transaction correctness and integrity Distributed operation and availability trade-offs
Updates Can be committed atomically within a transaction May propagate asynchronously across replicas
Reads Depend on isolation and consistency guarantees May observe stale data depending on read policy
Conflicting writes Managed using transactions, locks, constraints or aborts May require conflict resolution or application reconciliation
Availability during partitions Depends on architecture and consistency requirements Often designed to preserve some operations during partial failures
Typical examples Order processing, accounting, transactional records Replicated catalogs, activity feeds, certain distributed workloads

These are tendencies, not absolute product categories. Relational databases can use asynchronous replication, and distributed NoSQL databases can support strongly consistent reads and transactional operations.

6. How CAP Relates to ACID and BASE

CAP is another distributed-systems concept. It describes a trade-off involving three properties when a network partition occurs:

  • Consistency: in the CAP sense, reads and writes behave as if there were a single up-to-date copy, according to the model's guarantees.
  • Availability: every request to a non-failing node receives a non-error response.
  • Partition tolerance: the system continues operating despite communication failures between nodes.

When a network partition occurs, a distributed system cannot guarantee both CAP consistency and CAP availability for every request. It must sometimes reject or delay operations to preserve consistency, or serve some operations without guaranteeing the latest globally consistent state.

This does not mean that every database is permanently either CP or AP in every situation. Real systems have different operations, consistency settings and failure behaviors.

Example: A network partition

          Node A
             |
             X   Network failure
             |
          Node B

Node A cannot communicate with Node B.

Suppose both nodes could accept a withdrawal from the same account while disconnected. If each independently approves spending based on the same balance, the account could be overdrawn.

A system prioritizing strong consistency may reject or block some writes until it can safely coordinate. A system designed to remain available for those writes may accept them and need to reconcile conflicts later.

The exact outcome depends on the database's consistency protocol and application design.

7. Strong Consistency vs Eventual Consistency

These terms describe how updates become visible to readers. They are not the same as ACID vs BASE.

Requirement Strong consistency Eventual consistency
Read immediately after a successful write Can guarantee visibility under the documented model May return an older value
Replica synchronization Reads coordinate to preserve the required guarantee Updates can propagate asynchronously
Latency May incur coordination overhead Can allow faster local reads in some architectures
Conflict handling Often prevents conflicting results through coordination May require conflict resolution or reconciliation
Suitable workloads Balances, inventory reservations, critical configuration Feeds, analytics, replicated content and approximate counters

Strong consistency does not necessarily mean every request must be slow. The performance impact depends on the topology, protocol, network latency and operation.

Eventual consistency does not necessarily mean data is unreliable or lost. It means readers may temporarily observe different states while updates propagate.

8. When Should You Prefer ACID Guarantees?

Prefer strong transactional guarantees when partial updates, conflicting operations or stale reads could violate important business rules.

Example: Processing an invoice payment

Suppose a system records a payment and marks an invoice as paid. Both database changes should succeed or fail together. 

BEGIN;

INSERT INTO payments (
    invoice_id,
    amount,
    status
)
VALUES (
    123,
    250.00,
    'completed'
);

UPDATE invoices
SET status = 'paid'
WHERE id = 123;

COMMIT;

This example assumes the payment completion has already been established by the relevant business workflow. In a real integration, a database transaction alone cannot make an external payment provider and your database commit atomically.

ACID-oriented transactions are especially useful for:

  • Financial records and account balances.
  • Inventory reservations and order creation.
  • Maintaining relationships and uniqueness constraints.
  • Updating multiple related database records.
  • Preventing invalid concurrent state changes.

9. When Can Eventual Consistency Be Acceptable?

Eventual consistency can be useful when immediate agreement between all replicas is unnecessary and the system benefits from distributed operation.

Example: An activity feed

A user posts a comment. The primary system accepts the comment, and the update propagates to feed-generation workers and read replicas.

Some users might see the comment a little later. This is often an acceptable trade-off for a social feed.

Other possible use cases include:

  • Social feeds and activity timelines.
  • Analytics dashboards with slightly delayed metrics.
  • Search indexes updated asynchronously.
  • Replicated product descriptions.
  • Recommendation data that is periodically refreshed.

The application must still handle conflicting writes, failed replication, retries and reconciliation where necessary. Eventual consistency is not an excuse to ignore correctness.

10. A Critical Distinction: Transactions Across Services

One of the most common misunderstandings is assuming that an ACID transaction automatically covers every operation performed by a backend application.

Consider an order workflow that updates a database and then sends a message to a queue. 

1. Save order in database
2. Publish OrderCreated event
3. Return success

What happens if the database commit succeeds but publishing the message fails?

The order exists, but downstream services never learn about it. A local database transaction cannot automatically roll back an external message publication.

A common solution is the transactional outbox pattern: 

BEGIN TRANSACTION;

INSERT INTO orders (...);

INSERT INTO outbox_events (...);

COMMIT;

Background publisher
        |
        v
Read unpublished outbox event
        |
        v
Publish message
        |
        v
Mark event as published

The order and the event record are committed atomically in the same database. A background publisher then sends the event, typically with retries.

The publisher may send an event more than once, so consumers should be idempotent. This pattern bridges reliable database transactions and asynchronous distributed processing without pretending that the whole workflow is one ACID transaction.

11. Common Misconceptions

"ACID means reads always return the latest data."

Not necessarily. Transaction isolation, replica configuration and the consistency guarantees of the particular read determine which versions are visible.

"BASE means the database can lose data."

No. Eventual consistency concerns convergence and visibility, not an automatic permission to lose acknowledged writes. Durability must be evaluated separately.

"NoSQL databases do not support transactions."

Many NoSQL databases support transactions or atomic operations. The scope and guarantees vary by product.

"ACID and BASE are mutually exclusive."

No. A system can provide ACID transactions within one database and replicate the resulting data asynchronously to other systems.

"Eventual consistency is always faster."

Not necessarily. Performance depends on the query, data model, network, replication protocol, workload and consistency settings.

"Strong consistency solves every concurrency problem."

Strong consistency does not automatically make an application workflow correct. You still need appropriate transactions, constraints, idempotency and business logic.

What Should I Remember?

  • Atomicity: all changes in one transaction succeed together or are rolled back.
  • Consistency: committed transactions preserve enforced integrity rules when the transaction and database are correctly designed.
  • Isolation: concurrent transactions follow the guarantees of the selected isolation level.
  • Durability: committed changes survive failures according to the configured durability guarantees.
  • ACID does not automatically guarantee globally fresh reads, exactly-once processing or atomicity across independent services.
  • BASE describes an approach that emphasizes distributed availability and allows temporarily divergent state where appropriate.
  • Eventual consistency means replicas can converge when updates stop and synchronization succeeds.
  • ACID and BASE are not strict opposites. A system can use ACID transactions and asynchronous replication at the same time.
  • CAP concerns consistency and availability during network partitions, a different question from ACID transaction properties.
  • Use strong transactional guarantees when business correctness depends on them. Allow eventual consistency where stale reads are acceptable and the trade-offs are understood.
