Concurrency & Distributed Systems

8 October 2026

Concurrency is the execution of multiple tasks whose work overlaps in time. In backend systems, concurrency happens constantly: multiple HTTP requests, workers, database transactions and scheduled jobs may access the same resources simultaneously.

The challenge is not simply running things at the same time. The challenge is making sure that concurrent operations produce correct and predictable results.

1. Concurrency vs Parallelism

Concurrency means multiple tasks are in progress during overlapping periods of time.

Parallelism means multiple tasks are actually executing at the same time, typically on different CPU cores.

A backend application can therefore have concurrency even when only one CPU core is executing instructions at a time.

2. Race Conditions

A race condition occurs when the result depends on the timing or ordering of concurrent operations.

A common example is a shared counter: 

counter = 0

Worker A: READ 0
Worker B: READ 0

Worker A: ADD 1
Worker B: ADD 1

Worker A: WRITE 1
Worker B: WRITE 1

Final value = 1  ❌

We expected the result to be 2, but both workers read the same old value.

This is especially common with the read → modify → write pattern.

3. Read → Modify → Write

Many concurrency bugs come from splitting an operation into multiple steps: 

READ
↓
MODIFY
↓
WRITE

For example, suppose a product has one item in stock: 

stock = 1

Request A: READ 1
Request B: READ 1

A: stock--
B: stock--

A: WRITE 0
B: WRITE 0

Two requests may both believe they successfully purchased the same item.

When possible, combine the operation into one atomic database statement: 

UPDATE products

SET stock = stock - 1
WHERE id = 123
AND stock > 0;

Then check the number of affected rows: 

1 row → operation succeeded

0 rows → no stock / another request won

The database can safely perform the update as one operation, avoiding the application-level read-modify-write race.

4. Atomic Operations vs Transactions

An atomic operation makes one operation happen without exposing an intermediate state.

A transaction groups multiple database operations so they succeed or fail together. 

Atomic operation:

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

Transaction:

START TRANSACTION;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;

Atomic operations are useful when one database statement can express the required invariant. Transactions are useful when multiple operations must be coordinated.

5. Transactions

A transaction provides a boundary around a group of database operations. 

START TRANSACTION;

Operation A
Operation B
Operation C

COMMIT;

If something fails: 

ROLLBACK;

Transactions are especially important when several changes must remain consistent with one another.

6. Isolation Levels

Isolation determines what concurrent transactions are allowed to observe.

Common MySQL isolation levels are:

  • READ UNCOMMITTED — may read uncommitted changes.
  • READ COMMITTED — reads only committed data.
  • REPEATABLE READ — MySQL's default; ordinary reads use a consistent transaction snapshot.
  • SERIALIZABLE — strongest isolation, with greater contention.

Different isolation levels control anomalies such as:

  • Dirty reads
  • Non-repeatable reads
  • Phantom reads
  • Lost updates

Isolation answers the question: 

"What can my transaction see?"

7. Locks

A lock controls which concurrent operations can access or modify a resource.

For example, MySQL's FOR UPDATE can lock selected rows: 

START TRANSACTION;

SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;

-- check balance

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

COMMIT;

Another transaction attempting to acquire the same conflicting row lock may have to wait.

A locking read such as FOR UPDATE is useful inside an explicit transaction because the lock is held until COMMIT or ROLLBACK.

This gives us a useful distinction: 

Isolation → What can I see?

Locks → What can I block or prevent?

8. Deadlocks

A deadlock occurs when transactions wait for each other indefinitely. 

Transaction A:

locks Row 1
waits for Row 2

Transaction B:
locks Row 2
waits for Row 1

The database detects the circular dependency and normally rolls back one transaction.

A common way to prevent deadlocks is to acquire locks in a consistent order: 

Always lock:

Row 1
then
Row 2

Never:

Transaction A: 1 → 2
Transaction B: 2 → 1

Transactions should also be kept short and should avoid slow external operations while holding locks.

Applications should generally be prepared to retry a transaction after a deadlock.

9. Optimistic Locking

Optimistic locking assumes conflicts are relatively uncommon and detects them instead of preventing them.

A version column can be used: 

id = 123

status = pending
version = 5

The worker reads version 5 and attempts: 

UPDATE invoices

SET status = 'processing',
version = version + 1
WHERE id = 123
AND version = 5;

The result tells us whether we won: 

1 affected row → success


0 affected rows → someone changed it first

This differs from pessimistic locking: 

Pessimistic:

"Prevent conflicts."

Optimistic:
"Allow conflicts, but detect them."

10. Idempotency

An operation is idempotent if performing it multiple times has the same intended effect as performing it once. 

SET balance = 100

→ idempotent

balance = balance + 100
→ not idempotent

Idempotency is essential when requests can be retried.

For example: 

Client
↓
Payment API
↓
payment succeeds
↓
response lost
↓
client retries

Without protection, the payment could be processed twice.

An idempotency key can identify the logical operation: 

Idempotency-Key: abc123

The database should enforce uniqueness rather than relying on: 

if (!exists) {
insert();

}

Two concurrent requests can both pass the check. A unique constraint or atomic insert provides the actual protection.

11. Queues and Workers

Queues allow work to be processed asynchronously. 

API
↓
Queue
↓
Workers
↓
External services

Multiple workers allow the system to process many messages concurrently.

A worker normally acknowledges a message only after successful processing: 

Receive
↓
Process
↓
Success
↓
ACK

If the worker crashes before acknowledging the message, the queue can deliver it again.

This commonly results in at-least-once delivery, which means consumers must be prepared for duplicates.

12. Message Reliability

Queue systems commonly use a temporary ownership period called a visibility timeout or message lease. 

Message received
↓
temporarily hidden
↓
worker processes it
↓
ACK

If the worker does not acknowledge it before the timeout, the message may become available again.

The timeout must be long enough for normal processing. Otherwise, two workers may process the same message concurrently.

Failed messages are usually retried with exponential backoff: 

1s
2s
4s
8s
16s
...

Jitter adds randomness to retry delays so that many workers do not retry at exactly the same time.

After a configured number of attempts, a message can be moved to a Dead Letter Queue (DLQ). 

Message
   ↓
Process
   ↓
Failure
   ↓
Retry + Backoff
   ↓
Maximum attempts?
   ↓
DLQ

Temporary failures should usually be retried, while permanent failures such as invalid input should generally not be retried indefinitely.

13. At-Most-Once vs At-Least-Once vs Exactly-Once

Message delivery can be described using three common guarantees.

  • At-most-once: delivered zero or one time; messages may be lost.
  • At-least-once: delivered one or more times; duplicates are possible.
  • Exactly-once: intended to produce exactly one delivery or processing result.

Exactly-once behavior is difficult to guarantee across an entire distributed workflow.

A more practical approach is often: 

At-least-once delivery
        +
Idempotent consumer
        =
Reliable processing

For example, a consumer can store processed message IDs with a unique constraint: 

processed_messages
------------------
message_id PRIMARY KEY
processed_at

14. Transactional Outbox

A common distributed-systems problem occurs when an application needs to update a database and publish an event. 

START TRANSACTION

INSERT invoice

Publish InvoiceCreated

COMMIT

The database operation and message publication are two separate systems. One can succeed while the other fails.

The transactional outbox pattern solves this by storing the event in the same database transaction: 

START TRANSACTION

INSERT invoice

INSERT outbox_event

COMMIT

A separate publisher then reads the outbox and publishes the events: 

Application
    ↓
DB transaction
    ↓
Invoice + Outbox Event
    ↓
Outbox Publisher
    ↓
Queue
    ↓
Workers

The publisher can still crash after publishing but before marking the event as published. Therefore, the outbox provides reliable at-least-once publishing, not automatic exactly-once delivery.

Consumers still need idempotency.

15. Distributed Locks

A normal in-memory lock only coordinates threads or processes on the same machine. It cannot coordinate workers running on different machines or Kubernetes pods. 

Pod A ──┐
Pod B ──┼──→ Shared resource
Pod C ──┘

A distributed lock provides shared coordination, often using Redis or a database.

A Redis-style lock might conceptually look like: 

SET lock:invoice:123 worker-abc NX EX 30
  • NX → acquire only if the lock does not exist
  • EX 30 → expire after 30 seconds
  • worker-abc → identifies the owner

The expiration acts as a lease. If the worker crashes, another worker can eventually acquire the lock.

However, if processing takes longer than the lease, the lock may expire while the original worker is still running. This is one reason distributed locks require careful design.

Often, an atomic database claim is simpler: 

UPDATE invoices
SET status = 'processing'
WHERE id = 123
  AND status = 'pending';

If one row was affected, that worker successfully claimed the invoice.

16. Distributed Concurrency

Concurrency becomes more difficult when operations happen on different machines. 

Pod A ──────┐
Pod B ──────┼── Network ── DB / Redis / APIs
Pod C ──────┘

Networks can introduce:

  • Latency
  • Timeouts
  • Lost responses
  • Duplicate requests
  • Network partitions
  • Partial failures

One of the most important problems is ambiguity: 

Request
   ↓
External service succeeds
   ↓
Response is lost
   ↓
Client sees timeout

The client cannot know whether the operation failed or succeeded. Retrying therefore requires idempotency.

17. Split Brain and Stale Workers

A split brain occurs when multiple nodes believe they have authority over the same resource.

Distributed locks can also suffer from stale workers. For example: 

Worker A
acquires lock
    ↓
lock expires

Worker B
acquires lock
    ↓
Worker A continues running ❗

A fencing token can protect against this by assigning an increasing token to each new owner: 

Worker A → token 5
Worker B → token 6

The shared resource can reject operations using an older token.

This prevents a stale worker from modifying state after another worker has legitimately taken ownership.

18. Caching and Concurrency

Caches reduce database load, but they introduce their own concurrency problems.

A common pattern is cache-aside: 

Request
   ↓
Cache
 ┌─┴─┐
Hit  Miss
 ↓    ↓
Return DB
       ↓
     Cache
       ↓
     Return

A cache stampede can happen when many requests encounter the same cache miss simultaneously. 

Cache expires
      ↓
100 requests
      ↓
100 DB queries ❗

One solution is request coalescing using a shared lock: 

Request A → acquires lock → loads DB → updates cache

Request B ───────────────────────→ waits

Request C ───────────────────────→ waits

Another technique is TTL jitter, which gives different cache entries slightly different expiration times.

Stale-while-revalidate can also return slightly stale data while another worker refreshes the cache in the background.

19. Cache Invalidation

When underlying data changes, the cache must eventually reflect the new state. 

Update DB
   ↓
Invalidate cache

Updating the cache before the database can be dangerous: 

Update Cache
     ↓
Update DB fails ❌

Cache now contains data
that the DB never committed.

Cache design therefore involves a trade-off between freshness, performance and complexity.

20. Rate Limiting

Rate limiting controls how many requests can enter a system over time.

It is different from concurrency limiting: 

Rate limiting
→ How many requests over time?

Concurrency limiting
→ How many operations at once?

Fixed Window

Count requests within fixed time intervals. 

12:00:00 ───────── 12:01:00

Maximum: 100 requests

A weakness is the boundary: 

12:00:59 → 100 requests
12:01:00 → 100 requests

200 requests in ~1 second

Sliding Window

Counts requests over a rolling time period, providing a more accurate limit at the cost of additional state and computation.

Token Bucket

A bucket contains tokens that are consumed by requests and replenished at a fixed rate. 

Capacity: 10 tokens
Refill:   2 tokens / second

Request → consume token

This allows controlled bursts while maintaining an average rate.

Leaky Bucket

The leaky bucket smooths traffic by processing requests at a controlled rate.

Rate limiting itself must be concurrency-safe. A distributed implementation cannot simply: 

READ count
↓
count + 1
↓
WRITE count

because concurrent requests can race. The counter update and limit check need atomic coordination.

21. Retry Storms and Backpressure

Retries can make a failure worse. 

Service becomes slow
      ↓
Requests timeout
      ↓
Clients retry
      ↓
More requests
      ↓
Service becomes even slower
      ↓
More retries

This is a retry storm.

Exponential backoff, jitter, rate limiting and bounded concurrency help control the amount of work entering an unhealthy system.

This is an example of backpressure: preventing downstream systems from receiving more work than they can safely handle.

22. Consistency Models

In distributed systems, the same data may exist on multiple servers. Replication can therefore cause clients to observe different versions of the data. 

Primary                 Replica
X = 20                  X = 10

       ← replication →

A consistency model defines what clients are allowed to observe.

Strong / Linearizable Consistency

Once a write has successfully completed, a later read observes that write. 

WRITE X = 20
     ↓
READ X
     ↓
20

Linearizability also requires operations to appear to occur in a single order that respects real-time ordering.

Eventual Consistency

Replicas may temporarily disagree but eventually converge if no new updates occur. 

Primary  → X = 20
Replica  → X = 10
             ↓
        replication
             ↓
Replica  → X = 20

This can provide better availability and lower coordination costs, but clients may temporarily see stale data.

Read-Your-Writes

After a client successfully writes data, that client can subsequently see its own update. 

WRITE name = "Nefeli"
        ↓
READ name
        ↓
"Nefeli"

Monotonic Reads

Once a client has seen a particular version, subsequent reads will not return an older version. 

READ → version 5
READ → version 5
READ → version 6

Never:

READ → version 4

Causal Consistency

Causally related operations are observed in their causal order. 

Create Post
     ↓
Create Comment

A client should not observe the comment before the post that caused it to exist.

23. Consistency vs Serializability

These concepts are related but different.

Serializability concerns concurrent database transactions and whether their result is equivalent to some serial execution.

Linearizability concerns the ordering and visibility of operations, particularly in distributed systems. 

Serializability
→ How transactions interact

Linearizability
→ How operations appear in real time

Similarly, distributed-systems consistency should not be confused with the C in ACID, which concerns preservation of database invariants.

24. Choosing the Right Guarantee

Stronger consistency is not automatically better. It often requires more coordination and can increase latency or reduce availability.

Strong consistency may be important for:

  • Financial balances
  • Inventory where overselling is unacceptable
  • Critical permissions
  • Distributed coordination

Eventual consistency may be acceptable for:

  • Search indexes
  • Analytics
  • Recommendations
  • View counts
  • Social media feeds

The goal is often to choose the weakest consistency guarantee that still satisfies the business requirements.

Final Thought

Concurrency problems rarely come from one request doing something complicated. They usually appear because multiple operations can happen at the same time and the system has to decide what happens when they interact.

At the database level, we use atomic operations, transactions, isolation and locks. At the application level, we use idempotency and optimistic concurrency. At the distributed level, we need queues, retries, outboxes, distributed coordination, caching strategies, rate limiting and consistency guarantees.

The most important question is therefore not simply "How do I make this concurrent?", but: 

What can happen concurrently?
        ↓
What can go wrong?
        ↓
What guarantee do I need?
        ↓
What mechanism provides that guarantee?
