HTTP Headers

30 September 2026

What are HTTP Headers?

HTTP headers are key-value pairs that allow the client and server to exchange additional information about an HTTP request or response.

For example: 

Content-Type: application/json
Accept: application/json
Authorization: Bearer <token>

Headers can communicate information about authentication, the format of the request or response, caching, cookies, security policies, client capabilities, tracing and much more.

They are separate from the actual data being sent in the request or response body.

Request Headers vs Response Headers

HTTP headers exist on both requests and responses.

Request

POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json
Authorization: Bearer eyJ...

{
    "name": "Nefeli"
}

The client is sending information to the server about the request.

Response

HTTP/1.1 201 Created
Content-Type: application/json
Location: /users/123
Cache-Control: no-cache

{
    "id": "123",
    "name": "Nefeli"
}

The server is sending information back to the client about the response.

Some headers are primarily used on requests, some on responses, and some can appear on both.

Content & Representation

Content-Type

Content-Type describes the media type of the message body being sent. 

Content-Type: application/json

Common values include: 

application/json
text/html
text/plain
application/xml
multipart/form-data
application/x-www-form-urlencoded

For example, if a client sends JSON: 

POST /users

Content-Type: application/json

{
    "name": "Nefeli"
}

Accept

Accept tells the server which response media types the client understands or prefers. 

Accept: application/json

This is an important distinction:

  • Content-Type describes the data being sent.
  • Accept describes the response format the client wants.

These headers are part of a broader concept called content negotiation.

Content-Length

Content-Length indicates the size of the message body in bytes. 

Content-Length: 1234

In modern HTTP, message framing can also use mechanisms such as chunked transfer encoding, so you should not assume every response necessarily contains a Content-Length header.

Authentication

Authorization

The Authorization header is commonly used to send authentication credentials or an access token. 

Authorization: Bearer eyJhbGciOi...

The Bearer scheme is commonly used with OAuth 2.0 access tokens.

Other authentication schemes exist, such as Basic authentication: 

Authorization: Basic base64-encoded-credentials

Authentication and authorization are different concepts:

  • Authentication: Who are you?
  • Authorization: What are you allowed to do?

Cookies

Cookies allow servers to store small pieces of state in a user's browser. They are commonly used for sessions and authentication.

Set-Cookie

A server can ask the browser to store a cookie using Set-Cookie. 

Set-Cookie: session_id=abc123; Secure; HttpOnly; SameSite=Lax

Cookie

The browser can then send the cookie back to the server: 

Cookie: session_id=abc123

Important cookie attributes

  • Secure — only send the cookie over HTTPS.
  • HttpOnly — prevents JavaScript from accessing the cookie through document.cookie.
  • SameSite — controls when cookies are sent in cross-site requests.
  • Domain — controls which domains receive the cookie.
  • Path — controls which paths receive the cookie.
  • Max-Age / Expires — controls cookie lifetime.

Caching

HTTP has built-in mechanisms that allow clients and intermediary caches to avoid downloading the same resource repeatedly.

Cache-Control

Cache-Control controls caching behavior. 

Cache-Control: max-age=3600

Other directives include:

Cache-Control: no-cache
Cache-Control: no-store
Cache-Control: private
Cache-Control: public
Cache-Control: max-age=3600

These directives have different meanings. In particular, no-cache does not simply mean "don't cache"; it means that a stored response generally must be revalidated before reuse.

ETag

An ETag identifies a particular representation of a resource. 

ETag: "abc123"

The client can later ask whether that representation has changed: 

If-None-Match: "abc123"

If the resource has not changed, the server can respond with: 

304 Not Modified

This allows the client to reuse its cached copy instead of downloading the resource again.

Last-Modified

Another way of describing when a resource was last changed is: 

Last-Modified: Wed, 30 Sep 2026 10:00:00 GMT

A client can then send: 

If-Modified-Since: Wed, 30 Sep 2026 10:00:00 GMT

Conditional Requests

Headers such as If-None-Match and If-Match allow a request to depend on the current state of a resource.

This is useful for both caching and concurrency control.

Optimistic concurrency

Imagine two clients retrieve the same resource: 

GET /users/123

ETag: "version-42"

Client A updates the resource first. The server now has: 

ETag: "version-43"

Client B can prevent accidentally overwriting the newer version by sending: 

If-Match: "version-42"

Because the resource is now version 43, the server can reject the update instead of silently overwriting someone else's changes.

CORS

Cross-Origin Resource Sharing (CORS) controls how browsers allow web pages from one origin to make requests to another origin.

An origin is defined by its: 

scheme + host + port

For example: 

https://example.com
https://api.example.com

These are different origins because the hosts differ.

Origin

Browsers can send an Origin header: 

Origin: https://example.com

Access-Control-Allow-Origin

The server can indicate which origins are allowed: 

Access-Control-Allow-Origin: https://example.com

Other CORS headers

Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Allow-Credentials: true

CORS is primarily a browser security mechanism. It is important to understand that CORS does not prevent servers from receiving requests from non-browser clients such as curl or backend services.

Security Headers

Some response headers allow a server to communicate security policies to a browser.

Strict-Transport-Security

HTTP Strict Transport Security (HSTS) tells browsers to use HTTPS for a site. 

Strict-Transport-Security: max-age=31536000

Content-Security-Policy

Content Security Policy (CSP) controls which sources a browser is allowed to load or execute. 

Content-Security-Policy: default-src 'self'

CSP is particularly useful for reducing the impact of certain cross-site scripting attacks.

X-Content-Type-Options

X-Content-Type-Options: nosniff

This tells browsers not to try to guess a different content type from the one declared by the server.

X-Frame-Options

X-Frame-Options: DENY

This can control whether a page can be embedded in a frame and can help protect against clickjacking.

Referrer-Policy

Controls how much referrer information browsers send with requests. 

Referrer-Policy: strict-origin-when-cross-origin

Redirects

Location

The Location header tells the client where a resource or redirect points. 

HTTP/1.1 302 Found
Location: https://example.com/new-location

It is also commonly used after creating a resource: 

HTTP/1.1 201 Created
Location: /users/123

Rate Limiting

APIs often limit how many requests a client can make in a given period.

When a client exceeds the limit, the server can return: 

HTTP/1.1 429 Too Many Requests

Retry-After

Retry-After can tell the client when it should try again. 

Retry-After: 60

This means the client should wait before retrying.

Tracing & Request IDs

Request identifiers are useful when debugging distributed systems. 

X-Request-ID: 7f8c9d...

A request can pass through several services: 

Client
   ↓
API Gateway
   ↓
Payment Service
   ↓
Ledger Service
   ↓
Notification Service

If the same request identifier is propagated through these services, the logs can be connected together.

Modern distributed systems may also use standardized tracing mechanisms such as the W3C Trace Context headers: 

traceparent
tracestate

Client & Request Information

Host

The Host header identifies the host and, when relevant, port targeted by the request. 

Host: api.example.com

In HTTP/2 and HTTP/3, the :authority pseudo-header serves the corresponding role.

User-Agent

User-Agent identifies information about the client making the request. 

User-Agent: Mozilla/5.0 ...

It can be useful for logging and analytics, but it should not generally be treated as trustworthy security information because clients can modify it.

Referer

The Referer header can indicate the page from which a request originated. 

Referer: https://example.com/products

Note that the spelling of the header is historically Referer, not Referrer.

Idempotency

Some APIs use an Idempotency-Key header to make retries of non-idempotent operations safe. 

POST /payments
Idempotency-Key: 8f3c9a...

For example, if a client submits a payment and doesn't receive the response because of a network failure, it can retry using the same key.

The server can recognize that the operation has already been processed and return the previous result instead of performing it twice.

Idempotency keys are especially important for APIs involving payments, orders and other operations with important side effects.

Custom Headers

Applications can define their own headers when necessary. 

Idempotency-Key: abc123
X-Request-ID: 7f8c9d...

Historically, custom headers were often prefixed with X-. This convention is no longer generally recommended for new headers.

Before creating a custom header, check whether a standard HTTP mechanism already solves the problem.

Proxies & Forwarded Headers

Requests often pass through reverse proxies, load balancers, API gateways or CDNs before reaching the application. 

Client
   ↓
CDN
   ↓
Load Balancer
   ↓
Reverse Proxy
   ↓
Application

The application may therefore need information about the original client or protocol.

Commonly encountered headers include: 

Forwarded
X-Forwarded-For
X-Forwarded-Proto
X-Forwarded-Host

These headers require careful handling because applications should not blindly trust values supplied by untrusted clients. Whether they can be trusted depends on the network architecture and which proxy inserted or sanitized them.

HTTP/2 & HTTP/3

HTTP/2 and HTTP/3 introduce some concepts that are useful to recognize when looking at network traffic.

HTTP/2 uses pseudo-headers such as: 

:method
:path
:scheme
:authority
:status

These are not ordinary HTTP headers. They provide information that was represented differently in HTTP/1.1.

HTTP/2 and HTTP/3 also use binary protocols rather than the textual wire format used by HTTP/1.1.

A Useful Mental Model

When looking at an HTTP request, ask yourself what each part is responsible for: 

POST /payments?currency=EUR HTTP/1.1

Authorization: Bearer ...
Content-Type: application/json
Accept: application/json
Idempotency-Key: abc123
X-Request-ID: 7f8c9d...

{
    "amount": 1000,
    "currency": "EUR"
}
  • URL/path: What resource are we interacting with?
  • Query parameters: How should the request be filtered or modified?
  • Headers: What metadata or instructions accompany the request?
  • Body: What data are we actually sending?
  • Method: What kind of operation are we performing?

Understanding this distinction makes HTTP APIs much easier to reason about.

What Should I Remember?

  • HTTP headers are metadata exchanged between clients and servers.
  • Request headers describe the request or provide instructions to the server.
  • Response headers describe the response or provide instructions to the client.
  • Content-Type describes the body being sent.
  • Accept describes the response formats the client can handle.
  • Authorization is commonly used for authentication.
  • Cookie and Set-Cookie are used for browser cookies.
  • Caching relies heavily on headers such as Cache-Control and ETag.
  • Conditional headers such as If-Match can help prevent concurrent updates from overwriting each other.
  • CORS uses several headers to control browser cross-origin requests.
  • Security headers allow servers to communicate browser security policies.
  • Retry-After can help clients handle rate limiting and temporary unavailability.
  • Request and tracing headers help debug distributed systems.
  • Custom headers should be used carefully when standard HTTP mechanisms don't already solve the problem.
