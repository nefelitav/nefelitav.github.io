Types of Databases Explained

15 October 2026

Databases are designed to store, organize, retrieve and manage data. However, not all databases organize data in the same way or optimize for the same requirements.

Some databases are excellent at handling financial transactions and relationships between entities. Others are designed for flexible documents, massive write volumes, relationship traversal, full-text search or real-time analytics.

Understanding the different types of databases helps you choose the right technology for a particular problem instead of automatically reaching for MySQL or PostgreSQL for everything.

The important question is not just "Which database is the fastest?" but "Which database best fits my data, access patterns, consistency requirements and scale?"

The Big Picture

Database type Best suited for Examples
Relational (SQL) Structured data, transactions and relationships PostgreSQL, MySQL
Document Flexible, nested records MongoDB, Couchbase
Key-value Fast lookups by key Redis, Amazon DynamoDB
Wide-column Large-scale distributed workloads Apache Cassandra, HBase
Graph Highly connected data Neo4j, Amazon Neptune
Time-series Timestamped measurements and metrics InfluxDB, TimescaleDB
Search Full-text search and relevance ranking Elasticsearch, OpenSearch

Distributed SQL Relational data across multiple nodes CockroachDB, YugabyteDB

These categories are not always mutually exclusive. PostgreSQL is relational but can also support JSON documents, full-text search and vector search. Redis is an in-memory data store that also supports persistence and multiple data structures.

1. Relational Databases (SQL)

Relational databases organize data into tables containing rows and columns. Relationships between tables are represented using keys, and SQL is used to query and manipulate the data.

Example

customers
---------
id
name
email

orders
------
id
customer_id
total
status

An order references its customer through customer_id. You can retrieve orders together with their customers using a JOIN. 

SELECT
    customers.name,
    orders.total,
    orders.status
FROM customers
JOIN orders
    ON orders.customer_id = customers.id
WHERE customers.id = 123;

What makes relational databases useful?

  • Relationships: foreign keys connect related records.
  • Transactions: multiple changes can succeed or fail together.
  • Constraints: unique constraints, foreign keys and checks help enforce data integrity.
  • SQL: flexible queries, joins, filtering and aggregations.
  • Consistency: transactions and constraints help maintain correct business data.

What is ACID?

ACID describes four properties commonly associated with reliable database transactions.

  • Atomicity: all changes in a transaction happen, or none do.
  • Consistency: transactions preserve defined integrity rules.
  • Isolation: concurrent transactions are controlled according to the chosen isolation level.
  • Durability: committed changes survive failures according to the database's durability guarantees.

Popular relational databases

  • PostgreSQL: advanced SQL, extensibility, complex queries and rich data types.
  • MySQL: widely used in web applications and backend services.
  • SQL Server: common in Microsoft-oriented enterprise environments.
  • Oracle Database: used in large enterprise and mission-critical environments.

When should you use a relational database?

  • Financial transactions and payment records.
  • Orders, customers, invoices and subscriptions.
  • Applications with relationships between many entities.
  • Systems requiring constraints and transactional updates.
  • Applications that need flexible querying and reporting.

Example: an invoicing application that stores invoices, invoice lines, tax breakdowns and payment records would usually benefit from a relational database.

Relational databases can scale significantly. Do not assume that you need NoSQL simply because an application has many users or a large amount of data.

2. Document Databases

Document databases store records as documents, commonly using JSON-like structures. Each document can contain nested objects and arrays.

Example

{
    "customerId": 123,
    "name": "Alex",
    "address": {
        "city": "Amsterdam",
        "country": "Netherlands"
    },
    "preferences": {
        "language": "en",
        "notifications": true
    },
    "tags": ["business", "premium"]
}

Instead of splitting every field into separate relational tables, a document database can store related information together in one document.

Popular document databases

  • MongoDB
  • Couchbase
  • Firestore

Advantages

  • Flexible schemas for records with different fields.
  • Natural representation of nested JSON data.
  • Convenient retrieval of a complete document.
  • Can scale horizontally depending on the database and workload.

Trade-offs

  • Flexible schemas can lead to inconsistent data if validation is neglected.
  • Relationships and cross-document queries may be less convenient than relational joins.
  • Duplicating data can simplify reads but complicate updates.
  • Transaction capabilities vary by product and deployment.

When should you use a document database?

  • Records have flexible or evolving structures.
  • Data is naturally represented as nested documents.
  • Most reads retrieve a complete document or aggregate.
  • Different records may have different attributes.

Example: a content management system where different article types have different metadata could benefit from a document model.

Document databases are not automatically better for JSON. PostgreSQL, for example, supports JSONB alongside relational tables, indexes and SQL.

3. Key-Value Databases

Key-value databases store values associated with unique keys. The primary access pattern is simple: provide a key and retrieve or update its value. 

user:123:session -> "session-data"
product:456:stock -> "20"
rate-limit:api-key-1 -> "42"

The application does not necessarily query the value by arbitrary fields. It often knows the exact key it needs.

Popular technologies

  • Redis
  • Amazon DynamoDB
  • Riak KV

These systems have different capabilities. Redis provides in-memory data structures, while DynamoDB is a managed, distributed database with durable storage and configurable consistency options.

When should you use a key-value database?

  • Fast lookups by known identifiers.
  • Session storage and temporary application state.
  • Rate-limit counters and caching.
  • High-volume access patterns with predictable keys.
  • Distributed workloads that fit the database's key-based model.

Example: a backend that repeatedly reads a merchant's configuration by merchant ID may use Redis to cache the configuration.

A key-value database is less suitable when the application frequently needs complex joins or arbitrary queries across many fields.

4. Wide-Column Databases

Wide-column databases organize data into rows identified by keys, with columns grouped into families or otherwise modeled for distributed access. Their storage and query models differ from traditional relational tables.

They are designed for workloads that may involve huge datasets, high write throughput and distribution across many nodes.

Popular technologies

  • Apache Cassandra
  • Apache HBase
  • Google Cloud Bigtable

How is this different from a relational database?

In a relational database, developers commonly design normalized tables and use joins to retrieve related data.

In many wide-column systems, developers design the data model around the queries they need to execute. Related data may be deliberately duplicated so that a query can be served efficiently without joins.

When should you use a wide-column database?

  • Very large datasets distributed across many machines.
  • High-volume writes with predictable access patterns.
  • Event records, telemetry and activity histories.
  • Workloads requiring horizontal scalability.

Example: a global IoT platform collecting billions of device measurements may consider Cassandra or Bigtable, depending on its query patterns and operational requirements.

Wide-column databases are not simply relational databases with more columns. Their partitioning, query and consistency models need to be understood before choosing them.

5. Graph Databases

Graph databases represent data as nodes and relationships, often with properties attached to both.

They are particularly useful when the relationships between entities are as important as the entities themselves.

Example

(Alice)-[:FRIEND_OF]->(Bob)
(Bob)-[:WORKS_AT]->(Company)
(Alice)-[:PURCHASED]->(Product)

A graph database can traverse relationships to answer questions such as:

  • Which friends of my friends work at this company?
  • Which accounts are connected to a suspicious account?
  • Which products are related through common purchases?
  • How are two entities connected through multiple relationships?

Popular graph databases

  • Neo4j
  • Amazon Neptune
  • ArangoDB

When should you use a graph database?

  • Social networks and relationship discovery.
  • Fraud detection and suspicious-account analysis.
  • Recommendation engines based on connected entities.
  • Dependency graphs and network topology.
  • Queries that repeatedly traverse multiple relationship levels.

Example: a fraud detection system could use relationships between customer accounts, devices, addresses and payment instruments to identify suspicious connections.

You do not need a graph database merely because your data contains relationships. Relational databases handle many relationship-based workloads very well. A graph database becomes attractive when traversing complex connections is a central operation.

6. Time-Series Databases

Time-series databases are optimized for data points associated with timestamps.

Examples include:

timestamp           metric          value
10:00:00            cpu_usage       65
10:00:01            cpu_usage       68
10:00:02            cpu_usage       72

The data is often append-heavy: new measurements arrive continuously, and users query ranges of time to analyze trends.

Popular technologies

  • InfluxDB
  • TimescaleDB
  • Prometheus, primarily for monitoring metrics

Common use cases

  • Infrastructure and application metrics.
  • Sensor and IoT measurements.
  • Stock prices and market measurements.
  • Energy consumption over time.
  • Historical performance monitoring.

When should you use a time-series database?

Consider one when most of your data is timestamped, ingestion rates are high, and queries frequently aggregate values over time windows.

Example: a monitoring system that records thousands of measurements per second and needs to calculate average CPU utilization over the previous hour.

For ordinary business records that happen to include timestamps, a relational database may still be the simplest choice.

7. Search Databases and Search Engines

Search engines are optimized for finding relevant results in text and other indexed fields. They commonly support full-text search, relevance scoring, tokenization, filtering and aggregations.

Example

Imagine a marketplace with millions of products. Users expect to search for phrases such as: 

"waterproof hiking boots for winter"

A search engine can analyze text, match relevant terms, rank results and apply filters such as brand, category, price and availability.

Popular technologies

  • Elasticsearch
  • OpenSearch
  • Apache Solr

When should you use a search engine?

  • Full-text search across large amounts of text.
  • Search results ranked by relevance.
  • Product catalogs with multiple filters.
  • Log search and investigation.
  • Autocomplete and search suggestions.

Example: an e-commerce application can store products in PostgreSQL and maintain a searchable index in Elasticsearch.

Search indexes are often updated asynchronously and may lag behind the primary database. For that reason, the search engine is commonly a derived representation of the data rather than the authoritative source of truth.

8. Vector Databases

Vector databases store and search numerical vectors, often called embeddings. An embedding represents information such as text, images or audio as a list of numbers.

Similar pieces of content can have vectors that are close together according to a chosen similarity metric.

Example

"How do I reset my password?"
                |
                v
          Embedding model
                |
                v
       [0.12, -0.48, 0.73, ...]
                |
                v
       Search similar vectors
                |
                v
       Return relevant documents

Unlike ordinary keyword search, vector search can retrieve conceptually similar content even when the wording differs.

Popular technologies

  • Qdrant
  • Milvus
  • Weaviate
  • pgvector for PostgreSQL

When should you use a vector database?

  • Semantic search over documents.
  • Retrieval-augmented generation (RAG) applications.
  • Finding similar images or products.
  • Recommendations based on vector similarity.
  • Searching large collections of embeddings.

Example: a support chatbot can retrieve the most relevant help-center articles before sending their contents to a language model to generate an answer.

Vector search does not replace every other database. Many applications combine vector similarity with metadata filters, full-text search and relational data.

9. Analytical and Columnar Databases

Analytical databases are optimized for reading and aggregating large amounts of data. Columnar storage is a common technique used by analytical systems.

Row-oriented vs column-oriented storage

A row-oriented database typically stores the fields of a record together conceptually, which is useful when an application reads or updates individual records. 

Row-oriented:

Customer 1: id, name, country
Customer 2: id, name, country
Customer 3: id, name, country

A column-oriented analytical system groups values by column, making it efficient to scan only the fields needed for an aggregation. 

Column-oriented:

IDs:       1, 2, 3
Names:     Alice, Bob, Carol
Countries: NL, DE, NL

This is a simplified illustration. Actual physical layouts, compression and execution strategies vary by system.

Popular technologies

  • ClickHouse
  • Snowflake
  • Google BigQuery
  • Amazon Redshift

When should you use an analytical database?

  • Business intelligence and dashboards.
  • Large-scale reporting and aggregations.
  • Historical analysis across billions of records.
  • Product analytics and event analysis.
  • Data warehouse and analytics workloads.

Example: a payments company wants to analyze millions of transactions to calculate monthly volume by country, currency, merchant category and product.

The transactional application might store each payment in PostgreSQL, while a warehouse or analytical database processes large reporting queries without burdening the main application.

10. In-Memory Databases

In-memory databases keep working data primarily in RAM, allowing very low-latency access. Some also support persistence to disk and replication.

Redis is a well-known example. Despite being frequently used as a cache, Redis also supports counters, sorted sets, queues, streams and other data structures.

When should you use an in-memory database?

  • Low-latency reads and writes.
  • Frequently accessed cached data.
  • Shared sessions and temporary state.
  • Rate limiting and counters.
  • Real-time leaderboards and certain queue workloads.

In-memory storage is not necessarily volatile in every configuration. Persistence and recovery capabilities depend on the product and its settings.

However, RAM is expensive relative to many forms of disk storage, and durability guarantees must be evaluated explicitly. Do not choose an in-memory system as the sole store for critical records simply because it is fast.

11. Embedded Databases

Embedded databases run inside an application or process instead of requiring a separately operated database server.

They can store data in local files and are useful when a complete client-server database deployment would be unnecessary.

Popular technologies

  • SQLite
  • DuckDB
  • RocksDB, an embedded key-value storage engine

These products serve different purposes. SQLite is a transactional relational database, DuckDB focuses on analytical workloads, and RocksDB is an embeddable key-value storage engine.

When should you use an embedded database?

  • Mobile and desktop applications.
  • Local application storage.
  • Command-line tools and development utilities.
  • Offline-first applications.
  • Local analytical queries over files using DuckDB.

Example: a mobile application can use SQLite to store data locally so users can access it without an internet connection.

SQLite is not simply a weaker MySQL. It is an excellent database for many local workloads. However, a multi-instance web backend with concurrent remote clients may be better served by a client-server database.

12. Distributed SQL Databases

Distributed SQL databases aim to provide a relational model and SQL interface while distributing data across multiple nodes.

Depending on the product, they may offer automatic sharding, replication, distributed transactions and fault tolerance.

Popular technologies

  • CockroachDB
  • YugabyteDB
  • Google Cloud Spanner

When should you use distributed SQL?

  • Relational data must be distributed across many nodes.
  • High availability across machines or regions is required.
  • Horizontal scaling is needed alongside SQL and transactions.
  • The application has demanding availability and growth requirements.

Example: a global application needs relational transactions while distributing its data across geographic regions.

Distributed SQL is not a free upgrade from MySQL or PostgreSQL. Network latency, transaction coordination, operational complexity and consistency choices can introduce significant trade-offs.

13. Specialized Databases

Some databases are designed for narrower domains or particular workloads.

Spatial databases

Spatial databases support geographic data and queries such as finding objects within a region or calculating distances. PostgreSQL with PostGIS is a common example.

Use them for maps, delivery zones, geographic analysis and location-based services.

Ledger databases

Ledger-oriented databases provide mechanisms for maintaining verifiable, append-oriented histories of changes. Amazon QLDB was a historical example, but it reached end of support in 2025; it should not be selected for a new project.

Use a ledger-oriented design when tamper evidence and an auditable history are central requirements. A database marketed as a ledger does not automatically replace accounting controls, backups or regulatory compliance.

Hierarchical databases

Hierarchical databases organize records in parent-child tree structures. They are associated with some legacy enterprise systems and workloads where hierarchical access is fundamental.

They are less common for new general-purpose web applications, where relational, document and other models offer greater flexibility for many use cases.

Database Type vs Database Deployment Architecture

It is important to distinguish a database's data model from the way it is deployed.

For example, SQL vs NoSQL describes broad data-model and query differences. Single-node vs distributed describes deployment and data placement. These are different dimensions.

Concept What it describes Example
SQL / NoSQL Data model, query model and associated capabilities PostgreSQL vs MongoDB
Single-node / distributed Where data is stored and processed Single PostgreSQL server vs distributed cluster
Row / columnar storage Physical organization optimized for different access patterns Typical transactional engine vs ClickHouse
OLTP / OLAP Transactional processing vs analytical processing Order processing vs historical reporting
Managed / self-hosted Who operates the database infrastructure Managed cloud database vs self-managed server

SQL vs NoSQL

SQL databases are commonly associated with relational tables, structured schemas and declarative queries. NoSQL is an umbrella term for several non-relational models, including document, key-value, wide-column and graph databases.

Aspect Relational databases NoSQL databases
Data model Tables and relationships Documents, keys, graphs, wide columns or other models
Schema Typically explicitly defined and enforced Varies; may be flexible or query-driven
Relationships Foreign keys and joins are common May use embedding, references or graph edges
Transactions Commonly strong transactional support Capabilities vary significantly by product
Scaling Vertical and horizontal options, depending on architecture Many products are designed for distributed scaling
Query flexibility Generally broad SQL querying capabilities Often depends on the chosen data model and access patterns

NoSQL does not mean "no consistency," "no schema" or "automatically faster." Modern relational databases can scale significantly, and many NoSQL databases support transactions. The important differences are the actual guarantees and capabilities of each product.

OLTP vs OLAP

Another important distinction is whether the database primarily supports day-to-day transactions or large analytical queries.

OLTP OLAP
Online Transaction Processing Online Analytical Processing
Processes individual business operations Analyzes large volumes of historical data
Many short reads and writes Large scans and aggregations
Examples: creating an order, updating an invoice Examples: revenue by country, monthly transaction trends
Often uses row-oriented storage Often uses columnar storage

A common architecture uses an OLTP database for the live application and an analytical warehouse for reporting. Data is transferred through events, change data capture, scheduled pipelines or other ingestion mechanisms.

How to Choose the Right Database

Start with the problem you need to solve, not with a list of popular technologies.

Step 1: Understand your data

  • Is the data relational or naturally document-shaped?
  • Are relationships and joins important?
  • Does the schema change frequently?
  • Must the data be retained permanently?

Step 2: Understand your access patterns

  • Do you retrieve records by ID?
  • Do you run complex filters and joins?
  • Do you search text by relevance?
  • Do you aggregate billions of historical records?
  • Do you traverse many relationships?

Step 3: Define your correctness requirements

  • Can reads be slightly stale?
  • Must concurrent updates never overwrite one another?
  • Do multiple writes need to succeed atomically?
  • Can the system tolerate losing some recent data?
  • Must the application continue during node or region failures?

Step 4: Consider scale and operations

  • How much data will be stored?
  • How many reads and writes occur per second?
  • What are the latency requirements?
  • How will backups, recovery and migrations work?
  • Can the team operate the technology reliably?

Do not introduce a specialized database until its advantages justify the added complexity. An index, a better SQL query, a read replica or a cache may solve the actual bottleneck.

Can One Application Use Multiple Databases?

Yes. This is commonly called polyglot persistence: using different storage technologies for different workloads within the same system.

For example, an e-commerce platform might use: 

                  Client
                    |
                    v
               Application
                    |
       +------------+------------+
       |            |            |
       v            v            v
   PostgreSQL     Redis     Elasticsearch
   (orders,       (cache,   (product
   customers)     sessions) search)
       |
       v
   Analytics Pipeline
       |
       v
   Data Warehouse
   (historical reports)
  • PostgreSQL: authoritative order and customer records.
  • Redis: frequently accessed temporary state.
  • Elasticsearch: a searchable index of products.
  • Data warehouse: large-scale historical analysis.

Each additional database introduces operational costs, failure modes, synchronization requirements and monitoring needs. Use multiple databases when their distinct benefits are worth those costs.

Common Mistakes

1. Choosing NoSQL because it sounds more scalable

Relational databases can handle substantial workloads. First measure the bottleneck and understand the consistency and query requirements.

2. Assuming one database is best at everything

A database optimized for transactions may not be the best choice for full-text search or large analytical scans.

3. Ignoring access patterns

The same dataset can work well in one database and poorly in another depending on how the application reads and writes it.

4. Forgetting consistency and durability

Understand what happens during concurrent updates, replication lag, crashes and failover. These behaviors matter more than a simple benchmark.

5. Introducing too many technologies

Every additional database requires deployment, monitoring, backups, upgrades, security controls and operational knowledge. Simplicity is a real architectural advantage.

6. Using a search index as the authoritative database

Search engines are often eventually consistent projections of application data. Use the system of record for critical writes unless the architecture explicitly establishes otherwise.

What Should I Remember?

  • Relational databases are a strong default for structured business data, relationships, transactions and constraints.
  • Document databases work well for nested records and flexible data structures.
  • Key-value databases excel at lookups by known keys and simple access patterns.
  • Wide-column databases support large-scale distributed workloads with query-driven data models.
  • Graph databases are useful when traversing relationships is central to the application.
  • Time-series databases specialize in timestamped measurements and time-based analysis.
  • Search engines support full-text search, relevance ranking and rich filtering.
  • Vector databases support similarity search over embeddings.
  • Analytical databases optimize large aggregations and historical reporting.
  • In-memory databases provide low-latency operations and useful data structures.
  • Embedded databases are useful for local storage and application-specific workloads.
  • Distributed SQL databases combine relational capabilities with distributed architectures, at the cost of additional complexity.
  • SQL vs NoSQL, OLTP vs OLAP, and single-node vs distributed describe different dimensions of a database system.
  • You do not need a different database for every feature. Start simple and introduce specialized systems when a concrete requirement justifies them.
