N+1 Queries

14 October 2026

The N+1 query problem is a common performance issue in database-backed applications. It occurs when an application executes one query to retrieve a collection of records and then executes an additional query for each record to retrieve related data.

The result is often far more database queries than necessary, increasing response times and database load.

A useful principle is: retrieve related data efficiently instead of making one database round trip per record.

1. What Is the N+1 Query Problem?

Imagine an application that retrieves a list of orders and displays the name of the customer who placed each order.

We have two tables: 

orders
------
id
customer_id
total

customers
---------
id
name

First, the application retrieves all orders: 

SELECT id, customer_id, total
FROM orders;

If the query returns 100 orders, the application might then execute one query per order to retrieve its customer. 

SELECT id, name FROM customers WHERE id = 1;
SELECT id, name FROM customers WHERE id = 2;
SELECT id, name FROM customers WHERE id = 3;

-- ... 97 more queries

The application executes one query for the orders and another 100 queries for the customers. 

Total queries = 1 + 100 = 101

This is called the N+1 query problem: one initial query followed by N additional queries.

2. Why Is It a Problem?

The problem is not necessarily that any individual query is slow. It is the cumulative cost of executing many queries.

  • More database round trips: Each query may require communication between the application and the database.
  • Increased database load: The database must repeatedly process queries and return results.
  • Slower response times: The overhead of many queries can accumulate during a single request.
  • Poor scalability: A page that works with 10 records may become slow when it handles hundreds or thousands.

If the number of records increases, the number of queries increases with it. This makes N+1 problems particularly harmful for endpoints that return large collections.

3. What Does N+1 Look Like in PHP?

N+1 problems often appear when database queries or ORM relationships are accessed inside a loop. 

$orders = $orderRepository->findAll();

foreach ($orders as $order) {
    $customer = $customerRepository->find(
        $order->getCustomerId()
    );

    echo $customer->getName();
}

The initial call retrieves all orders. Inside the loop, each call to find() retrieves one customer.

If there are 100 orders and every lookup executes a separate query, the application performs 101 queries.

Notice that the problem is not the loop itself. The problem is that the loop triggers a database query for every record.

4. Solution: Use a JOIN

If you need data from related tables, you can often retrieve it using a single SQL query with a JOIN. 

SELECT
    o.id AS order_id,
    o.total,
    c.name AS customer_name
FROM orders o
JOIN customers c
    ON c.id = o.customer_id;

Instead of fetching the orders and then querying each customer separately, the database returns the orders together with their customer names.

Typical result: One query instead of 101.

When to use it: When related data belongs in the same result set, such as in reports, list endpoints, and read-heavy queries.

Trade-off: Joins can duplicate parent data when retrieving one-to-many relationships. Joining multiple collections can multiply the number of returned rows.

5. Solution: Use Eager Loading

Many ORMs support relationships between entities. For example, an order may have a relationship to a customer.

With lazy loading, the related customer is retrieved when the application accesses the relationship. If this happens inside a loop, it can trigger N+1 queries. 

// Potential N+1 problem

$orders = Order::all();

foreach ($orders as $order) {
    echo $order->customer->name;
}

In Laravel Eloquent, accessing $order->customer can execute an additional query for each order if the relationship has not already been loaded.

Eager loading retrieves the related data upfront, using a small number of queries instead of querying for each record. 

// Eager loading

$orders = Order::with('customer')->get();

foreach ($orders as $order) {
    echo $order->customer->name;
}

Laravel typically executes two queries: one for the orders and one for the associated customers.

When to use it: When working with ORM relationships and you know which related data the application will need.

Trade-off: Loading every possible relationship can retrieve unnecessary data. Eager-load only the relationships the application actually needs.

6. Solution: Use Batching

Sometimes a JOIN is not possible or the related data comes from another service. In these cases, you can retrieve multiple records in one operation using batching.

Instead of retrieving every customer individually: 

foreach ($orders as $order) {
    $customer = fetchCustomer(
        $order['customer_id']
    );
}

Collect the customer IDs and retrieve the customers together: 

$customerIds = array_unique(
    array_column($orders, 'customer_id')
);

$customers = fetchCustomersByIds($customerIds);

The underlying database query might look like: 

SELECT id, name
FROM customers
WHERE id IN (1, 2, 3, 4, 5);

The application can then map the returned customers to the orders using their IDs.

When to use it: When related data comes from separate services, when a JOIN is not practical, or when many individual lookups can be grouped into fewer requests.

Trade-off: Very large batches may need to be split into smaller chunks. The application must also handle missing records and preserve the relationships between results.

7. Comparing the Solutions

Approach           Typical query count
--------------------------------------
N+1                1 + N
JOIN               1
Eager loading      Often 2 or a few more
Batching           Usually a few

These are typical patterns, not guarantees. The actual query count depends on the ORM, relationship types, batch sizes, and query strategy.

A single query is not always better than multiple queries. A large JOIN that returns many duplicate rows may be less efficient than a small number of focused queries.

The goal is to reduce unnecessary work, not to minimize the query count at all costs.

8. How to Detect N+1 Queries

N+1 problems can be difficult to notice when development datasets are small. Query logs and profiling tools help reveal them.

Inspect query logs

Look for the same SQL statement executing repeatedly with different IDs during a single request. 

SELECT * FROM customers WHERE id = 1;
SELECT * FROM customers WHERE id = 2;
SELECT * FROM customers WHERE id = 3;
...

Use profiling tools

Database query logs, application profilers, and ORM debugging tools can show how many queries a request executes and how much time they take.

Inspect loops and relationships

Be suspicious of database queries or lazy-loaded relationships inside loops, particularly when each iteration uses a different ID. 

foreach ($orders as $order) {
    $customer = $customerRepository->find(
        $order->getCustomerId()
    );
}

A query inside a loop is not automatically an N+1 problem. The important question is whether the repeated operations could reasonably be combined or avoided.

9. N+1 Problems Beyond Databases

The same pattern can occur when calling external APIs.

Imagine an endpoint retrieves 100 orders and then makes 100 HTTP requests to fetch the corresponding customer details. 

foreach ($orders as $order) {
    $customer = $customerApi->getCustomer(
        $order->customerId
    );
}

Although these are HTTP requests rather than SQL queries, the underlying problem is the same: one initial operation triggers many individual operations.

Possible solutions include:

  • Bulk endpoints: Fetch multiple customers in a single HTTP request.
  • Batch processing: Group requests and process them in batches.
  • Caching: Reuse previously fetched data when appropriate.
  • API redesign: Return the required customer information as part of the original response when appropriate.

10. N+1 Queries vs. PHP Generators

PHP generators and eager loading solve different problems.

  • Eager loading: Reduces unnecessary database queries when retrieving related data.
  • Generators: Produce values on demand, which can help reduce memory usage when processing large datasets.

For example, a generator can help process a large number of orders without keeping every order in memory at once. However, it does not automatically eliminate N+1 queries.

These techniques can be combined. An application might process orders in batches, eager-load the associated customers for each batch, and process the orders without loading the entire dataset into memory.

The distinction is: eager loading optimizes database access, while generators optimize how values are produced and consumed.

11. Common Misconceptions

"Adding an index fixes N+1 queries."

An index can make each individual query faster, but it does not eliminate repeated database round trips. A hundred fast queries may still be slower than two well-designed queries.

"A single query is always better."

Not necessarily. Large joins can produce duplicate data and consume more memory. A small number of focused queries can be more efficient.

"Eager loading is always the best solution."

Eager loading is often appropriate for ORM relationships, but joins or batching may be better depending on the use case.

"Every query inside a loop is an N+1 problem."

Not necessarily. The problem occurs when repeated queries could reasonably be combined or avoided.

12. A Practical Optimization Process

When investigating a potential N+1 problem: 

1. Identify a slow or frequently executed endpoint.

2. Inspect the database queries executed by one request.

3. Look for repeated queries with different IDs.

4. Determine which related data is needed.

5. Choose an appropriate solution:
   - JOIN
   - Eager loading
   - Batching

6. Measure the query count and execution time again.

7. Check memory usage and the size of returned results.

8. Verify that the behavior remains efficient as data grows.

Do not stop at reducing the number of queries. Verify that the application actually performs better.

13. N+1 Queries Checklist

  • Does a request execute repeated queries with different IDs?
  • Are ORM relationships being loaded lazily inside a loop?
  • Could a JOIN retrieve the required data more efficiently?
  • Could eager loading avoid repeated relationship lookups?
  • Could multiple lookups be batched into one operation?
  • Are all retrieved columns and relationships necessary?
  • Have query count and execution time been measured?
  • Does performance remain acceptable with larger datasets?
  • Has memory usage been considered as well as query count?

Final Thought

The N+1 query problem is a reminder that code that looks simple does not always execute efficiently.

A single property access inside a loop can trigger hundreds of database queries, especially when ORM relationships are loaded lazily.

The most useful mindset is: understand the queries your code generates, retrieve related data efficiently, and measure the improvement.
