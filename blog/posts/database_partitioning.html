Database Partitioning

October 15, 2026

As a database grows, some tables can contain millions or even billions of rows. Queries against these tables may become expensive, and routine operations such as deleting old records or maintaining indexes can become increasingly difficult.

Database partitioning divides a large table into smaller pieces called partitions. The database can then work with the relevant partitions instead of always processing the entire table.

Let's look at how partitioning works, which strategies databases support, and when it is worth using.

1. What Is Database Partitioning?

Database partitioning is the process of dividing a large table into smaller, logically related pieces based on a defined rule.

From the application's perspective, the data can often still be queried through one table name. The database determines which underlying partitions contain the relevant records.

Imagine an application that stores every payment event in a single table. 

Before partitioning:

payment_events
├── Event from January
├── Event from February
├── Event from March
├── ...
└── Event from December


After partitioning by month:

payment_events
├── payment_events_2026_01
├── payment_events_2026_02
├── payment_events_2026_03
└── ...

These partitions are still part of one logical table. The example uses monthly partitions, but the correct partitioning strategy depends on the data and queries.

2. Why Use Partitioning?

Partition pruning

One of the main benefits of partitioning is partition pruning. When a query includes conditions that identify relevant partitions, the database can skip partitions that cannot contain matching rows.

For example:

SELECT *
FROM payment_events
WHERE created_at >= '2026-10-01'
  AND created_at < '2026-11-01';

If the table is partitioned by month using created_at, the database may only need to scan the October 2026 partition.

Without effective pruning, the database may need to consider many more partitions. The exact behavior depends on the database, query, and partition definition.

Easier data retention

Suppose an application must retain payment events for only a limited period. With time-based partitions, old data may be removed by dropping an entire partition rather than deleting millions of individual rows. 

Old approach:
DELETE FROM payment_events
WHERE created_at < '2024-01-01';

Partitioned approach:
Drop or detach the partitions
that contain expired data.

The exact commands depend on the database. Partition removal must follow the application's retention, audit, and backup requirements.

More manageable maintenance

Some databases allow operations such as creating, attaching, detaching, or maintaining partitions individually. This can make very large tables easier to manage.

Partitioning does not automatically make every query faster, and it does not replace indexes. It is most useful when the partition strategy matches the application's query patterns and maintenance needs.

3. How Does Partitioning Work?

A partitioned table has a partition key and a rule that determines which partition receives each row.

For example, if payment events are partitioned by created_at, the database uses the timestamp to decide which partition stores a new event. 

INSERT INTO payment_events (id, created_at, amount)
VALUES (101, '2026-10-15', 49.99);

The database checks the partition rule
and stores the row in the October 2026 partition.

When reading data, the database can use the query conditions and partition definitions to determine which partitions need to be accessed.

4. Types of Partitioning

Range partitioning

Range partitioning assigns rows to partitions based on ranges of values.

For example, partitioning payment events by date:

Partition 1: January 2026
Partition 2: February 2026
Partition 3: March 2026
...

Advantages:

  • Works well for time-based data and range queries.
  • Can simplify retention by allowing old ranges to be removed.
  • Can make it easier to isolate recent data from historical data.

Disadvantages:

  • Some partitions may grow much faster than others.
  • Queries that do not filter by the partition key may need to access many partitions.

List partitioning

List partitioning assigns rows to partitions based on explicit values.

For example:

Partition 1: country = 'NL'
Partition 2: country = 'BE'
Partition 3: country = 'DE'
Partition 4: Other supported countries

This can be useful when a known set of categories, regions, or business units determines how data should be organized.

The design must account for new values and any default partition behavior supported by the database.

Hash partitioning

Hash partitioning applies a hash function to the partition key and uses the result to assign a row to a partition. 

partition = hash(customer_id) % 4

This is a simplified illustration. A database generally manages the actual hash partition mapping.

Advantages:

  • Can distribute rows relatively evenly across partitions.
  • Can avoid concentrating all recent records in one partition.

Disadvantages:

  • Range queries on the key may need to access many partitions.
  • It is less useful when queries naturally target a particular range or category.

5. Example: Partitioning a Table in PostgreSQL

PostgreSQL supports declarative table partitioning. The following example creates a table partitioned by the range of a timestamp. 

CREATE TABLE payment_events (
    id BIGINT NOT NULL,
    created_at TIMESTAMP NOT NULL,
    amount NUMERIC(12, 2) NOT NULL
) PARTITION BY RANGE (created_at);

Next, create partitions for two months:

CREATE TABLE payment_events_2026_09
PARTITION OF payment_events
FOR VALUES FROM ('2026-09-01')
TO ('2026-10-01');

CREATE TABLE payment_events_2026_10
PARTITION OF payment_events
FOR VALUES FROM ('2026-10-01')
TO ('2026-11-01');

The upper boundary is exclusive. Therefore, the October partition includes timestamps on October 31 and excludes timestamps on November 1.

Insert data through the parent table:

INSERT INTO payment_events (id, created_at, amount)
VALUES
    (1, '2026-09-15 10:00:00', 25.00),
    (2, '2026-10-15 12:30:00', 49.99);

PostgreSQL routes each row to the appropriate partition. The application can query the parent table without naming the individual partitions. 

SELECT *
FROM payment_events
WHERE created_at >= '2026-10-01'
  AND created_at < '2026-11-01';

PostgreSQL can prune partitions that cannot contain matching rows. You can inspect the query plan with EXPLAIN to check which partitions are accessed.

This example is for PostgreSQL. Syntax, capabilities, and limitations differ across database systems.

6. Partitioning vs. Indexing

Partitioning and indexing are different techniques, and they can be used together.

  • Indexing: Creates a data structure that helps the database locate matching rows without scanning the entire table.
  • Partitioning: Divides the table into smaller pieces so that irrelevant partitions can potentially be skipped.

Imagine a table containing several years of payment events.

Partitioning:
Only access the partitions for October 2026.

Indexing:
Within the relevant partition, use an index
to locate events for a specific customer.

Depending on the query, the database may use partition pruning, indexes, both, or neither. You should inspect actual query plans rather than assume partitioning always improves performance.

7. Partitioning vs. Sharding

Partitioning and sharding both divide data, but they usually describe different levels of an architecture.

  • Partitioning: Divides a table or dataset into smaller parts managed by a database system. These partitions may all reside on one database server.
  • Sharding: Distributes subsets of data across separate database instances or servers. 
Partitioning:

Database Server
└── payment_events
    ├── Partition 1
    ├── Partition 2
    └── Partition 3


Sharding:

Application
├── Database Server 1: Customers A–M
└── Database Server 2: Customers N–Z

Partitioning does not necessarily distribute workload across multiple machines. Sharding is generally used when data or throughput needs to be distributed across database instances.

The terminology can overlap. Some database systems support distributed partitioning, and a sharded architecture can use partitioning within each shard.

8. Partitioning Is Not Always Faster

Partitioning adds structure and operational requirements. It is not a universal performance optimization.

Queries without the partition key

If a query does not constrain the partition key, the database may need to inspect many or all partitions. For example, searching by customer ID in a table partitioned only by date might require checking multiple date partitions.

Too many partitions

Creating thousands of tiny partitions can add planning, metadata, and operational overhead. The appropriate number depends on the database, workload, and size of each partition.

Indexes and constraints

Indexes and uniqueness constraints behave differently across database systems and partitioning schemes. Some databases require a unique constraint to include the partition key, for example.

Understand the database's specific limitations before choosing the partition key or schema.

Maintenance

Applications that use time-based partitions may need to create future partitions in advance, monitor partition growth, and decide what happens when a row does not match any existing partition.

9. When Should You Use Partitioning?

Partitioning may be useful when:

  • A table contains a very large number of rows.
  • Queries frequently filter by a suitable partition key.
  • You need to remove or archive old data efficiently.
  • Different parts of a table have different retention or maintenance needs.
  • You have measured a performance or operational problem that partitioning can address.

When might it not be worth it?

  • Your tables are relatively small and perform well.
  • Your queries do not align with the proposed partition key.
  • Indexes and query improvements would solve the problem more simply.
  • The extra partition management would introduce more complexity than value.

Before partitioning a table, measure query performance, inspect query plans, and understand how the table is accessed and maintained.

10. Real-World Example: An Invoicing System

Imagine a billing system that stores millions of invoice events over several years. Most queries retrieve events for a particular invoicing period.

The system could partition the events table by created_at, using monthly partitions. 

invoice_events_2026_08
invoice_events_2026_09
invoice_events_2026_10
invoice_events_2026_11

When an application requests events from October 2026, the database can skip partitions for other months.

If the system also needs to remove data beyond its retention period, old partitions may be detached or dropped according to the database's capabilities and the application's compliance requirements.

This approach can simplify queries and maintenance, but it does not replace the need for appropriate indexes, correct retention policies, and tested operational procedures.

11. Summary

Database partitioning divides a large table into smaller pieces that the database can manage according to a partitioning rule.

The key concepts to remember are:

  • Partitioning divides a table or dataset into smaller pieces.
  • Partition keys determine where rows belong.
  • Range, list, and hash partitioning are common strategies.
  • Partition pruning allows the database to skip partitions that cannot match a query.
  • Indexing and partitioning solve different problems and can be used together.
  • Partitioning is not the same as sharding: partitioning divides data into pieces, while sharding generally distributes pieces across database instances.

The goal is to choose a partitioning strategy that matches your query patterns and maintenance needs. Partitioning can be very effective for large tables, especially time-based data, but it should be driven by a real requirement rather than added by default.
