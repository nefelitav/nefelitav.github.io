REST vs GraphQL vs SOAP vs gRPC vs WebSockets vs MQTT

15 October 2026

APIs allow applications and services to communicate, but they don't all communicate in the same way. Some expose resources over HTTP, some let clients request exactly the data they need, some use strict message contracts, and others support continuous, real-time communication.

REST, GraphQL, SOAP, gRPC, WebSockets, and MQTT are often compared as if they were interchangeable. In reality, they solve different problems and operate at different levels.

1. Quick Comparison

Technology Communication model Typical format Best suited for
REST Request-response Usually JSON Public APIs, CRUD, web backends
GraphQL Client-defined queries Usually JSON Flexible data fetching for frontend applications
SOAP Structured message exchange XML Enterprise systems with strict contracts and WS-* standards
gRPC Remote procedure calls Usually Protocol Buffers Efficient communication between backend services
WebSockets Persistent, bidirectional connection Application-defined messages Chat, live dashboards, multiplayer applications
MQTT Publish-subscribe messaging Application-defined payloads IoT devices, sensors, unreliable networks

Important: REST and GraphQL describe API approaches; SOAP defines a messaging protocol; gRPC is an RPC framework; WebSockets provide a persistent, bidirectional communication channel; and MQTT is a lightweight publish-subscribe messaging protocol. They are related, but they are not all alternatives at exactly the same architectural level.

2. REST (Representational State Transfer)

REST is an architectural style commonly used to build HTTP APIs. It organizes an API around resources, identified by URLs, and uses HTTP methods to perform operations on them.

Example

GET    /users/42
POST   /users
PUT    /users/42
PATCH  /users/42
DELETE /users/42

A typical response might look like this:

{
    "id": 42,
    "name": "Nefeli",
    "email": "nefeli@example.com"
}

How it works

  1. The client sends an HTTP request.
  2. The server processes it.
  3. The server returns an HTTP response with a status code and, often, a JSON body.

Each request is generally independent. REST's stateless constraint means the server does not rely on client session state stored between requests to understand the request. Authentication can still use tokens, cookies, or other mechanisms.

When to use REST

  • Building a conventional backend for a web or mobile application.
  • Exposing a public API to third-party developers.
  • Implementing CRUD operations for users, products, orders, and invoices.
  • Integrating systems that communicate naturally over HTTP.
  • Building APIs that benefit from HTTP caching, standard status codes, and familiar tooling.

Advantages

  • Simple and widely understood.
  • Excellent ecosystem of libraries, documentation, gateways, and debugging tools.
  • Works naturally with HTTP infrastructure.
  • Easy to inspect using a browser, curl, or an API client.

Trade-offs

  • A response may include fields the client does not need.
  • A frontend may need multiple requests to build one screen.
  • API versioning and backward compatibility require deliberate design.
  • Request-response alone is not a natural solution for continuous real-time updates.

Example: A billing backend exposes GET /invoices/123 to retrieve an invoice and POST /invoices to create one.

3. GraphQL

GraphQL is a query language for APIs and a runtime for executing those queries. Instead of defining many resource-specific endpoints, an API commonly exposes a GraphQL endpoint where clients specify which data they want.

Example

query {
    user(id: 42) {
        name
        email
        orders {
            id
            total
        }
    }
}

The server returns the requested fields:

{
    "data": {
        "user": {
            "name": "Nefeli",
            "email": "nefeli@example.com",
            "orders": [
                {
                    "id": "order-123",
                    "total": 49.99
                }
            ]
        }
    }
}

The client requested the user, their name and email, and some fields from their orders. It did not need to call separate endpoints for each resource.

What problem does it solve?

Imagine a mobile screen that needs a user's name, profile picture, and the titles of their latest five orders. A REST API might require multiple requests or return more data than the screen needs. GraphQL allows the client to describe the desired data in one query.

When to use GraphQL

  • Frontend applications with complex screens that combine many related resources.
  • Mobile applications where reducing unnecessary data transfer matters.
  • Products with multiple clients that need different views of the same underlying data.
  • APIs where the data requirements change frequently across frontend teams.

Advantages

  • Clients choose the fields they need.
  • Related data can often be fetched in one request.
  • A schema describes available types, fields, and operations.
  • It can reduce over-fetching and under-fetching.

Trade-offs

  • More complexity in authorization, query validation, and execution.
  • Deep or expensive queries can overload the backend without limits and cost controls.
  • Caching is less straightforward than caching individual REST resources by URL, although it is possible.
  • Poor resolver design can cause the N+1 query problem.

Important: GraphQL does not automatically make an API faster. The server still needs efficient database queries, batching, caching, pagination, and query limits.

GraphQL can also support subscriptions for updates, but these require an appropriate transport and infrastructure; WebSockets are commonly used.

4. SOAP (Simple Object Access Protocol)

SOAP is a protocol for exchanging structured messages. It uses XML-based envelopes and supports formal service contracts. SOAP is common in established enterprise integrations, including some banking, insurance, and government systems.

Example

<soap:Envelope
    xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
    <soap:Body>
        <GetInvoice>
            <InvoiceId>123</InvoiceId>
        </GetInvoice>
    </soap:Body>
</soap:Envelope>

A SOAP request wraps an operation and its parameters inside an XML envelope. A SOAP service may describe its operations and message structures using a WSDL (Web Services Description Language) contract.

What makes SOAP different?

  • XML messaging: messages follow a defined structure.
  • WSDL: describes service operations and the expected message types.
  • WS-* standards: provide extensions for capabilities such as message-level security and reliable messaging.
  • Protocol independence: SOAP is not inherently limited to HTTP, although HTTP is common.

When to use SOAP

  • Integrating with an external provider that only offers a SOAP API.
  • Working with legacy enterprise systems built around WSDL contracts.
  • Interoperating with systems that require particular WS-* standards.
  • Supporting formal, schema-driven contracts in an established enterprise environment.

Advantages

  • Strict message contracts and XML schemas.
  • A mature ecosystem for enterprise integrations.
  • Standardized extensions for specific security and messaging requirements.

Trade-offs

  • XML messages are often more verbose than JSON.
  • Tooling and configuration can be more complex.
  • It is often unnecessarily heavyweight for a new, simple web API.

Example: Your service needs to retrieve payment information from a bank whose integration contract defines SOAP operations. You implement the required SOAP client rather than choosing REST simply because it is more common for modern web APIs.

5. gRPC (Google Remote Procedure Call)

gRPC is a remote procedure call (RPC) framework. Instead of thinking primarily in terms of resources and HTTP methods, a client calls a method exposed by another service.

It commonly uses HTTP/2 for transport and Protocol Buffers (Protobuf) for compact, strongly typed message serialization.

Define a service

syntax = "proto3";

service InvoiceService {
    rpc GetInvoice (GetInvoiceRequest)
        returns (Invoice);
}

message GetInvoiceRequest {
    string invoice_id = 1;
}

message Invoice {
    string invoice_id = 1;
    int64 amount_cents = 2;
    string currency = 3;
}

A client can then call the generated method in its language-specific client library, conceptually like this:

invoice = invoiceClient.GetInvoice({
    invoice_id: "inv_123"
});

The actual generated method signatures depend on the programming language and client library. The important point is that the service contract defines the available methods and message types.

gRPC supports four communication patterns

  • Unary: one request, one response.
  • Server streaming: one request, multiple responses.
  • Client streaming: multiple requests, one response.
  • Bidirectional streaming: both sides can stream messages.

When to use gRPC

  • Communication between backend microservices.
  • High-throughput, low-latency internal service calls.
  • Systems that benefit from strongly typed service contracts and generated clients.
  • Streaming between services.
  • Polyglot environments where services use different programming languages.

Advantages

  • Compact binary messages through Protobuf.
  • Generated clients and service definitions reduce manual integration work.
  • HTTP/2 enables features such as multiplexing and streaming.
  • Supports deadlines, cancellation, and metadata.

Trade-offs

  • Harder to inspect manually than a JSON-based API.
  • Browser integration may require gRPC-Web or a compatible gateway.
  • Protobuf schema evolution needs care.
  • Requires compatible client and server tooling.

Example: An Order Service calls a Payment Service to authorize a payment. Both are backend services maintained by your organization, and you want typed contracts and efficient communication. gRPC could be a good fit.

6. WebSockets

Traditional HTTP follows a request-response model: the client sends a request, and the server sends a response. WebSockets establish a persistent connection that allows both sides to send messages independently.

A WebSocket connection commonly begins with an HTTP handshake and then upgrades to the WebSocket protocol.

How it works

  1. The browser establishes a WebSocket connection to the server.
  2. The connection remains open while both sides are connected.
  3. The server can send an update without waiting for another client request.
  4. The client can also send messages over the same connection.

Browser example

const socket = new WebSocket("wss://example.com/live");

socket.addEventListener("open", () => {
    socket.send(JSON.stringify({
        type: "subscribe",
        channel: "invoice-status"
    }));
});

socket.addEventListener("message", (event) => {
    const message = JSON.parse(event.data);
    console.log("Received update:", message);
});

The server could send a message when an invoice changes status:

{
    "type": "invoice.updated",
    "invoiceId": "inv_123",
    "status": "paid"
}

When to use WebSockets

  • Chat and messaging applications.
  • Live dashboards and real-time notifications.
  • Multiplayer games and collaborative editing.
  • Applications where clients and servers exchange frequent updates in both directions.

Advantages

  • Bidirectional communication over a persistent connection.
  • Low overhead for repeated messages after the connection is established.
  • Servers can push updates immediately.

Trade-offs

  • Connections consume server and infrastructure resources.
  • Reconnection, authentication, heartbeat handling, and horizontal scaling require planning.
  • Applications need to define their own message format and semantics.
  • WebSockets do not automatically provide durable message delivery or replay after disconnection.

Example: A merchant keeps an invoice page open and receives a live notification when the invoice is paid, instead of repeatedly polling an HTTP endpoint.

If the browser only needs occasional updates and can tolerate a delay, ordinary HTTP polling or Server-Sent Events (SSE) may be simpler alternatives.

7. MQTT (Message Queuing Telemetry Transport)

MQTT is a lightweight publish-subscribe messaging protocol designed for devices and networks where bandwidth, power, or connectivity may be limited.

Instead of sending a message directly to a particular recipient, a publisher sends it to a topic through an MQTT broker. Subscribers receive messages for the topics they have subscribed to.

Example

Imagine a temperature sensor publishing readings to this topic:

factory/room-1/temperature

It publishes a payload such as:

{
    "temperature": 22.4
}

A monitoring service subscribes to the topic and receives new readings through the broker.

How it works

  1. A device connects to an MQTT broker.
  2. The device publishes a message to a topic.
  3. The broker forwards the message to matching subscribers.
  4. Subscribers process the message independently of the publisher.

Quality of Service (QoS)

MQTT defines three message delivery QoS levels:

  • QoS 0 — At most once: the message is sent without a protocol-level delivery acknowledgement. It may be lost.
  • QoS 1 — At least once: delivery is acknowledged, but duplicates may occur.
  • QoS 2 — Exactly once: the MQTT protocol uses a handshake to deliver the message exactly once within the relevant protocol exchange.

QoS 2 does not guarantee that your business operation runs exactly once end to end. Applications still need to consider persistent sessions, broker configuration, consumer processing, database transactions, and idempotency.

When to use MQTT

  • IoT devices and sensors.
  • Smart homes, industrial monitoring, and telemetry.
  • Devices operating over slow or unreliable networks.
  • Many devices publishing data to multiple independent consumers.
  • Battery-powered devices where lightweight communication matters.

Advantages

  • Lightweight protocol with relatively low message overhead.
  • Publish-subscribe decouples publishers from subscribers.
  • QoS options allow different delivery trade-offs.
  • Supports retained messages and session features, depending on configuration.

Trade-offs

  • Requires an MQTT broker and appropriate operational management.
  • Not a natural replacement for a conventional public CRUD API.
  • Security, topic permissions, connection limits, and message handling need careful design.
  • Delivery guarantees depend on QoS and configuration, and do not automatically guarantee business-level correctness.

Example: Thousands of temperature sensors send measurements to a broker. Multiple services independently subscribe to readings for alerting, analytics, and storage.

8. The Most Important Differences

REST vs GraphQL

Both are commonly used for HTTP APIs, but they shape data access differently.

  • REST: the server exposes resource-oriented endpoints and defines their responses.
  • GraphQL: the client describes the fields and related data it wants from a schema.

Choose REST for straightforward resource APIs. Consider GraphQL when many clients need different combinations of related data and the flexibility justifies the additional complexity.

REST vs gRPC

  • REST: typically uses HTTP methods, URLs, and JSON representations.
  • gRPC: calls explicitly defined service methods and commonly uses Protobuf over HTTP/2.

REST is often convenient for public APIs and browser-facing applications. gRPC is often attractive for internal service-to-service communication. Neither is automatically faster or better in every system.

SOAP vs REST

  • SOAP: formal XML messaging protocol with an established ecosystem of enterprise standards.
  • REST: architectural style commonly implemented with HTTP and JSON.

For a new, simple HTTP API, REST is often easier. If a partner requires SOAP or relies on specific SOAP standards, use SOAP to meet that contract.

WebSockets vs MQTT

  • WebSockets: provide a persistent, bidirectional connection between two endpoints.
  • MQTT: provides publish-subscribe messaging through a broker.

Use WebSockets for direct, real-time interaction between an application and its server. Use MQTT when lightweight messaging and decoupling many publishers from many subscribers are central requirements.

These are not mutually exclusive. An application can use WebSockets to update a browser while using MQTT to receive messages from IoT devices.

9. How to Choose: Real Scenarios

Scenario Likely choice Why
Build an API for a web shop REST Resource-based endpoints are straightforward to build and consume.
A mobile screen needs selected fields from many related resources GraphQL The client can request the exact data it needs.
Integrate with a bank that requires a SOAP contract SOAP You must comply with the provider's protocol and schema.
Two internal microservices exchange typed requests frequently gRPC Generated contracts and compact messages can be useful.
A browser receives live chat messages WebSockets The server can push messages over a persistent connection.
Thousands of sensors publish readings MQTT Lightweight pub-sub suits device telemetry and multiple consumers.
External developers need a stable, documented API REST or GraphQL Choose based on resource-oriented access versus flexible queries.
A backend service streams a sequence of results to another service gRPC streaming It supports typed streaming RPCs.
A live dashboard updates when backend events occur WebSockets or SSE Use WebSockets for bidirectional interaction; SSE for server-to-client updates only.
Multiple independent systems consume domain events A message broker or event bus Asynchronous messaging may be a better fit than direct API calls. MQTT is one option for suitable messaging needs.

10. Can You Combine Them?

Absolutely. Real systems often use different communication styles for different purposes.

                 Web / Mobile App
                        |
                 REST or GraphQL
                        |
                  API Backend
                   /       \
                gRPC       Message Broker
                 |              |
          Internal Services   MQTT / Events
                                  |
                              IoT Devices

For example, an e-commerce system might use:

  • REST for its public product and order API.
  • GraphQL for a frontend that needs flexible, related data.
  • gRPC for internal calls between Order and Payment services.
  • WebSockets to send live order-status updates to the browser.
  • MQTT for communication with warehouse sensors or connected devices.
  • SOAP when integrating with a legacy external provider that requires it.

You do not need to select one technology for the entire application. Select the communication approach that fits each interaction, while keeping the overall architecture as simple as possible.

11. Common Misconceptions

  • "GraphQL is always better than REST." No. GraphQL provides flexible queries, but adds complexity. REST can be simpler and easier to cache.
  • "gRPC is always faster." Not necessarily. Its binary serialization and transport can help, but performance depends on payloads, network conditions, application logic, and implementation.
  • "WebSockets guarantee message delivery." No. A persistent connection does not automatically provide durable storage, retries, or replay.
  • "MQTT is just WebSockets for IoT." No. MQTT defines a publish-subscribe messaging protocol with broker-based delivery semantics. WebSockets define a bidirectional communication channel.
  • "SOAP is obsolete." SOAP is less common for many new web APIs, but remains relevant when existing enterprise systems and contracts depend on it.
  • "REST means JSON." REST does not require JSON. JSON is simply a common representation format for REST APIs.
  • "All six are competing protocols." They operate at different levels and can coexist in the same system.

12. What Should I Remember?

  • REST: resource-oriented HTTP APIs; a strong default for conventional web backends.
  • GraphQL: clients request the fields and relationships they need.
  • SOAP: structured XML messaging with formal contracts and enterprise standards.
  • gRPC: typed remote procedure calls, commonly used between backend services.
  • WebSockets: persistent, bidirectional communication for real-time applications.
  • MQTT: lightweight, broker-based publish-subscribe messaging, especially for IoT.

The most useful question is not "Which API style is the best?" but "What communication problem am I solving?"

Consider who is communicating, whether communication is synchronous or asynchronous, whether data should be pushed or requested, how strict the contract must be, and what reliability and performance requirements the system has. Those requirements should guide the choice.
