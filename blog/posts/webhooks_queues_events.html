Webhooks, Queues & Events

30 September 2026

Webhooks, queues, Pub/Sub and events are common building blocks for asynchronous and distributed systems. They allow systems to communicate without everything happening inside one synchronous request.

The Big Picture

  • Webhook — "Tell this specific system when something happens."
  • Queue — "Give this work to a consumer to process."
  • Pub/Sub — "Tell everyone interested that something happened."
  • Event — "Something happened."

Webhooks

A webhook is an HTTP callback. Instead of repeatedly asking whether something happened, a server sends an HTTP request to a URL provided by the receiving system. 

Client                    Server


POST /payments ──────────►
◄────────── 200 OK


    ... payment completed ...


POST /webhook ◄───────────

For example, a payment provider can notify a merchant when a payment is completed. 

POST /webhooks/payment


{
"event": "payment.completed",
"payment_id": "pay_123"
}

Webhooks are simply HTTP requests, so they need many of the same considerations as normal APIs:

  • Authentication
  • Signature verification
  • Retries
  • Timeouts
  • Idempotency
  • Monitoring

Webhook Signatures

Since webhook endpoints are often publicly reachable, the receiver needs a way to verify that the request came from the expected sender. 

Webhook-Signature: t=1727683200,v1=abc123...

The receiver can verify the signature using a shared secret, preventing arbitrary clients from sending fake events.

Queues

A message queue allows one system to send work without requiring another system to process it immediately. 

Producer
↓
Queue
↓
Consumer

For example, an API can put an invoice-generation task on a queue and let a worker process it later. 

API
│
│ publish
▼
Queue
│
│ consume
▼
Invoice Worker
│
▼
Invoice

Why Use a Queue?

  • Decoupling — producer and consumer don't need to operate at the same time.
  • Buffering — queues can absorb traffic spikes.
  • Retries — failed messages can often be retried.
  • Scaling — multiple workers can process messages in parallel. 
Queue
│
├── Worker 1
├── Worker 2
├── Worker 3
└── Worker 4

These are often called competing consumers: a particular message is generally processed by one worker rather than by all workers.

Events

An event represents something that happened in a system. 

payment.created
payment.completed
invoice.generated
customer.updated
order.cancelled

An event describes a fact rather than a command. 

Command:
CreatePayment

Event:
PaymentCreated

A command means "please do this". An event means "this already happened".

Pub/Sub

Pub/Sub (Publish/Subscribe) allows a publisher to send a message to a topic that multiple independent subscribers can receive. 

                 ┌──► Billing
             │
Publisher ───► Topic ───► Notifications
│
└──► Analytics

The publisher does not need to know which subscribers exist. Each subscriber can process the message independently.

Queue vs Pub/Sub

Queue:
Producer ───► Queue
│
┌────┴────┐
▼         ▼
Worker A  Worker B

A message is generally processed
by one competing consumer.

Pub/Sub:

Producer ───► Topic
│
┌───────┼───────┐
▼       ▼       ▼
Billing  Alerts  Analytics

Each subscription can receive
its own copy of the message.

A useful mental model:

  • Queue: "Here is work. Someone process it."
  • Pub/Sub: "Something happened. Everyone interested can react."

Topics & Subscriptions

PaymentCompleted Topic
      │
┌─────┴─────┐
│           │
Subscription A  Subscription B
│           │
▼           ▼
Notifications  Accounting

Each subscription can have its own processing state, retries and backlog. This means one subscriber can be temporarily unavailable without necessarily blocking the others.

Event-Driven Architecture

In an event-driven architecture, systems communicate by producing and consuming events. 

Payment Service
  │
  │ PaymentCompleted
  ▼
Event Broker
│
├──► Billing
├──► Notifications
└──► Analytics

The payment service does not need to know about every consumer. New consumers can be added independently, reducing coupling between services.

They Are Not the Same Thing

  • Event — describes what happened.
  • Queue — delivers work to consumers.
  • Pub/Sub — distributes messages to multiple subscribers.
  • Webhook — typically uses HTTP to notify a specific external system.

Message Brokers

A message broker is infrastructure that receives, stores and delivers messages between producers and consumers. 

Producer
↓
Broker
↓
Consumer

Brokers can support different messaging patterns, including queues and Pub/Sub.

Examples include RabbitMQ, Apache Kafka, Google Cloud Pub/Sub, Amazon SQS and Azure Service Bus. They have different models and capabilities, so they should not be treated as interchangeable.

How They Work Together

These concepts can be combined in a single system. 

Payment API
 │
 │ PaymentCompleted
 ▼
Event Broker
│
├──► Billing Service
├──► Notification Service
└──► Webhook Service
│
▼
Merchant API
  1. A payment is completed.
  2. A PaymentCompleted event is published.
  3. A messaging system distributes the event.
  4. Billing consumes it and creates an invoice.
  5. A webhook service notifies the merchant.

Important Challenges

Duplicate Messages

Messages may sometimes be delivered more than once. Consumers should therefore handle duplicates safely.

Retries

Temporary failures can trigger retries, but unlimited retries can make failures worse.

Dead-Letter Queues

Messages that repeatedly fail can be moved to a dead-letter queue for investigation or later processing. 

Queue
│
├── success ─────► Consumer
│
└── repeated failure
│
▼
Dead-Letter Queue

Ordering

Sometimes events must be processed in the correct order. 

PaymentCreated
↓
PaymentAuthorized
↓
PaymentCompleted

Idempotency

Consumers should often be able to process the same message more than once without producing an incorrect result.

What Should I Remember?

  • A webhook is typically an HTTP callback used to notify a specific system.
  • A queue buffers and distributes work to consumers.
  • Pub/Sub distributes messages to multiple independent subscribers.
  • An event represents something that happened.
  • A command asks a system to do something, while an event describes something that happened.
  • Message brokers can support queues, Pub/Sub and other messaging patterns.
  • Webhooks, queues, Pub/Sub and events can be combined to build asynchronous, loosely coupled systems.
  • Retries, duplicates, ordering, dead-letter queues and idempotency are important distributed-system concerns.
