JWT vs Session-Based Authentication

15 October 2026

After a user logs in, how does the server recognize them on their next request? Two common approaches are server-side sessions and token-based authentication using JWTs.

1. Session-Based Authentication

With session-based authentication, the server creates a session and stores its state on the server side. The browser receives a session identifier, usually in a cookie.

1. User submits credentials
2. Server verifies credentials
3. Server creates session: session_id = abc123
4. Browser stores session ID in a cookie
5. Browser sends cookie on future requests
6. Server looks up the session and authenticates the user

Example cookie

Set-Cookie: session_id=abc123;
            HttpOnly;
            Secure;
            SameSite=Lax

The session ID is an opaque identifier. It should not contain user information that the server blindly trusts. The server uses it to find the corresponding session.

Advantages

  • Sessions can be invalidated centrally, for example on logout.
  • Session state can be updated without issuing a new token to the browser.
  • Works naturally with traditional server-rendered web applications.

Trade-offs

  • The application needs a session store, such as a database or Redis, when sessions are not held locally.
  • Multiple application instances need access to the shared session state or another compatible session strategy.
  • Cookie-based authentication requires appropriate CSRF protections when the browser automatically sends credentials.

2. JWT-Based Authentication

JWT stands for JSON Web Token. It is a format for representing claims in a token. A JWT can be signed, allowing the receiver to verify its integrity and origin. A signed JWT is not necessarily encrypted.

In a common access-token setup, the server issues a token after authentication. The client sends it on later requests, and the API validates it.

1. User authenticates
2. Server issues an access token
3. Client stores the token appropriately
4. Client sends token with API requests
5. API validates signature and relevant claims
6. API checks authorization and processes request

Example JWT payload

{
  "sub": "user_123",
  "iss": "https://auth.example.com",
  "aud": "invoice-api",
  "exp": 1792000000
}

A JWT commonly has three Base64URL-encoded sections: header, payload, and signature. Base64URL encoding is not encryption, so don't put secrets in a normal signed JWT payload.

Validation matters

  • Verify the signature using an explicitly allowed algorithm and trusted key.
  • Validate expiration and, when applicable, not-before time.
  • Validate issuer and audience.
  • Use the token only for its intended purpose.
  • Apply authorization checks even after authentication succeeds.

Advantages

  • A service can validate a properly signed token without looking up a session on every request.
  • Useful for APIs and distributed systems where multiple services need to validate tokens.
  • Claims can carry limited information needed by the recipient.

Trade-offs

  • Revoking a JWT before it expires can be harder without a denylist or another server-side mechanism.
  • Long-lived tokens increase the impact of token theft.
  • JWTs are easy to misuse if validation rules or storage decisions are incorrect.
  • JWTs can become large and should not carry unnecessary claims.

4. Stateless vs Stateful

JWT is often called stateless because a service can validate it without querying a session store. But a system using JWTs can still be stateful: it might maintain refresh-token records, revocation lists, user status, or authorization data.

Likewise, sessions don't require a single server. A shared Redis session store can support multiple backend instances.

5. Can JWTs Be Stored in Cookies?

Yes. JWT describes the token format, not where the browser stores it. A JWT can be stored in a cookie, and a session identifier can also be stored in a cookie.

For a browser application, an HttpOnly, Secure cookie can reduce direct JavaScript access to the credential. However, cookies are sent automatically in matching requests, so CSRF protection and appropriate SameSite settings remain important. Storing tokens in local storage makes them accessible to JavaScript and therefore more exposed if an XSS vulnerability occurs.

6. When Would I Choose Each?

Choose server-side sessions when:

  • You are building a conventional web application with a backend.
  • You want simple session invalidation and centralized session control.
  • You don't need independently verifiable access tokens across many services.

Consider JWT access tokens when:

  • You have multiple APIs that need to validate tokens issued by a trusted identity service.
  • You have a defined token lifecycle and need to support service-to-service authorization.
  • You understand and can implement expiration, key rotation, revocation, and secure storage appropriately.

7. Common Mistakes

  • Assuming a JWT is encrypted: a signed JWT payload is readable by anyone who obtains it.
  • Making tokens last forever: use sensible expirations and a refresh strategy where needed.
  • Assuming logout invalidates every JWT: deleting a token from the client does not invalidate a copy already stolen.
  • Skipping authorization: authentication establishes identity; authorization determines permitted actions.
  • Thinking JWT is always more scalable: databases, caches, network calls, and other bottlenecks still matter.

8. What Should I Remember?

  • Session: a server-managed login state, commonly identified by a cookie.
  • JWT: a token format that can carry signed claims.
  • JWT and sessions can coexist: they're not mutually exclusive approaches.
  • Security depends on the whole design: expiration, revocation, transport, storage, and authorization matter.

For a typical server-backed web application, I'd seriously consider a secure session cookie before introducing JWT complexity. For distributed APIs, JWT access tokens may be a better fit when their benefits are actually needed.
